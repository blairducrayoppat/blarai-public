What the battery is, in one paragraph

The thing being measured

Every night at 11 PM, BlarAI gives its coding assistant a small software project written the way a normal person would ask for it — "I want a flashcard program I can use from a command window." The assistant plans the work, breaks it into pieces, builds each piece, and checks its own work as it goes. At the end, a separate final exam runs: a set of tests that decides whether the finished program actually does what was asked. Each run gets a verdict (did it succeed?) and, if it didn't, an attribution — whose fault was it? The choices are roughly: the coder built it wrong, the plan was bad, the checking machinery broke, or the surrounding system failed. That attribution is the number that matters, because it's what tells you whether the assistant is getting better.

The defect: the exam was broken, and the student was failed for it

Look at B4's row again. Every one of its six build stages passed. All six pieces of the program were built, checked, and merged successfully. Then the final exam ran, failed four of its six questions, and the run was blamed on the coder.

Here is what those four failures actually were. Three of them are this:

NameError: name 'data_storage' is not defined

The exam refers to a part of the program it never actually opened. That's not the program being wrong — that's the exam paper referring to a page it forgot to turn to. The fourth failure is subtler and, if anything, worse: the exam ran the "does the program exit cleanly when I ask it to?" test, the program exited cleanly, and the exam recorded that as a failure because it wasn't written to expect the thing it had just asked for.

Why it did that, and why the design isn't stupid

The component that spots a broken exam is deliberately advisory only. It is forbidden from changing a verdict — and that restriction is correct. It exists so that no clever after-the-fact classifier can ever quietly upgrade a failure into a success. That's a genuine safety property and I have not touched it.

The defect is narrower: the part of the code that decides whose fault it was never asks whether the exam was fit to judge. It looks at exactly two things — did the final exam fail, and was it flaky? If the exam failed and wasn't flaky, blame the coder. There is no third question, and "was this exam even valid?" is that missing third question.

It has happened before

This is not a one-off. The project's own quality ledger records the same card, on 2026-07-16, with the identical pairing: parked, blamed on the coder, internally flagged as a broken examiner. That's at least two occurrences in four days, both unnoticed.

The cost is that your campaign's permanent record now carries coder-blame for examiner bugs. The battery exists to answer one question — is the coding assistant getting better? — and its evidence base has been quietly accumulating wrong answers.

What I did about it

Filed as ticket #965 and the fix is built. It adds the missing third question: if the exam covered none of what was asked, a failure against it is attributed to the checking machinery, not the coder. It can never turn a failure into a success — a parked run stays parked; only the blame label changes, so your pass/fail banking is untouched. Because a repeat offence requires a permanent guard rather than a patch, it ships with tests that lock the behaviour both ways: a broken exam must re-route the blame, and a valid exam must still blame the coder — so we can tell "this control works" apart from "this control can't reach anything."

Three smaller defects surfaced alongside it, filed as #967. The most interesting one explains how the broken exam got through: the quality checker mistakenly flags legitimate references as "invented," and because it ranks those higher than real problems, both of the system's two repair attempts were spent chasing false alarms while the 0-out-of-6 coverage went untouched. The repair even introduced the data_storage error while trying to fix a non-problem.

The web card: I owe you a correction

Earlier today I told you adding the web-based test job might not fit in the nightly window, and cited a number. That number was real but it was the wrong kind of number, and it alarmed you for no reason.

Two numbers that are easy to confuse

A budget is a safety cap — "stop this job if it somehow runs this long." It's set deliberately generous, because its job is to catch runaway processes, not to predict anything. Runtime is how long the work actually takes. I quoted you budget arithmetic as though it forecast runtime. In practice these jobs finish in roughly a third to a half of their budget: last night's two jobs had 8.7 hours of budget between them and were done in 3.7.

A three-job night would likely finish around 6 AM — well inside a window that allows until 3 PM. The web card fits.

And its history makes the case stronger, not weaker. The web card, B5, was benched for "harness failures." I pulled every run of it. Both failures say the same thing:

TIMED OUT — the overall run budget elapsed mid-task

It ran out of budget. That is precisely the starvation bug that ticket #927 — the merge I own for tomorrow — exists to fix. The web card wasn't failing because web work is hard; it was failing because it was given three hours for a job that needs more. The two tasks you gave me are the same fix, and the correct order is the one already scheduled: budgets tomorrow, web card the night after.

One honest unknown: because B5 was always killed at the cap, nobody knows how long it truly takes. Its first properly-funded night is partly a measurement.

The real problem: nobody owned the read

You said things were falling through the cracks. I checked every change made in both repositories today. Today was genuinely productive — five merges plus an entire publications programme stood up. Not one of them touched last night's battery.

The cause is structural, not effort. Every reliably-completed item in this project has a ticket and a named owner. The morning read is the one recurring obligation that is assumed rather than assigned — so on a busy day it is the thing with nobody's name on it, and it evaporates. The same cause produced the 07-18 slip that pushed #790 a day late. That's twice in one week from one root cause.

Make the morning read an owned, recurring item.Recommended

Filed as #966. A standing item that opens each morning carrying the read's checklist, and counts as done only when findings are recorded on tickets — a read that leaves no durable record didn't happen. Best version: the battery writes the item itself when a night completes, so the reminder is produced by the thing needing to be read rather than by someone remembering. That converts this from a vigilance problem into a structural one, which is the pattern this project already uses everywhere else.
