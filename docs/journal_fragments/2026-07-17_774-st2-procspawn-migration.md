### 2026-07-17 — #774 sub-task 2: routing the fleet's raw spawns through the blessed helper, honesty over completeness

*Plain summary: I moved 10 of the 12 raw process-spawn sites in the fleet code onto the one vetted spawn helper (shared/procspawn.py), and — the load-bearing judgment — deliberately LEFT two of them raw because routing them through the helper would have changed what they do. The safety gate that tracks this debt shrank from 12 tracked sites to 2, exactly as designed.*

Sub-task 4 had welded the spawn-surface gate shut the day before: `tests/integration/test_no_new_raw_spawn_sites.py` AST-scans all production `shared/`/`services/`/`launcher/` code, fails loud on any raw `subprocess.*`/`os.spawn*`/`os.system` call not in a documented allowlist, and — via `test_allowlist_not_stale` + `test_allowlist_matches_live_surface_exactly` — forces the allowlist to shrink in lockstep with any migration. Sub-task 2's job was to pay down the Group-A debt: the 12 `shared/fleet/*` sites the allowlist listed as migration targets. This branch is the payment: `feat/774-st2-procspawn-migration`, off main at the sub-task-4 gate `79248f55`.

The mapping was mostly mechanical once I read `shared/procspawn.py` end to end. The captured pytest/tasklist/git runs (`dispatch._safe_run`, `oracle_qa._default_run`, `static_pregate._default_run`, `swap_ops._default_hermetic_run`, `swap_ops.real_ovms_alive`, and the transport's `_interp_has_af_hyperv` probe) are the `hidden_console` shape — `subprocess.run` + `CREATE_NO_WINDOW` for a non-interactive console child of the console-less pythonw driver, which is exactly what those sites already were. The two DETACHED launcher/driver spawns (`swap_ops.restart_launcher`, `swap_ops._spawn_detached_driver`) and the detached pwsh fleet-trigger (`dispatch.run_fleet`) are the `detached_no_console` shape. `restart_launcher` collapsed especially well: its hand-rolled breakaway-then-OSError-fallback double-`Popen`, its manual UTF-8 log-file open/close, and its `PYTHONIOENCODING` `setdefault` are the *precise* wiring `detached_no_console` encodes, so two Popen calls became one helper call with no behavior lost.

The real work was NOT migrating everything. Two sites I left raw on purpose, and saying why is the point:

- `guest_oracle._default_pytest_run` runs the coder's snapshot pytest INSIDE the NIC-less Alpine guest. That module ships across the vsock isolation boundary and is stdlib-only at module scope by design. Taking a `shared.procspawn` dependency there would enlarge what has to be trusted inside the isolated guest — the opposite of security_by_design principle 9. Leaving it raw is the *secure* call, not the lazy one.
- `guest_oracle_transport.GuestOracleBridge._run` speaks a BINARY frame protocol: bytes stdin (a JSON line plus length-prefixed request frames) and bytes stdout parsed as frames. Every procspawn helper decodes stdout to UTF-8 text with `errors='replace'` and none accepts bytes input, so routing this through the blessed surface would silently corrupt the vsock frames. The helper genuinely does not serve this need; forcing it would be a bug dressed as tidiness.

So the ratchet went 12 → 2, and the two survivors carry a comment at the site AND in the allowlist explaining the constraint. The honest tension I had to sit with: "behavior-preserving" and "route through the helper that ADDS the learned hardening" pull against each other. The helper's whole reason to exist (lesson 219) is to pin the child to UTF-8 (`PYTHONUTF8`/`PYTHONIOENCODING`), feed DEVNULL stdin, and add tree-kill/breakaway-fallback — every migration therefore changes the child's I/O env slightly. I resolved it by reading "behavior-preserving" as *preserve the dispatch's observable contract* (same argv, same cwd, same success/failure semantics, same return shape, same detach/lifecycle), and treating the R3/R4/R5 hardening as the intended, gate-documented effect rather than a regression. The rejected alternative — refuse any site whose child env changes — would have migrated zero sites and defeated the sub-task.

Two deltas I flag rather than hide: `run_fleet` now returns `popen_failed` only after BOTH the breakaway and the detached-only attempt fail (the helper owns the fallback the loop used to spell out), and `_spawn_detached_driver` GAINED the breakaway→detached-only fallback it previously lacked — matching `restart_launcher`'s robustness. Both are error-path improvements on an already-approved capability, not new behavior on the happy path.

Since I was editing the gate anyway, I folded the three sub-task-4 review nits. N1: the alias resolver was a single in-source-order pass, so a spawn call syntactically ABOVE its `import subprocess` was resolved against an empty alias map and silently missed. I split it into a two-pass scan (`_AliasCollector` first, `_SpawnCallFinder` second) and added a regression test with a helper defined above a bottom-of-file import. N2: documented the gate's API boundary (covers `subprocess.*` + the `os` spawn/exec/system family; NOT `ctypes` Win32 `CreateProcess`, `os.startfile`, or `asyncio.create_subprocess_*`) in both the gate docstring and TEST_GOVERNANCE §2.7. N3: broadened the parse-error `except` from bare `SyntaxError` to also catch `ValueError` (null bytes) and `UnicodeDecodeError` (a non-UTF-8 file) so an unscannable file fails the gate cleanly instead of crashing it — with a test proving the non-UTF-8 file becomes a fail-closed `parse_errors` entry (the case the old bare `except` would have let escape). Interesting wrinkle: on this CPython (3.11.9) null bytes surface as `SyntaxError`, not `ValueError`, so the load-bearing broadening is really the `UnicodeDecodeError` one; I kept `ValueError` as the task specified for version-robustness.

Verification: the gate is green with the 12→2 allowlist and both new self-tests (14 passed). Behavior preservation is carried by the existing fleet tests, which mostly monkeypatch `subprocess.Popen`/`subprocess.run` at module scope — and because the helper calls those same globals internally, the patches still intercept, so the tests assert the helper produces the identical flags/handles/env the raw calls did (`restart_launcher` still spawns twice on the OSError fallback with DETACHED-not-CREATE_NO_WINDOW and PYTHONIOENCODING=utf-8; `_spawn_detached_driver` still resolves the pythonw sibling; `run_fleet` still detaches with the RunId). Total 877 tests across every module the migration touched: 0 failed, 0 unexpected skips. LOCALAPPDATA was redirected for every run.

Left deliberately un-pruned to keep this battery-adjacent diff tight and behavior-obvious: a few now-redundant module constants (`dispatch._CREATE_BREAKAWAY_FROM_JOB`, `oracle_qa._NO_WINDOW`, `swap_ops._DETACHED`/`_NEW_GROUP`/`_BREAKAWAY`) and the `swap_ops.pythonw_sibling` helper that `procspawn` now mirrors. They are harmless module-level names (not lint-flagged) and document the flags; a follow-up can prune them once this lands.

Proposed lesson: *When ratcheting raw calls onto a blessed helper, "migrate everything" is the wrong target — "migrate everything the helper can serve without changing what the call DOES" is right. Two classes legitimately stay raw: code that ships across an isolation boundary (adding the dependency enlarges the trusted surface) and code whose contract the helper cannot express (a binary protocol under a text-decoding helper). Name the survivors at the site and in the allowlist; the helper's added hardening is the intended effect, not a behavior break, so long as the observable dispatch contract is preserved.*
