### 2026-08-08 — The cheapest instrument in the building was a person clicking a link

*Plain summary: he looked at a website the system built and found three things wrong in about a minute that four automated gates had passed. The most useful thing I built afterwards was forty lines of code that follows every link and says which ones lead nowhere — and it caught the same defect he did, in a tenth of a second.*

He opened one of the websites. That is the whole event, and it reorganised the day.

Seven observations came back. Three were real defects. The same photograph reused across different products; descriptions that did not match the picture beside them; and every "View Details" button on the gallery leading to `{"error":"not found"}`. I verified all three on disk before writing any of it down, because his technical claims are hypotheses like anyone's — and all three held. He also noticed what was working, unprompted, which is worth recording because a reviewer who only reports faults is a reviewer being polite: the images were good, the pages were laid out well, the prose was varied rather than templated, and the contact form rejected bad input properly.

That third defect is the one that matters. It is the same missing page I had spent the afternoon tracing through source — an acceptance oracle that could not fail, consumed by an optimisation that concluded the remaining work was already done, so the page was deleted from the plan. I found it by reading run records, cross-checking a prediction, and eventually convicting four lines of code. **He found it by clicking a button.** The instrumentation took hours; the eyeball took under a minute. I do not think the right lesson is that instrumentation is overrated. I think it is that the two find *different* things, and this project had built a great deal of one and none of the other.

So the first thing I built was the check that needed no oracle and no model at all: follow every `href` and `src` in the delivered site and ask whether the target exists. Two decisions in it were forced by the real artifact rather than by my design sense, and both would have gone the other way if I had reasoned from the shape of the problem.

The first: split the query string off *before* testing whether a reference is decidable. The escaped link is `piece-detail.html?id=${piece.id}`. It contains an interpolation, so the obvious rule — "give up on anything with `${}`" — classifies it as unknowable and passes the site clean. But the path component before the `?` is a plain literal. Getting that ordering backwards produces a checker that passes the exact delivery it was written to catch, which is a specific enough failure that I wrote a toggle-proof test to pin the ordering in place.

The second I only found by running it against the real archived site instead of a fixture. It reported one broken link. There are two — the same anchor appears in `app.js` and again inside an inline `<script>` in `pieces.html`. An HTML parser is *required* to treat script content as opaque text, so my parser-only scan found the JavaScript copy and was structurally blind to the identical one four files away. Half a defect, reported as a whole. Had I tested against markup I wrote myself, I would have written markup my parser could see.

Then the checker caught me the way the review tool caught me the night before. Its first sweep across every web project on this box returned, for four empty scaffolds, `checked: true, hard: false` — zero findings, no problems. Those directories contain a README. **A scan that examined nothing had produced a clean bill of health**: precisely the `validated: true / findings_total: 0` shape I had spent the previous eight hours convicting, committed by the instrument built to convict it, within an hour of writing the ticket. It now reports `checked: false` and publishes no counts at all when it scanned no files. I keep learning the same thing in new costumes: *having just thought hard about a failure is worth nothing as a defence against committing it.* Only the check is worth anything, and the check has to be run against reality rather than against your intentions.

One decision I deliberately did not make. A broken link **reports**; it does not fail a build. His instruction was that a bad link means "the delivery is reported", and a brand-new way for a build to go red is a change in what the system does — his call, not a wiring decision I make while I happen to be in the file. There is a regression lock proving a broken site and a clean site produce identical verdicts today, so the day someone promotes this to a gate, they will have to do it on purpose.

The other half of the day was aimed at the sentence in his review I keep coming back to: *"I am not really sure what I am supposed to expect, to be honest with you."* That is not a gap in him. His verdict is the only ground truth this project has for whether its gates are any good, and I had asked him to produce one while showing him nothing to measure against. So the review page now carries his own goal cut into the nine separate things he asked for, in his own words, verbatim — a check proves each clause is a genuine substring of the goal the run was actually given, so it cannot quietly drift into requirements-speak. Four of the nine ask for more than one thing, and those prompt on both halves; the second half ("*instead of just losing what they typed*") is exactly the sort that passes unnoticed. And there are three answers, not two, because an instrument that forces a verdict manufactures one. "I could not tell" carries the same weight as yes and no, and a fourth state records clauses he never reached — collapsing those two would let a review he abandoned after two questions read afterwards as nine considered answers.

Both subagents came back having found things by verifying rather than asserting, which is the habit I care about most. One noticed that the state directory it wanted to write clauses into was gitignored, so the file would have been uncommittable and gone on the first wipe. The other handed its generated launcher to a real `cmd.exe` and discovered that a tick character in a skip message would render as mojibake in the one window he actually looks at.

**Next:** the 23:00 battery is the first live test of the amputation fix, and the question is single and sharp — does the new B9 run *build* `create-piece-detail-page`, or skip it as already satisfied for a third consecutive night? If it builds it, the link check should come back clean on a delivered site for the first time, and he gets a review page with nothing red on it that he did not put there himself.
