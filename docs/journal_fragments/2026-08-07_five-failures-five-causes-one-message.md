### 2026-08-07 — Five failures, five causes, and two of them printed the same sentence

*Plain summary: the multi-page website test had never once run. Tonight it failed five times before it worked, and every failure was in the machinery around the coder rather than the coder itself. Two of them printed identical error text for completely unrelated reasons. It is now building the site — and the first task took 40 minutes while the next two took 8 and 11, which changes what we thought the whole thing costs.*

B9 is the card that measures the thing the operator says is his priority: a website with several pages that share a layout and a data source. It was authored on 2026-08-06 and had never been run. Tonight it ran five times.

**Attempt 1** died at the approve. I launched it with `Start-Process -WindowStyle Hidden` to dodge the harness's process reaper, and that context has no GPU. The boot log ends `opencl device count:2` followed by `no opencl gpu device is available` and `invalid gpu device in environment: index 0` — it *enumerated both devices and could use neither*. The model never loaded, the assistant accepted the socket and never answered. My mistake, against a rule I had written down myself: GPU work launches via an elevated scheduled task.

**Attempt 2** died in preflight, and this is where I made it worse. Attempt 1 had left an `ovms.exe` — the model server — resident. The box read **Available 0.05 GB of 31.32**, while the top ten processes summed to under one gigabyte, because the integrated GPU draws its VRAM from system memory and it appears in nobody's working set. I killed it, reclaimed 27 GB, and moved on satisfied.

**Attempt 3** died on a `Move-Item`, and taught the actual lesson. My cleanup had been half a cleanup: I killed the model server and left attempt 1's *swap driver* alive. That driver is detached by design — its own log says "the launcher is exiting now" — and it kept building in the sandbox until 18:39, an hour after the run that spawned it had exited. Attempt 3 archived that directory out from under it at 18:13. Both died: attempt 3 on a locked `public\` folder it could not move, and attempt 1's three candidates on `fatal: not a git repository: (NULL)` once their worktree's git pointer was emptied. They destroyed each other over one directory.

The transferable part is not "reap your orphans." It is that **I selected by memory footprint when ownership was the question**. Attempt 3's preflight read a clean 26.2 GiB and `nothing to lean — no restartable app was running`, while a live dispatch owned the very folder it was about to move. A swap driver mid-build is not a memory hog. Ownership was sitting on disk the whole time: a fleet journal with more `TASK-START` than `TASK-END` still owns its repo. That is the admission check now, and I verified it against the real artifact — at 18:13 that journal read 1 and 0, so it would have refused.

**Attempt 4** died at the approve again, with the *identical message* to attempt 1: `approve did not fire EXECUTE: No response from the Assistant Orchestrator`. Same sentence, entirely different cause. Attempt 4's assistant was healthy — zero GPU errors, 26 GiB free, egress guard armed. What killed it was that every battery run used the session key `"battery"`, a constant, and the coordinator parks its pending dispatch durably against that key. Attempt 1 created a pending plan, stalled, never cleared it; attempt 4 opened the same key and inherited it, then approved a plan whose sandbox had since been archived.

I had already seen the fingerprint and dismissed it. An hour earlier I filed a ticket noting that attempt 4's scorecard carried attempt 1's `run_id` — I called it a provenance nit and moved on. That borrowed id could only have come from the inherited pending slot. It was not a cosmetic defect standing near the real one; it *was* the real one, seen from the other end. Two tickets, one bug.

The fix is a per-run session key rather than a teardown step, and the reason matters more than the change: **the contaminating run had crashed**, so any cleanup it was supposed to perform would not have performed. Two runs that do not share a key cannot contaminate each other whatever either does.

**Attempt 5 is building the website.** Three tasks delivered and merged — home page, contact page, piece list — and the shared-layout task running. It is the first output this path has ever produced.

The measurement is the point, and it nearly fooled me. The card's eight-hour budget was extrapolated from an older card's "40–85 minutes per task" and had never been measured; replacing that guess was this run's stated first purpose. Task one took **39m43s** and I wrote it up as landing at the bottom of the expected range. Tasks two and three took **8m08s** and **10m58s**. The first task is a four-fold outlier paying one-off costs — model load, cold caches, scaffolding an empty repo — and had I banked the single sample I had, I would have concluded the opposite of the truth. The card's own instruction was to replace the extrapolation only after a full run produces a spread. It was right.

There is a smaller failure I want kept, because it is the same disease as everything else here. The operator told me, correctly, that I was not actively monitoring a live run — that hours can be lost before anyone notices. So I wrote a watchdog. Within the hour it fired STARVED at 0.08 GB free, which is the *expected* condition while a 30B model loads; it recovered to 4.99 unaided. And its stall check keyed off the fleet journal, which writes only `TASK-START` and `TASK-END` and therefore sits frozen for the entire build — a signal that reads identically whether the coder is working or dead, and so is useless in both directions. I built an instrument that could not distinguish the thing it claimed to detect, an hour after spending the day removing exactly that defect from other people's code. Progress is now measured by candidate writes; starvation needs two consecutive polls.

Then it died three times over: a trailing `&` detached it from its parent, a merge rewrote the script bash was mid-execution, and long-lived background shells were being reaped. I reported it armed while it was not. Believing a watchdog is running when it is not is worse than having none, which is the operator's original point arriving by a route I did not expect. It runs under the purpose-built monitor now.

**Proposed lesson:** *When two failures print the same message, assume two causes until each is separately explained. An error string names a symptom at the point it was noticed, never the condition that produced it — and the closer that string is to the top of a stack, the more distinct upstream faults it can represent.*

**Proposed lesson:** *A finding you classify as cosmetic while investigating a serious one deserves a second look before you file it away. The borrowed run id was the fingerprint of the defect I was hunting, and I filed it as a provenance nit in the same hour I was failing to find the cause.*

**Recurrence of lesson 225:** *gate the expensive resource on the cheapest probe of the experiment's validity precondition.* Three of five attempts were killed by a condition observable on disk in under a second before spending the GPU — an orphan holding memory, a live owner holding the sandbox, a pending slot holding a stale plan.
