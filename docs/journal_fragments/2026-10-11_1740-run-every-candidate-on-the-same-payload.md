### 2026-10-11 — Run every candidate on the same payload: the paper comparison and the measured one disagreed in three places

*Plain summary: phase 2 of the containment comparison (#1740) ran a restricted token (two forms), an AppContainer (four variants) and Microsoft's MXC container on the same test program, with controls and lock-off runs. The measurements confirmed the permission predictions exactly and overturned three things the research had suggested: a restricted token can be singled out by a network rule (only the fully restricted form), git-bash cannot run in any of the confined setups, and Microsoft's container cannot reach localhost on this Windows build.*

The LA approved running arms B, C and D before the #775 flip and adding Microsoft's container as arm E, and asked for a visible warning before any test that could touch his own traffic. The arm E research was the first to come back: a researcher read `microsoft/mxc` at source, verified the release checksum and the Microsoft signature, and three skeptics tried to break its recipe. They found what mattered: the launcher's fallback can silently drop to a tier that edits real access lists, I was running elevated so nothing would have stopped it, and the probe it recommends is not read-only because it runs a cleanup first. I built the safety checks around those three facts before the first container launch: the probe must report the base tier for the exact config, every config sets the fallback flag off, only throwaway folders are granted, MXC's recovery folder is redirected, and the access lists of the granted folders, the registry key and the profile list are compared before and after every run.

Three of my own mistakes cost time and are worth keeping. First, restricted tokens would not start at all (exit `0xC0000142` in 0.05 s). I changed the restricting list twice, adding the logon identity as Codex's design does, before a matrix of lists against a trivial command showed that every list failed, which pointed at something common to all of them: the token's default access list. Setting it, as Chromium and Codex both do, fixed it. The second cause, found earlier in the same hour, was that Windows launches a process from a token only if it is derived in one step from the launcher's own token; mine was two steps. Second, my first countdown test ran 6 seconds and the LA saw nothing. I checked the window with a screenshot test and a window-handle listing, found my test harness had mangled the quoting, and reran at 25 seconds; the window was visible, topmost and in the foreground. The screenshot captured his whole desktop, so I deleted it rather than bank it. Third, I wrote in the first draft of the report that no setup differed from the control in start times beyond its variation; the data said otherwise wherever a network rule was being applied by a concurrent process, and I corrected it to draw no timing conclusion.

The results that mattered. The permission predictions made by Windows' own access check before any launch agreed with the launches in every variant that had a prediction (48 of 48 fixture writes, 15 of 15 secret reads per variant; Microsoft's container was not predicted), including the surprising one: a refusal entry naming an AppContainer is ignored (12 of 12 launched containers). The network separation test, scoped to one test program so it could not touch his traffic, blocked only the fully restricted token when a block naming the operator and a restricting identity sat under a permit naming the operator; the write-restricted token behaved as the operator. So the question "can a network rule single out a restricted token" has the answer "the fully restricted form, yes", and OpenAI's statement that it cannot is about firewall rules. git-bash failed in every confined setup (under the AppContainer-class setups because its runtime creates a named object in the global namespace; under the restricted tokens with different access errors); the coder uses git-bash, so every confined setup tested needs a fix for it before it can replace anything (commits 7b2eb665 and a34b2ebe hold the runs). Microsoft's one-shot process container (the only MXC form run) ran strictly and cleanly (no access-list changes, no registry residue) but refused the host-loopback setting on this build, which is the coder's only route to its model.

The recommendation I wrote keeps the dedicated account as the base and proposes testing a write-restricted token on top of it, because that closes the leak class the account design has had to chase folder by folder. I rejected adopting an AppContainer-class container now (the loopback and git-bash blockers), adopting the fully restricted token (it leaves the same broad-group leaks and breaks the tools), and running the separation test unscoped (it would have exposed his own traffic for no extra information). I did not run the dedicated account itself, because only the LA can; the report says its column is a model plus earlier evidence.

No lesson is proposed.
