### 2026-10-14 — A privacy fix put to the operator as a decision was a control that had not been built

*Plain summary: the independent review of the nolabs draft found the study records a public snapshot would publish carried the machine's name, the operator's account name and the paths of his credential stores with their access lists. I presented it as a decision with two options. The Lead Architect's answer was that it was never his question: a script removes the identifiers deterministically and a lock keeps them out, every time, at the publish seam. Built the same afternoon: 92 files rewritten, a gate lock, the host name in the publisher's leak gate, and a doctrine rule.*

The review (section 4 B1) was right about the exposure and I was wrong about whose call it was. Three identifiers sat in the Windows containment study records: the computer name in 10 effective-access files and 11 other tracked files, 11 of which were already on the public mirror; the operator's Windows account name in 82 files under the two evidence directories; and, in five effective-access records, rows of ``kind: secret`` naming six credential-store paths (SSH keys, git credentials, cloud credentials, two agent tools' secret stores) with the access list of each. I wrote it up as DECISION 1 with a recommendation and an alternative. The decision_boundary test in CLAUDE.md says a defect has one correct fix you can name and a decision has trade-offs only he should weigh; this had one correct fix (remove them, deterministically, before publication) and I dressed it as a trade-off because the fix touched 92 files and felt large. Size is not a trade-off.

What was built, and the two design calls inside it. ``scripts/scrub_public_identifiers.py`` follows the SID rewrite of the day before (``scripts/rewrite_sid_domain.py``): tracked files only, byte-level replacement, CRLF and byte-order marks preserved, a log with the LF-normalised sha256 before and after, the identifiers read from the machine and never written to the script or the log. The first design call is scope: the host name is scrubbed from every tracked file, because code can read it at run time and nothing legitimate needs the literal; the operator account name is scrubbed only inside the two evidence directories, because outside them it is a working path this checkout depends on (CLAUDE.md, hooks, runbooks) and is already public in about 634 paths, so rewriting it would break the checkout for no reduction in exposure. The second is the credential rows: redaction rather than exclusion. The access masks and SDDL on those rows are the measurement (what a limited token could reach); the path is the exposure. The path becomes ``<credential-store-N>`` with N the rank in the sorted set of paths, so the mapping is the same on every run and across files, and the row keeps its numbers. 371 occurrences across the records and the Markdown summaries.

Five tracked tools held the host and user names as literals, as detection needles: the Hugging Face publisher's deny list, the community-export scrub and its verifier, the phase-1 dataset builder, and two test files. A tree-wide lock cannot coexist with needles. My first pass made them read the names from the environment at run time, and the adversarial review (Opus 5.5, 13 findings, FAIL) showed what that costs: under any other account, the restricted coder account or SYSTEM, the four controls stopped protecting this operator's name, a regression against the parent. The same review found the host name inside the lock file itself, as my own "honest limit" example; eleven gzip gate logs carrying both names through pytest test IDs that no grep sees inside compressed bytes; the credential table surviving in the study's report and its performance copy, outside the two directories I had scoped; the publisher's leak-gate pattern matching one letter case while the publisher's grep is case-sensitive (12 of 21 files on the parent); a toggle test that called a second scanner and stayed green with the real scan deleted; placeholder numbers reassigned per run; and ten ordinary byte shapes (a JSON ``\n`` escape before the name, percent-encoded paths, UTF-16, glue, a file name) that both controls passed.

The second pass put recognition in one module, ``scripts/identity_lock.py``, by digest: sha256 of the lower-cased name, so a control recognises the name under any account without holding it, and every view of the bytes is read (escapes unescaped, percent-decoded, UTF-16 decoded, gzip members decompressed). The four tools call it beside their environment strings; the scrub rewrites gzip members and UTF-16 files in place; placeholders are ``<host>`` and ``<user>``, the community scrub's convention, and credential stores take their number from an append-only map of path digests. The lock's toggles now plant each shape in a scratch tree and drive the same ``scan`` the tree test drives, with a clean twin beside each. The leak-gate line is a per-letter case class and the publisher's own match now reads 21 of 21. The digests stay reversible at five letters; a key-stretched digest would make a 4,000-file scan minutes-slow, and the account name is already in hundreds of tracked working paths, so the digest locks and does not hide, and the docstring says so.

Mid-pass the Lead Architect asked why the operator name could not at least be kept out of anything new. It can: ``scripts/identity_user_baseline.json`` freezes the tracked files outside the scrub's scope that carried the name when the lock was set. My first ratchet froze the file list with a ceiling on its length; the second review showed four ways round it in an hour (append to a listed file, swap a cleaned file's slot for a new one, leave a cleaned file listed, raise the ceiling with the list), and that the listed files are the ones sessions write to most. The ratchet now records a count per file and compares the list with main's copy: a listed file may carry no more than its count, a cleaned file must be dropped, and on a branch the list can only be a subset of main's with lower or equal counts. The performance records joined the scrub's scope so new gate logs are cleaned rather than refused.

The second review also found the thing I would least have guessed: my hand edit that made the probe payload read the operator's home from the environment would, in arm A, make the coder account probe its own profile and report that as the operator's stores, because the payload runs as the coder. The home is now an argument the launcher passes from its own environment, with no default. And the scrub, run as any other account, would have rewritten that account's name into the operator's placeholder across the evidence with every gate green; it now refuses unless the live account's digest is the pinned one. The credential-store placeholder map went: the store names are standard and the map decoded in milliseconds from the public account name, so a store path is clean when it reads ``C:\Users\__USER__\.ssh`` and nothing pretends otherwise.

A third reader found the next one before the human reviewer did: the automated review that runs on every commit named a parser differential in the recognition module. The lock read every view of a file (percent-decoded, UTF-16, ANSI-stripped, gzip members) while the ratchet, written a day later, tokenised the raw bytes alone, so a new file carrying the name only in one of those shapes would have passed the ratchet the round-2 review had just certified. The count now reads the same views as the lock and returns the largest per-view count. Against the committed baseline that changed nothing (0 files raised, 0 new, 0 lowered), which is the useful kind of nothing: the baseline was measured in the one view where the name actually appears in working paths, and the fix only closes the views it did not read.

Round 3 then found the cost of a fix without a lock. The round-2 change that made the probe payload demand the operator's home as an argument was applied to two launchers; the third, the container arm, kept its old command line, so every run of that arm would have ended at argument parsing and the summary would have filed a harness error under the containment outcomes. No test referenced the payload or its launchers. There is one now, and it fails on the pre-fix file. The same round showed that my byte views never chained: a colour code written as JSON would leave its digits glued to the name in every view, and a JSON-escaped first letter split the name in two, while the publisher's preflight, which decodes JSON before scanning, refused the same files. The views now decode rather than separate, and each is read again stripped and percent-decoded. The stronger lock immediately found one tracked file: a review document that had deliberately written the host name JSON-escaped as an example of what a scanner misses. Both the branch comparison and the rotation were fail-silent in the same way the round-2 toggles had been: a reference that did not resolve switched the comparison off with every test green, and the monthly journal rotation would have carried the name into a new archive volume and failed the gate at month end. The comparison now fails closed with one named exemption, the rotation refuses, and the hot journal's single occurrence reads a placeholder.

Found on the way: the containment-evidence bundle's hash table had been stale since the pull-request files were added to it in 65fee63a earlier the same day; the bundle gate test was failing on main and nobody had run it. Regenerated in the same commit. The second ruling of the afternoon, the service-mediated egress arm, became #1768 with its routing rule fixed first as DEC-20: a fence bypass reachable without administrator rights goes to Anthropic privately before anyone else.

Lesson proposed (search LESSONS.md before numbering): a privacy or security fix that one script can apply deterministically is a defect to fix, however many files it touches; presenting it to the operator as a decision is a dropped responsibility. The test is whether a second option exists that a reasonable owner might prefer; "leave the identifiers in" is not one. Second lesson proposed: a lock that recognises its subject only through the environment it runs in is a lock on that environment, not on the subject; recognise by a fingerprint the subject cannot change and that the lock does not have to hold in the clear.
