### 2026-10-15 — A leak gate certifies absence, not integrity

*Plain summary: the containment evidence now has its own small public repository, windows-containment-evidence, which every file enters only through a sanitiser and a leak gate. On its first pass the sanitiser damaged code in four ways while the gate stayed green. All four were found by reading a table of every substitution the sanitiser made.*

The Lead Architect ruled for option C: a new, neutral, dedicated repository for the Windows containment measurements, instead of keeping them inside blarai-public with its whole-tree exposure and its licence mismatch. I built it from blarai-public at `b04ee32d`: the 10-05 WFP SID-block bundle, the 10-13 NEP-0005 half-set and the 10-14 nono 9P control. They come to 140 files (136 copied files and four replacement-count markers), copied through a new standalone `tools/sanitize.py` and gated by `tools/leak_gate.py` at pre-commit and commit-msg.

The design call that mattered was what the public gate may contain. BlarAI's identity lock pins sha256 digests of the host and account names. In a public repository that is not hiding: a five-letter account name falls to exhaustive search in seconds. So the public gate reads the live `COMPUTERNAME`/`USERNAME` at run time. The private vocabulary (the #1777 phrases, role names, internal repository names) lives in an untracked `.leakgate.local.json`, and the gate refuses to run without it. The rejected path was copying the ratchet's digests across "as standalone copies". That literal reading of the brief would have published the name.

The failure path is the lesson. The first sanitiser run left 98 gate hits, and I worked them down to 4. Then I tabulated every distinct substitution the sanitiser had made, file by file and line by line, and found four kinds of damage the gate could never see. A cleanup meant for `(#1763)` stripped `()` from code everywhere, so `uuid4().hex` became `uuid4.hex` and PowerShell's `@()` became `@`. The bare upstream reference `#2089`, which is the nono issue itself and so public subject matter, was deleted like an internal one. A Windows build-lab stamp, `240331-1435`, matched the tracker-number-in-a-name rule. And the 9P case probes' upper-case fixture spellings (`P1755-RUN1`) slipped through the lower-case rule.

Each now has a self-test case that fails on the old rule, and auto-removal is narrowed to the internal range (#1NNN and c.NNNN). Any other bare number is refused by the gate for a person to resolve, because only a person can tell an upstream issue from an internal one. The controls that would have caught the damage are integrity checks, not leak checks. The sanitised 9P probe passes its own self-test exactly as the original does (990 checks, 0 failed, 1 skipped). The 42 PowerShell scripts parse the same before and after. The 9P verdicts re-count to 222 / 51 / 63 / 0 / 24 after sanitising and again after the prose edits.

Then the independent pre-push review (Opus, read-only, told nothing of my reasoning) failed the tree four times before it passed: 16 findings in round 1, then 4, 2 and 1, and round 5 PASS at `c86479f`. Round 1 is the part to remember. With the gate reporting 0 hits, the tree still held the operator's full name in a licence notice and a patch header, comment pointers to the tracker written in words ("comment" and a number) rather than in the `c.NNNN` form the sanitiser removes, two file names carrying a three-digit ticket number, and sentences reporting internal approvals. Feeding 20 crafted inputs to my own gate, the reviewer got 14 through. Every later round was the gate's docstring claiming a spelling that its pattern missed: a repository-shaped private prefix, a number glued to letters, a serial written as a JSON key, then as an escaped JSON key. Two dispositions were argued rejections and a third a partial one, and the reviewer accepted all three. The constants that embed an internal number (test ports, WFP key prefixes, the stale SID's RID) are measured values, so they stay and are disclosed in PROVENANCE.md. The project's name stays because PROVENANCE has to trace every copy to its blarai-public commit. The gate is a regex list, and the review is what found where the list was short. That is why "zero findings or no push" is the rule and "gate green" is not.

Three smaller calls are recorded in the new repository's PROVENANCE.md and on #1787. The NEP folder is dated by its run (10-13), not by the brief's example (10-11). Git says the first-publish commits are `27bb82c3` and `3b4d1156`, not the two the brief guessed. And commits use the GitHub no-reply address, because the global git email would have put a personal address into public metadata.

Proposed lesson: a gate that proves something is absent says nothing about whether what remains is intact. Any tool that rewrites text needs a check on what it must leave alone, and the cheapest one is a table of every distinct substitution, read before anything is committed.
