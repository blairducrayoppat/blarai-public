### 2026-08-06 — The lock enumerated spellings, and the fix had already changed the spelling

*Plain summary: a gate built to stop the app destroying typed text could not see the most likely way of reintroducing the bug, because it listed the exact phrasings to forbid and the fix itself had switched to a different phrasing. Two independent checks caught it; the second one only because the first fix went red on correct code.*

The defect underneath was the worst kind we have had: on 2026-07-27 the New Project dialog silently destroyed about 2,200 characters the operator had typed, and it was recovered only by taking a 674 MB memory dump of the still-running process and scanning the managed heap for UTF-16 runs. That worked because the app had not been restarted. It is not a repeatable recovery.

The fix is right and I want to record why, because the obvious alternative is worse. The handler validated after `ShowAsync()` returned, at which point the dialog and both text boxes are gone. The tempting repair is to stash the strings before showing, check them after, and re-open a prefilled dialog on failure — and that still has a window where the only copy of the operator's text lives in a local variable. Cancelling the `Closing` event instead means nothing is ever torn down on a failed check. The text is not restored; it is never destroyed. That is a structural difference, not a stylistic one.

The branch also shipped the structural control that LESSONS Rule 3 requires, and it had genuinely earned it: #1117, #1116 and #1126 are three instances of "we discarded what a human just typed" inside two days. The test parses `MainWindow.xaml.cs` as text and asserts the destructive shape is absent, and its docstring is admirably honest that this is a weaker claim than "the dialog behaves correctly" — a behavioural test needs a real display and the `@winui` ceremony tier, which does not run at every commit. A structural gate that runs every time beats a perfect test nobody schedules.

Then the independent review found the hole, and it is the interesting part. The lock matched `string.IsNullOrEmpty(goal|name)`. The fix had changed the file's idiom to `IsNullOrWhiteSpace`. So the single most likely way to reintroduce the bug — copying the two lines directly above in the new `Closing` handler — was the one form the lock could not see. The reviewer put the destructive check back in the file's current idiom and all three tests stayed green. The docstring promised exactly that coverage: "a future edit could keep the Closing handler AND re-add a post-ShowAsync emptiness check". It could, and nothing would have stopped it.

The reflex is to add `IsNullOrWhiteSpace` to the regex. That is the wrong repair, and naming why is the lesson: the list is a blocklist, and blocklists cannot be completed. `goal == ""`, `goal.Length == 0`, a helper called `IsBad(goal)` — each is a new hole. Deny-by-default is doctrine here for exactly this reason, and a test is as much a control as anything in the runtime. So the guarantee moved: between `ShowAsync` and the submit call there is now **no early return at all**, whatever it tests. The narrow regex survives only for the specific error message it can produce. I proved it with four mutations, each reintroducing the original defect after `ShowAsync`, and the fourth is the one that matters — `IsBad(goal)`, an arbitrary helper no list could ever hold. All four caught.

Writing that lock is what exposed the second defect, and I would not have found it by reading. The new structural check went red on correct source. The instinct at that point is to loosen the check; it was wrong, and the code was fine. The test anchored on a bare `ShowAsync()`, and the first match in the file is not the call — it is the explanatory comment above the `Closing` handler, which mentions `ShowAsync()` while explaining the bug. So the scanned region began thirty lines early and swept in the `Closing` handler, the very code that must never be flagged. The original passed only by luck: its regex wanted a bare `goal`, and the handler happens to use `goalBox.Text`. A control anchored on a comment is not anchored.

Two things about process. The branch-tip gate returned 9285 passed where main's baseline is 10313 — not a regression, just a tip 280 commits behind that lacks a thousand tests added since. A branch gate on an old tip is close to meaningless as evidence about the merged result, and it is worth saying plainly rather than letting a green-looking number stand in for one. And the review's most valuable output was not the finding itself but the mutation it ran to prove it: it did not argue that the lock was weak, it reintroduced the bug and showed the suite stayed green. I have started treating "did you make it fail?" as the question that separates a review from an opinion.

The residual is worse than the thing fixed. Two hundred lines below, `PromptAndRenameSessionAsync` has the identical shape — validate after `ShowAsync`, return, text gone — and it has no banner at all, so the operator gets silence. That is a fourth instance of a class whose third instance already shipped a control, and the control cannot see it, because the gate hardcodes one method as its anchor while the ticket asked for coverage of every operator-facing rejection path. Ticketed with the fix and the widening: enumerate the `ShowAsync` call sites and assert the property on all of them, so instance five cannot hide in a method nobody thought to name.

**Next:** the sweep, and the question of how many other gates in this repo are anchored on a single hardcoded symbol while their tickets asked for a class.
