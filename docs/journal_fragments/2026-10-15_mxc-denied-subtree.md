### 2026-10-15 — A probe that can only say HOLD has not been tested: five review rounds each found a lock that certified the wrong thing, and the live batch then confirmed a deny on one tier only

*Plain summary: asked whether Microsoft's MXC sandbox really keeps a process out of a "denied" sub-folder inside a folder it may write to, I wrote one probe, had it reviewed five times before it was allowed to run, hit one dead end on the first live attempt (a security setting that stopped the sandbox's Python from loading), and ran it. On this machine the sandbox chose its first tier and every one of 15 write attempts into the denied sub-folder was refused in three runs; the sub-folder was unchanged. That is a result about the first tier on this Windows build with Bitdefender present, and nothing about the tiers where the vendor describes a different mechanism.*

The question was one sentence: an MXC policy with a denied subtree inside a read-write tree, with write attempts into the denied subtree. The part that makes it more than a yes or no is the tier. MXC documents two ways of enforcing a denied path on Windows, one native to the operating system and one by deny entries added to the folder's permissions, and an earlier observation had shown that a kernel access check ignores a deny entry written for an AppContainer package identity. So the first thing the probe records, before any write, is which tier this build selects, and the result is read against that. It selected the first tier (`base-container`, native deny advertised, no permission rewriting needed) for both launchers it probed, and every dry run and launch log agreed. The second thing is what the harness refuses to believe: a refusal in the container proves nothing unless the same five writes land from an unconfined process on the same account (they did, 5 of 5), and the container's own report never decides the verdict; the host compares the subtree before and after (names, sizes, hashes, attributes, file write times, alternate streams) and any difference is a FAIL.

The result: 3 of 3 runs, each of the five writes (create a file, open the marker to append, rename, delete, create a directory) refused with Win32 error 5, 15 of 15, the host comparison found no change, writes inside the tree but outside the subtree landed, a read and a listing of the subtree were refused with the same code, and the permission records of the subtree before, during and after each run were identical with five inherited allow entries and no deny entry. The launcher's own log shows it built a PSEC 1.0 spec of 312 bytes in all four launches; that version is a per-launch reading of the policy launched, never a property of the host. The numbers and conditions are in `PERFORMANCE_LOG.md` and `docs/performance/mxc_denied_subtree_2026-10-15.json`. They are three runs on one machine in about eight seconds, a repeat and not a distribution, and the deny entry's absence says how this tier did not do it, not how it did.

The first live attempt is a named non-result and the dead end. With the policy's UI lockdown on, the container's Python failed at `import ctypes` (`DLL load failed while importing _ctypes`), the payload never produced a report and no write was attempted. I had written the policy as "no UI" because the case said filesystem only, and I had not run the container's Python under that policy before the evening. The fix was a smoke launch that imports the payload's modules under the exact measured policy shape before any measured launch, and a policy with the UI lockdown off (`ui.disable` false, clipboard none, injection false). I cannot say the UI setting alone is the cause: the harness changed between the two batches too, and the smoke launch passed under the new setting. The record says "the recorded difference", not "the cause". Turning the lockdown off is a departure from the case's policy line, so it is stated in every record as a bound, and a UI-lockdown-on run is in the not-measured list.

Five independent review rounds came before the live run, and the pattern was the same in each: the self-test passed, and the reviewer found a lock that certified something other than what its name said. Round one (two HIGH) found that HOLD was looser than the failure definition (an extra file in the subtree, a changed rename source or a move-in gave HOLD), and that create and append recorded no Win32 error at all because Python's `open()` reports a generic errno; the lock "a refusal records a Win32 error" only exercised a call that does set one. Round two (two HIGH) found that the step meant to drop dangerous privileges from the launching token was a silent no-op (a structure laid out wrongly, so the call reported success and removed nothing), which matters because an elevated Git Bash enables backup and restore privileges that let a rename, delete or mkdir ignore the permission check; it also found that a landing with no container report could be labelled LAUNCH-FAILED instead of FAIL. Round three (PASS) found that a host-side read error could still yield a false FAIL, and a lock asserting "an exclusive handle is not a change" that never called the code deciding the verdict; round four did not renew its approval. Round four (one HIGH) found that the round-three fix had over-corrected: a landed entry the host could not read lost its existence evidence, so a real bypass would have read INSTRUMENT-BLIND or LAUNCH-FAILED with a stop line saying the subtree was unchanged; a fix that closes a false FAIL must not open a false HOLD. Round five passed after one addendum: the reviewer's first self-test run died on a timeout in its third end-to-end case with 148 passes and no failures printed, and the runner reported exit 0 for a child that had died with a traceback, so approval waited for a complete self-test on a quiet machine (167 passed, 0 failed) and the reviewer read the closing tally and not the runner's exit code. Round five left three LOW items open (an all-unattributed FAIL reads like a real bypass in the verdict line; a signature check with a 300 s timeout can crash the harness with no record under load; the non-elevated runner's exit code), none of which can produce a wrong HOLD.

Two trade-offs stayed. The harness insists on error 5 for HOLD, stricter than the case required, because the native deny's error code is undocumented, and the price is that a different but still-refusing code would read as a blind run rather than a result. And I kept FAIL as any difference at all in the subtree, including entries no attempt explains, rather than downgrading unattributed changes, because downgrading hides evidence; the verdict line is where that needs to be marked, which is the open LOW item. The privileges the harness could not remove (SeDebug, SeChangeNotify, SeImpersonate, SeCreateGlobal) stayed enabled before and after and are recorded; whether the container's token inherits them is a hypothesis from reading source, not something this batch measured.
