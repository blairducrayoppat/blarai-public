### 2026-10-08 — Running the tests in parallel found the order the serial run was hiding

*Plain summary: I split the 24-minute test gate into concurrent groups to halve it, and the first runs failed on a test that only passes if another test happened to run in between; fixing that leak is a better result than the speed.*

The operator's complaint was plain: a 24-minute gate makes the development cycle crawl. After the installer fix the remaining cost was simply that 13,000 tests run one after another and many of them start processes, which this laptop does slowly. Running the same files as concurrent groups was the obvious answer and the first trial was good news: 13,253 tests, 730 seconds. The next trials were the lesson. Six groups failed one canary test; three groups, run three times in a row, failed the same canary test every time. The canary asserts that no URL adjudicator is registered in a bare process, and something in the same group had registered one and not cleared it.

My first guess was that alphabetical file order inside a group had put a polluter in front of it, which was true as far as it went (sequential order is the collection order and I had broken it), and restoring the order was right but not enough. The second failure was the one that mattered: the sequential gate passes, as far as I can tell, because a file in another group runs between the leaking launcher test and the canary and clears the door; I showed that main's fixture fails the pair and the fixed one passes, not which file does the clearing. Two tracing runs came back "no polluter found" because my file list had carriage returns in it and pytest collected nothing; a run that proves nothing looks exactly like a clean run, which is the same lesson as the timing instrument's. The corrected tracer, which checks the registry after each test's teardown rather than before it, named the test. The fixture now puts back what it found, and main's version of the file fails the pair while the fixed one passes.

An independent review then found what I would have shipped: a module pytest skips at collection time vanishes from the parallel count and prints "0 skipped" where the sequential gate prints one; two integration files that bind the real service ports land in different groups; and eight of my runner's checks could be switched off with every test still green. All fixed; sixteen mutations of the runner now each fail a test. Result: six groups, 13,288 tests, 700 to 709 seconds, three runs in a row, against 24 minutes.

Trade-off: the saving is about 2x, not 6x. Six groups each ran about 2.5 times slower than their share, so something shared (process creation, file scanning) is the limit; I did not isolate it. And the sequential order stays the definition of the bar and the only timing figure. A shared-resource audit of the remaining tests is #1709.

**Next:** the audit, then three more clean parallel runs; the fast form is now the default way to run the gate.
