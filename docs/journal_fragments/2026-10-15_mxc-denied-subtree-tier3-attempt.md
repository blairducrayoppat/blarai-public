### 2026-10-15 — A tier you ask for through a setting is a different principal, and its first failure was in the toolchain's permissions, not the policy: the Tier-3 attempt stopped at the smoke launch

*Plain summary: after the first tier held, I tried to reach the vendor's third tier (a deny entry added to the folder's permissions) by asking for the stricter sandbox identity. The tier was selected, but the sandbox's Python would not start (a missing-library error), so the smoke launch stopped the batch before any write into the denied sub-folder was attempted. The toolchain grants read to one built-in group and the stricter identity belongs to a different one. Nothing about Tier 3 denial was measured.*

The first batch answered the question for `base-container` only. The vendor describes the denied path on the third tier (`appcontainer-dacl`) as a deny entry written to the folder's permissions, and an earlier observation had shown that a kernel access check ignores a deny entry written for an AppContainer package identity, so that tier is where the open question is. This machine does not select that tier on its own, so the `fx-c` variant asks for it: the same policy with `leastPrivilege` true, which the vendor ties to the AppContainer path. `fx-c` changes the tier, `leastPrivilege` and the missing denial capture at once, so neither a hold nor a failure could be pinned to one of them; the records say so. The harness changed for it in two reviewed steps. Round 6 failed the first version (`261737de`) because a launch that failed and left a deny entry or a changed toolchain permission read as LAUNCH-FAILED with no state-left entry, and the smoke launch, itself a Tier-3 launch, had no cleanup check; round 7 passed the fix (`d1de3242`, 213 passed, 0 failed) after reproducing the closing verdict on synthetic records of every shape round 6 named. The disposition for both is in `docs/reviews/mxc-denied-subtree-review-disposition-2026-10-15.md`.

The attempt ran on the same evening, third run folder under `blarai-research-data/mxc-denied-subtree/`. The host prep for the system drive was in effect at the start (both required allow entries on the drive root, read by the new detector), the dry run selected `appcontainer-dacl`, and the smoke launch started the container's Python under the measured policy. It exited with `0xC0000135` (-1073741515, STATUS_DLL_NOT_FOUND) after 50 193 ms with no report written. The five-attempt host control ran afterwards and landed 5 of 5, so the account and the tree were not what blocked it. No attempt was made against the denied sub-folder, so there is no hold and no failure to report. The harness did what the round-6 review demanded: the verdict is STOPPED-STATE-CHANGE, because the launcher left one AppContainer profile mapping key in the user's registry hive (`...AppContainer\Mappings\S-1-15-2-952931689-...-3985063650`, a key that was not present before the launch). The toolchain tree, saved at the start and end with `icacls /save`, held 22 744 objects both times and the two saves are byte-identical, and the interpreter's and the toolchain root's permissions were unchanged. Prep and undo of the system drive were verified by the operator procedure in the round-7 file.

The cause is a reading, not a measurement. The toolchain grants read and execute (mask `0x1200a9`) to `ALL APPLICATION PACKAGES` and to nothing else in the AppContainer group, and the vendor's `leastPrivilege` path runs under `ALL RESTRICTED APPLICATION PACKAGES` (S-1-15-2-2), which that entry does not cover. That fits a library that cannot be loaded, and it fits the first batch, where the smoke launch under a different tier passed. It has not been tested by varying the grant, and the launcher's own log gives only the exit code. The record therefore says "consistent with", and a second hypothesis (the launcher's profile for this container id failing to map the toolchain path) is not excluded.

Trade-offs. I did not widen the toolchain's permissions on the strength of that reading and run again in the same sitting: it is a host permission change on a directory outside the repository, to a group the vendor treats as a stricter identity, and it should be a deliberate, recorded prep with its own undo, not a side effect of a probe. I also did not drop `leastPrivilege` to get a launch: that changes the variable the variant exists to hold, and a Tier-3 run on a different principal would not answer the question as asked.

**Next:** (1) remove the leftover profile mapping key after confirming it is the one this launch created (the `STOPPED-STATE-CHANGE` entry names it); (2) a recorded host prep that grants the same read and execute mask to `S-1-15-2-2` on the toolchain only, with a before-and-after `icacls /save` and an undo, then re-run `fx-c` with a fresh approval; (3) if the smoke launch still fails, read the launcher's own loader diagnostics before any further variable is changed. Neither (2) nor a policy change has been run; (2) alters a permission on a directory outside the repository and is the operator's call.
