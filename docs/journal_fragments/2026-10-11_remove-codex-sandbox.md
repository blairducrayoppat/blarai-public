### 2026-10-11 — A privileged write through the operating system's own call re-derives what you meant to leave alone; edit the object you opened, and prove the rest did not move

*Plain summary: removing the Codex sandbox leftovers (#1743) took six independent reviews. The access-entry part first rewrote whole folder lists through Windows and lost or added other principals' access; it now cuts the Codex entries out of each object's own list through one handle and checks every object afterwards. The account, rule and value part was split off and is ready to run on its own.*

The task looked small: delete two Codex accounts, two firewall rules, two hidden-user values, one group, and the four access entries naming Codex's capability SIDs. I wrote a script the LA double-clicks, with a dry run, a digest he approves, a backup, a verify and a throwaway-object self-test. The first review found a fail-open (an export that produced no file skipped its check) and an overclaiming PASS. I fixed those. The second found the thing that mattered: writing the list of a root folder makes Windows recompute every inherited entry below it. On the real Temp folder that would have dropped an app-container grant from 195,385 objects, and the result still read PASS. I answered with a "keep" step that made those entries explicit first. The third review showed the keep step was the wrong shape: on C:\ovms, removing the Codex entry made the folder re-inherit from C:\, which would have granted Authenticated Users Modify on 3,290 files, and my read-back called that gain a yellow note. A fix I wrote to preserve things was itself widening access.

What I got wrong was the premise. I kept asking how to make Windows' rewrite harmless. The write I wanted was much smaller than the call I was using: remove one entry from one object's list and change nothing else. SetSecurityInfo and SetNamedSecurityInfo both re-derive and propagate; I confirmed that on a fixture, where even a handle-based call erased a stale entry on the root and rewrote the children. The kernel call underneath, NtSetSecurityObject, writes exactly the list it is given, provided the request flag accompanies the auto-inherited flag. So Stage 2 now opens each object once, checks on that handle that it is the path it should be (final path, link count, every hard-link name inside the allowed folders), cuts the Codex entries out of that list, writes it back and reads it back. Every object is compared with its before-change list afterwards, and a loss or a gain stops the run before any irreversible step. A read-only simulation over the real trees (410k BlarAI objects in 5 to 8 minutes, 212k in Temp, 3,291 in C:\ovms) found 36 model files hard-linked into another worktree; the LA allowed that one folder.

The reviews also showed me a failure in my own tests. A reviewer planted forty single-line disablements of Stage 1's safety checks and thirty-seven stayed green, because the standing-gate lock matched text. I turned the checks into small functions and drove each on states built in memory, and every planted removal is now caught by either a structural pattern or a behavioural case (43 of the reviewer's mutants, all caught). The self-test itself went red permanently once Stage 1 had run, because one check drove the real account; it now uses a fixture spec in real-mode shape. Two self-test runs overlapped and deleted each other's fixtures until every object carried a random per-run token. And a part-way stop could have left the Offline account enabled with its loopback block gone, so both accounts are now disabled first.

Stage 1 (accounts, rules, values, group) is its own mode with its own digest and no access-list code on its path, and Stage 2 stays refused for the real machine until the LA says so.

**Recurrence of lesson 330:** a read that fails (an unreadable group, a service list, a stale export) must not look like "already gone"; here the type is the third answer, not a convention.

**Next:** the LA runs Stage 1 from the launcher and the lead verifies the end state with the read-only verify; a fresh review of Stage 2 before its lock is removed; then the LA's go on the access-entry stage.
