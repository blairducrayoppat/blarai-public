### 2026-10-15 — A refusal measured on one Windows build is a statement about that build, and a probe is only as honest as the shapes it can tell apart

*Plain summary: asked whether Microsoft's MXC sandbox accepts "use only this local proxy" and then blocks everything else, I built a probe, had it reviewed three times, and ran it. On today's Windows update both the released launcher and a newer build accepted the setting and blocked every direct connection in all twelve runs, with Bitdefender uninstalled and again with it reinstalled. On 2026-10-11 the same released launcher had refused a similar setting, so the earlier "refused" is now a statement about the older Windows build, not about MXC.*

The question came as a single sentence: MXC v1.0.0 with `runtimeConfig.networkProxy` pointing at a loopback proxy, refused or accepted, and if accepted, is non-proxy egress blocked. I wrote one script that drives two launchers (the Microsoft-signed v1.0.0 and a build from microsoft/mxc commit 525d0f25), a real forwarding proxy, a second local listener, and a payload that runs inside the container: three requests through the proxy as the control, then direct connects to that listener, to the default gateway and to 1.1.1.1:443. A refusal counts only as Windows error 10013; the same connects are repeated from an unconfined process before and after every launch so a refusal can be attributed to the container and not to the network. The first thing the probe recorded, before any container ran, was the host change: `wxc-exec --probe` on the released v1.0.0 launcher now reports host-loopback ingress supported (Windows 26200.9711), and `--dry-run` accepted the policy that the same launcher had rejected on 26200.9457 four days earlier. I had expected that rejection to carry over. It did not. The launchers' own logs carry the one mechanism-level observation: the proxy policy launched under PSEC 1.1 in all 12 launches (432 bytes), while the nine 2026-10-11 launches on 26200.9457 (the older main build; the v1.0.0 launcher was rejected then and did not launch; three of them the no-proxy baseline) logged PSEC 1.0 (232 or 344 bytes), so the logged version follows the policy launched, not only the host, and the vendor networking document says `hostLoopback: allow` is rejected when the PSEC 1.1 ingress contract is unavailable. `--probe` itself prints no PSEC version. So arm B, which was written to test main's identity-less proxy support on PSEC 1.0-only hosts, ran here on a host that supports PSEC 1.1, launched the proxy policy under it, and did not take that workaround path; its HOLD says nothing about it. What caused the change in acceptance is not isolated: the Windows build, the harness and the proxy port all changed between the two records (the security software is ruled out, below). Per the operator, Bitdefender was uninstalled on 2026-10-14 and Windows Defender was active during the first run; the raw record shows a stale McAfee firewall entry in Security Center.

The first run (elevated, 2026-10-15 16:07, commit `25210ef3`, no third-party suite): arm A and arm B each accepted the policy 3 of 3, the proxy control passed 9 of 9 requests per arm, and the direct connect to the second loopback listener, to the gateway and to 1.1.1.1:443 was refused with 10013 in every run; the unconfined controls connected every time. The numbers and conditions are in `PERFORMANCE_LOG.md` and `docs/performance/mxc_proxy_egress_2026-10-15.json`. They are three runs on one machine in half a minute, a repeat and not a distribution.

The operator then reinstalled Bitdefender and I asked for the same batch again as a second condition, since the earlier arms of this study all ran with it present and this one had not. The first attempt at that second condition is a named non-result: it passed the hash check and the unfenced control and then died on binding a loopback port, because a self-test of mine, running in the evidence repository's copy of the probe, held the probe's two ports. That is the plain cost of a harness whose instruments bind fixed ports meeting a builder who runs its self-test on the same machine during someone else's live run; the probe now checks its ports first and refuses by naming the holder, and I do not run its self-test while a live run may be pending. The unfenced control of that aborted attempt was also the connection the reinstalled Bitdefender firewall auto-allowed for the host Python, which makes the auto-allow part of the condition. The aborted attempt's WinError 10048 is from the console output the operator pasted; no raw file records it. The retry the same hour (16:43, same commit, from a clean detached worktree, hash check passed) gave the same result in every counted figure: 3 of 3 accepted, 9 of 9 through the proxy, every direct connect refused with 10013, controls connected, HOLD for both arms; only the launch wall times were longer (0.566 to 1.864 s against 0.387 to 0.698 s), recorded and not explained. So the Bitdefender state is not what moved the acceptance between the two records; the Windows build, the harness and the proxy port all changed too, and nothing here isolates which one did.

The probe went through three independent review rounds before it was allowed to run, and each caught something the self-test had certified. Round one found that the first version bound a listener on the host's own LAN address: it raised a Windows Firewall prompt on the operator's screen during my own self-test, and the unfenced control could not distinguish "MXC blocked it" from "the firewall blocked the listener" because traffic from the host to its own address is loopback-routed. The LAN listener was removed, the destination became a real LAN peer (the default gateway) judged from the container's error code, and the firewall rules for both interpreters, the loopback exemptions and the WinHTTP proxy joined the before-and-after state snapshot. The same round found that a timeout had been counted as a refusal, so a dead uplink would have manufactured a HOLD; now only the enforcement code counts and everything else blinds the run. It also found that an unexplained connection to the listener during the launch was ignored, and that a self-test mandated ignoring it. Round two found the sharper one: a launch that exited non-zero with no report was labelled "refused at launch", yet its own logs showed three tagged requests, so the container had run and died; the self-test's refusal fixture was itself a record in which the container ran, which is how the lock certified the wrong verdict. The fix needs no sign the workload ran, and the lock now holds the true refusal and the launched-then-failed record side by side on the same text. Round three passed, with a residual I fixed afterwards (the label could still follow the workload's own stderr, so it now also requires that MXC's log shows no process created).

Two trade-offs stayed. I kept a FAIL (any direct reach) as a hard stop even though the vendor's documentation says an identity-less proxy "opens both host-loopback directions" and that private-network traffic stays available when `ingress.default` is allow, because reading a reach against that text is the operator's call before any routing, and a harness that decided it would be deciding a question it does not own. I rejected counting 10061 or timeouts as refusals for stricter attribution, at the price of a possible evening of blind results.

**Next:** both batches are sanitised into the evidence repository with every figure re-counted from the sanitised files against the raw counts (47 figures per batch, no differences); independent review of the bundle and the harness's later fixes before anything is shared.
