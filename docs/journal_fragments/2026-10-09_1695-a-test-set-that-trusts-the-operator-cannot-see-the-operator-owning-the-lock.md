### 2026-10-09 — A test that counts the operator as trusted cannot see the operator owning the lock

*Plain summary: the script that removed the old nginx web gateway passed 203 tests and 65 of 65 mutations, then stopped twice on its first real run, because the tests treated the person running it as an approved owner and the real check did not.*

The NginxGateway service ran as the machine's highest account from a folder every signed-in account could write, so the contained coder could have become that account. #1695 removed it: one service, twelve scheduled tasks, three firewall rules and the folder, which is kept in an admin-only quarantine until the coder flip is done. A second check, number 25, now fails the containment proof if any boot-time program or script is writable by the coder. Three independent review rounds hardened the removal script (a link planted at the root of the delete walk, a lock that was checked once and not again before deleting, parser shapes such as `rundll32 x.dll,Entry` that hid a writable DLL from the sweep). My own runs of every suite and mutation set matched the builder's numbers each time.

The first real run, with everything green, stopped at step one. `takeown` without `/A` gives ownership to the current user, not to the Administrators group, and the script's own read-back refused a folder owned by me. The second run got further, removed the service, tasks and rules, and stopped at the move: the quarantine folder the script had just created was owned by me for the same reason. The test suite could not see either, in the same way twice. Its set of trusted owners included the current user as a stand-in for the operator, and its fake `takeown` called the real one with the same missing flag. A suite can only fail on a condition that is represented in it, and a convenience in the fixture had quietly removed the one condition that production enforced. The mutants were all killed because they mutated the code the tests drove, not the assumption the fixture made.

The repair was a shared `takeown /A` function used by both production and the tests, creation of the quarantine folder and its marker file owned by Administrators, tests that run the real `takeown.exe` and the real create with the production trusted set (SYSTEM and Administrators only), and three mutants that revert each (68 of 68 killed). The harness then declined the last repair step, a `takeown` on the quarantine folder, and I handed it to the Lead Architect as one command rather than work around the refusal; the run finished there, read-back confirmed. After the removal the real-machine sweep reports 0 offenders, where it reported 6, all nginx.

I also made a mistake the same afternoon: re-checking check 25, I ran the containment script in its real mode, which starts the coder's scheduled task once, instead of the read-only sweep I meant. Nothing was left behind and I disclosed it on #775, but the script had a mode switch whose default does the heavier thing, and I read its name instead of its documentation. The run also exposed a crash when the probe returns no results (#1715).

Trade-off: running the removal myself, elevated, cost two partial runs and a hand-off, but the alternative was a script that had never touched a real access list. A dry run cannot find an ownership bug; only a real run on a machine that matters can, which is why the script was built to stop on its own read-back and to resume where it stopped.
