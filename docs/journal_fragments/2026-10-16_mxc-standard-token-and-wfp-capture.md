### 2026-10-16 — A repeat under a new token confirms a verdict and not a cause, and a capture that finds the owner of a rule has still not found which rule refused

*Plain summary: asked whether Microsoft's MXC sandbox still blocks every direct connection when started from an ordinary non-administrator account, and whether the Windows firewall engine holds rules for the contained process, I ran the same proxy-only policy twice more. From a standard token both launchers blocked all direct connections in six of six runs. With the firewall engine's rule list captured during each launch, a Windows component named Tessera adds a per-launch block rule for the container, so the maintainer's reading that only a missing capability blocks it is incomplete; which of the two mechanisms refused any given connection was not measured.*

The first question (Q3) was a single sentence from the upstream thread: does the case-1 policy behave the same from a standard token. I added a standard-token mode to the probe (it refuses to run unless the token is Medium integrity and not elevated, and records the token in every file), had it reviewed twice before it ran (round 1 failed on a launch failure that could read as a policy refusal and on an empty direct-attempt report that could read as HOLD; round 2 passed), and ran it at 05:48 with Bitdefender present: both launchers accepted the policy 3 of 3, the proxy control passed 18 of 18, every direct connect to the second listener, the gateway and 1.1.1.1:443 was refused with 10013 in 18 of 18 attempts, and the uncontained controls connected 24 of 24 times. That answers the question as asked. It does not say the token mattered: the token, all four harness files and the running Bitdefender process set (1, 14 and now 16 processes) changed together against the elevated batches, so "the same verdicts and error codes" is all the data supports. The wrapper that starts the batch from a non-elevated token returned about 18 seconds before the batch ended, so the console capture is incomplete and the record cites the raw files; the wrapper now waits for a completion marker (fixed, tested, outside git) and the README command, which had lost its backslashes to escape sequences, is corrected in `d89bbed9`. The post-run review also found that the standard token cannot read the firewall engine's filter list, so Q3 records that state as not measured and a summary line that read as "no change" for it is a deferred probe fix. A per-program Bitdefender rule on the container interpreter's path is not excluded by this batch alone; the uninstalled-Bitdefender batch of 2026-10-15 gave the same pattern, which is the only argument against it.

Variant 4 was added to the session's work at 07:25 EDT, with the operator present, and ran at 07:58: the maintainer's inference was that MXC creates no firewall rules (its log says `firewall_rules_created` 0) and the container is blocked only because the internet capability is omitted. The test was to capture the Windows Filtering Platform filters before, during and after each launch, elevated, with the capture synchronised to the container being alive. It was six launches, egress HOLD again, and the delta was the same in all six: 1008 filters before, 1016 during, 1008 after, eight new filters that exist only during the launch. Six are keyed to that run's own AppContainer SID, and four of those are a Windows Tessera filter pair per address family, a PERMIT for TCP to the proxy port 18110 and a BLOCK with no other condition. The reviewer's independent parse, an MXC source read and a byte search placed the owner: the string is in a System32 library and in none of MXC's binaries, and MXC's own document calls Tessera an internal Windows component and names the two provider GUIDs. So `firewall_rules_created` 0 is true and the capability-only reading is not: direct egress is also under a SID-keyed block. The probe's own summary counted eight filters as referencing the SID; two of them only mention it in a remote-user descriptor and are keyed to another package, which the record now says as six and two.

What the capture does not give is the refusing layer. The second-listener refusal fits the Tessera block by the port split (18110 allowed, 18111 refused, nothing else port-specific), but the gateway and 1.1.1.1 refusals would come from either mechanism, and no net-event capture or MXC denial reason code was recorded. The positive control, a firewall rule for a synthetic package SID, compiled to no filter at all, so the control as designed cannot pass on this machine; I recorded it as uninformative rather than reading the failure either way, because the runs themselves (eight exact-SID filters, clean before and after) are what show the capture can see. A different control, or any change to the probe, needs a new pre-run review under the approval hash before another live run, so none was made. The constant second package SID behind the two MXC-Loopback filters is not unknown after all: the post-run review and the first draft of this record both left it unidentified, and the pre-merge records review derived it offline as the AppContainer SID of the name `MXC-Loopback`, which is MXC's own named loopback peer (`base_container_helpers.rs:24` at `525d0f25`). The four app-isolation filters are therefore one reciprocal loopback peering between the run container and MXC's peer, installed by the Windows Firewall service, and the four Tessera filters are Windows'. I had written that none of the eight filters belonged to MXC; that was wrong for the peer and is corrected in the records. Not known: which filter dropped any one attempt, whether the Tessera block alone would hold without the capability omission, whether Tessera is a documented interface, anything under UDP, IPv6 or DNS.

Records: two `PERFORMANCE_LOG.md` entries and `docs/performance/mxc_proxy_egress_standard_token_2026-10-16.json` and `mxc_proxy_egress_variant4_wfp_2026-10-16.json` (`bebb33da`, ownership and condition corrections in `b1923fd5`); the variant 4 disposition (finding 4 fixed by the MXC-Loopback derivation, the other three deferred to the next probe build with observable predicates) and the Q3 disposition are in `docs/reviews/`.
