### 2026-10-08 — A folder with a locked-down list can still be renamed away by whoever owns its parent

*Plain summary: while building the restricted coder account's own tool settings, the independent review showed that locking a folder's permissions does not stop the account that owns the folder above it from swapping it for a shortcut to somewhere else, and that my cleanup code would then have deleted the operator's real files through that shortcut.*

Step 4 of the containment flip gives the restricted `blarai-coder` account its own opencode settings, a few read-only grants for the tools it runs, a research-log path of its own, and a git trust entry for exactly its worktree. The builder produced 256 tests and 52 mutations of the code, all killed, and the reviewer ran every suite and confirmed the numbers. The numbers were not the finding. A missing guard has no mutant, so a suite like that proves the guards that exist, not the one that was never written.

The first finding was ordering. The folders were locked down last, after the files were written, and the final loop applied the permission list by path with no check that the path was still a real folder. Applying a list to a shortcut (a junction) changes the target, so a coder that swapped `.config` for a junction to `~/.ssh` during the write phase would have been granted read access to it by the operator's own provisioning. I moved the lock to the instant each folder exists, parents first, and added a link check before and after every application. The second review round then found what that did not cover: NTFS lets the owner of a parent folder rename a child regardless of the child's own list (reproduced with an unelevated token on a scratch tree), so the coder can rename its locked `.config` away at any time and put a junction named `.config` there pointing at the operator's own `~/.config`. The next rollback would have deleted the operator's seven settings files through it. The undo and the verdict now refuse a link at the folder and at its parent, and the link test itself throws when it cannot read a path instead of reading the error as "not a link".

Trade-off: a check followed by an apply still leaves a gap of microseconds, and detecting a swap afterwards does not undo the change it made. The race-free form applies the list through a directory handle opened without following links; that is about thirty lines and a test, and I ticketed it as a flip blocker (#1713) rather than bolt it on late, because the code is dormant behind `containment=off` and the review judged the residual acceptable until the ceremony. Three decisions are the Lead Architect's and not mine: dropping opencode's browser tool block for the coder is a capability change, the coder's research-usage log now lands in its own profile (splitting the evidence stream for the coder-definition-of-done row 6), and the coder's tests use machine-wide Python rather than the project virtual environments.
