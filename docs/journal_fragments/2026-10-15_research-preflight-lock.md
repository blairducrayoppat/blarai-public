### 2026-10-15 — A lock that scans for numbers has to be attacked on what it deletes, what it spares and how it lands

*Plain summary: research records (probe scripts, measurement JSON, the pre-flight checklist) must not carry our internal ticket numbers, because those records get published. A new check now refuses such numbers in a defined set of files, and the public evidence repository's sanitiser and gate were widened to match. Four independent reviews each found something the author had not, including one that would have turned main red on a plain merge.*

Ticket 1791. The measurement arcs publish raw records, and a ticket number in a file, a folder name or a record name tells a reader how our tracker is numbered. `docs/research/PREFLIGHT_RESEARCH_COMMIT.md` is the checklist a research commit follows; `scripts/research_tracker_lock.py` is the control behind its tracker rule, run by `tests/security/test_research_files_carry_no_tracker_numbers.py` in the standing gate. It reads the git index, never the working copy, in five patterns (tracker reference, fixture prefix, session token, a number in the file's own name, and a malformed opt-in), through the same byte readings the identity lock uses (JSON escapes, entities, percent-encoding, gzip, UTF-16). The evidence repository (windows-containment-evidence) got the matching widening: `tools/leak_gate.py` refuses bare three-to-five-digit references and numbers in path names, and `tools/sanitize.py` removes them before a bundle is published.

Three judgments. Scope is by path, not by tree: `tools/probes/<name>/`, `docs/performance/*.json` and the checklist are locked, plus any tracked text file or performance-log entry that opts in; the whole tree would have failed on 117 banked files with references that are history, and a lock that fails on history gets loosened. The banked files are instead frozen in a baseline (`scripts/research_tracker_baseline.json`, 117 content files and 14 name entries at the landing) that may only fall, so a new in-scope file starts at zero. Version numbers in names are exempt: five benchmark harnesses write `ov2026_2_1_0` into every record name, a 2000-to-2099 run followed by a dot and a digit or by `ov` and an underscore and a digit reads as an OpenVINO version, and the cost is a recorded hole (a tracker number in that range written that way passes; it matters when the tracker crosses 2000, about three weeks out). I rejected renaming the writers, which would have changed 14 banked record names and every future run's file name. The branch lands with `git merge --no-ff`, written into the doctrine landing rule next to the identity ratchet's files.

What four review rounds caught, each after the author's own tests were green. Round 1: the widened sanitiser ran its reference rule before the local replacements, so it deleted every bare upstream issue number the local file maps to `owner/repo`, 360 citations in the 9P control record, and the gate could not see the loss because a deletion leaves nothing to match; the hand-grown baseline passed the gate because nothing wired the reference check, and a reference that did not resolve passed too; a reference glued to a word (`PR1786`) was spared; and every 2000-to-2099 run in a name was read as a year, which blinds the name rule to most new tickets within weeks. Round 2: the year fix made the next run of five standing benchmark harnesses write refused names (the version exemption above is the answer), and any prose mention of the opt-in word failed the gate, which would have failed this ship's own review documents. Round 3: with main unmoved since the fork, a plain merge fast-forwards, puts the baseline's intermediate (higher) version on main's reference line and turns main red until twenty more baseline versions land; the installed git hooks already refuse that merge in the real checkout, so the doctrine line is a third layer, but the fix and its test are right either way. Round 4: editing a rules file without regenerating `docs/governance/rules-corpus.yaml` fails two corpus tests, which the agreed targeted test selection never ran. The review reports and their 40-row disposition are in `docs/reviews/research-preflight-review-disposition-2026-10-15.md`.

The lesson from the pattern: a control that deletes or rewrites must be checked against what it removes, not only against what it leaves; a control that is a ratchet must be checked against its own baseline being grown; and a targeted test selection is a proxy for the standing gate, so the doctrine files a change touches name the suites to add. Rejected: a whole-tree scope (fails on history), and a three-digit name rule (it would refuse `arc140v` and `uc0NN`; nine banked names with a three-digit ticket number stay a recorded limit).

**Next:** merge `--no-ff` after the standing gate; the evidence repository's branch `fix/number-patterns-widen` is reviewed through round 3 and merges on its own; the tracker passes 2000 in about three weeks, which is when the version-range hole starts to matter.
