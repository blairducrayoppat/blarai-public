### 2026-10-10 — Read the shipping products before the design question, and validate each instrument against another that could disagree

*Plain summary: phase 1 of the containment comparison (#1740) read OpenAI's, Anthropic's and Microsoft's actual Windows sandboxes. It found that the two shipping agent sandboxes use the same dedicated-account shape BlarAI chose, with a restricted token added on top. Microsoft's new agent container, which OpenAI now recommends over its own modes, ships AppContainer tiers too, so the products split and phase 1 decides nothing. It measured what each setup can reach with Windows' own access check. On the way it found an unrecorded lock on C:\Windows\Temp and two forgotten Codex accounts with write access to the fleet folders.*

The question the LA set was whether a restricted token or an AppContainer is a better design than the coder's dedicated account. The ADR-045 amendment framed it around nono's NEP-0005, a draft that calls AppContainer primary. Reading the raw file confirmed every claim #1669 recorded about it. It also showed that the draft has no Windows code behind it: 111 releases, none with a Windows asset, every external Windows PR closed unmerged. Two products that do ship were read at source. Anthropic's srt (@`5507fb0e`, alpha) runs a dedicated `srt-sandbox` user with a restricted token and a user-SID WFP fence. OpenAI's Codex (@`cc7ba336`, plus David Wiesen's 2026-05-13 write-up, which needed a real browser because the site refuses fetch tools) uses dedicated users with a write-restricted token. OpenAI states why it needed the account: Windows cannot match a firewall rule to a restricted token's second list. Microsoft's MXC 1.0 (2026-10-07) offers both an AppContainer tier and a per-run dedicated-account tier. The draft prefers AppContainer; both shipping agent sandboxes chose the dedicated account, and the draft's own Phase 1 needs the dedicated account. That does not settle the question. MXC ships AppContainer tiers. Chromium uses AppContainer for some processes. OpenAI's documentation now calls its own account-based modes "legacy fallbacks" behind MXC. My first draft of the report said a restricted token "cannot be the network fence" and was therefore only a complement. The independent reviewer blocked that: OpenAI's statement is about firewall rules, not raw WFP filters, and in the access-check model one construction does separate a fully restricted token from the operator. It was also a verdict the LA had ruled out for an interim. It became a question for phase 2, with a B3 arm (fully restricted) added for it.

The instrument work mattered more than I expected. I built two independent access checks: the kernel's AccessCheck on real tokens, and AuthZ on a bare SID for the coder, which cannot be logged on without a password. I validated each against the other before trusting any number. The first run disagreed on 15 of 24 paths. The cause was AuthZ applying no UAC filtering, so the operator's AuthZ context held Administrators enabled. Comparing it with the elevated token instead made all 40 rows agree. The AppContainer token from the operator's real limited token failed with a bad impersonation level. I built a primary token of the same shape instead and checked it against the real one on every path.

Two findings came from the instruments themselves. A true capability SID cannot be a restricting SID (CreateRestrictedToken returns invalid parameter). A deny entry naming an AppContainer's package SID, ALL APPLICATION PACKAGES or a held capability does not deny it under AccessCheck, while a user-SID deny does. An independent reviewer reproduced it with a real file open under an AppContainer token. No primary source states the rule; phase 2 repeats it inside a launched AppContainer.

Comparing today's permissions with the 2026-10-05 spike showed `C:\Windows\Temp` had changed from writable to administrators-only. 197 objects carry the same explicit lock, which puts the change after 2026-10-08 21:59; no upper bound for when is known. A candidate cause is #1695's mutation tests, one of which disables the folder gate while a test calls the real lock function on that folder; it was not reproduced. I filed #1742 rather than fix it, because restoring it reopens a coder write path and the call is the LA's. The same instrument showed that Codex's April setup left two enabled accounts that can write `B:\models` and the fleet folders, with no Windows Firewall rule blocking the offline account's egress (raw WFP filters could not be listed) (#1743).

I rejected one path: running arms B and C anyway because the probes are throwaway. The ticket sequences machine access behind the #775 ceremony, and the LA repeated it, so phase 2 waits and this merges as an interim with no recommendation. The primer now states the facts as checked against Microsoft's documentation.

No lesson is proposed; the instrument-validation habit is already lesson-shaped in LESSONS.
