### 2026-10-14 — A run that never finished was recorded as a denial, and a refused command nearly became a result

*Plain summary: the control that asks whether nono's sandbox fails open on the WSL 9P mount (#1755) ran twice in one evening. The first run, with a pseudo-terminal, hung at an interactive menu nono opens after the command, and my script wrote all six hung runs down as "denied as policy". The second run, with piped input, completed: 360 runs, none let a denied operation through, 222 were denied, 63 were over-denials, and 24 could not be judged. The lesson is what a "denied" has to rest on: a run that finished, a sandbox that was applied, and a control that could have succeeded.*

I built the extension in an afternoon: 26 new probes (a junction, symlinks, a hard link, `..`, other letter cases, 8.3 names, a stream) on top of the original four, a Windows-side fixture, a pre-flight that proves each probe can see a leak, and a self-test of about a thousand checks. An independent reviewer found one thing worth fixing before merge, and it was the one I was proudest of: the rule that decides "nono really started" had no lock, so the first script's looser rule (exit code 0, 1 or 2 counts) could come back and every check would still pass. I had written that rule's replacement because the first record, from 2026-10-12, stored only 500 characters of stderr per row and so could not prove the sandbox banner for 36 of its 48 rows.

Then the first live run failed in a way no check of mine imagined. Under a pseudo-terminal nono runs the command, finds a denied path, and opens an interactive "Review denied paths" menu (a grants everything, d denies everything, Esc cancels) and waits. My runner only knew the working-directory prompt that comes before the command. So all six runs it made sat at the menu until my 60-second limit, exit 124, and the script's verdict rule saw a banner, no effect and a good control, and wrote DENIED_AS_POLICY six times, with an overall of "no policy violation observed". Six minutes in, the abort-after-six rule stopped it. Without that rule the matrix would have spent about six hours producing 360 rows of the same wrong label. The rule had been added as a guard against a stuck run wasting time, not as protection for the result; it protected the result by accident, and that is the part I would not rely on again.

The fix has three pieces and one rejected path. A timed-out run now reads INCONCLUSIVE whatever it shows (commit `dcd4b3f9`), with one exception kept on purpose: an effect already seen from a denied operation stays a violation, because that rule must never be outvoted. The runner now cancels the menu with Esc after waiting for nono's key hints, because nono ignores keys for its first second, and it records the denied paths nono printed, which are nono's own statement of what it refused. A test found a gap in my own list probe on the way, which had judged success by exit code and would have missed a listing that printed the secret's name and then hung. The path I rejected was to run only with piped input and avoid the menu. That gives a clean record and leaves the case a user actually sees unmeasured, so the piped run is kept as run 2 and the pty path stays an open item until the fixed runner has run against the real nono.

Run 2 was the clean one, and it showed the banner rule earning its place. Twelve `mv` runs came back with no "Applying sandbox" line at all: nono refuses `mv` as a startup command before it applies any sandbox ("Command blocking is deprecated in v0.33.0 and only checks the directly-invoked startup command"). The first script's rule would have called each of those twelve a denial, since the exit code was 1 and no file had moved, and the write-up would then have said a move out of the grant is denied 3 of 3 in all four cases. It was never attempted in a sandbox. They read INCONCLUSIVE, the probe now starts `mv` through `sh -c` like the others (`448e237c`), and the README says in so many words that a rename out of the grant is not covered yet. Twelve more rows, the stream read, were inconclusive because 9P cannot address `name:stream` at all, which the control outside nono showed.

What I would carry forward: a verdict of "denied" is three claims, not one. The run finished, the sandbox was applied, and the same operation succeeds without it. Any of the three missing is "unknown", and the failure is to let the absence of an effect fill the gap. Mutation testing of the script's own self-test found four weak tests of mine on the way, including a check that compared the keys the runner types against the very constant that defines them; a lock that reads its expectation from the code it guards cannot fail.

**Next:** run the fixed script, pty and `mv` through `sh -c`, against the real nono; the Lead Architect's own run; then draft the #2089 correction from `docs/research/nono-9p-failclosed-control-2026-10-14/`.

*Proposed lesson (unnumbered): a negative result needs the run to have finished, the instrument to have engaged, and the control to have been able to say yes; a timeout, a refusal before the sandbox and a failed control are each "not measured", never "denied".*
