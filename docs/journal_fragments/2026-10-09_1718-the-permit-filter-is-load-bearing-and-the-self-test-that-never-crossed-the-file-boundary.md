### 2026-10-09 — The permit filter is load-bearing, and a self-test that never crosses the file boundary certifies the wrong thing

*Plain summary: six live runs showed that a locked-down Windows account can reach a local model server over loopback while its internet is blocked only because of one extra "allow loopback" filter; before the runs, an independent review found three ways the scripts could have thrown away or mislabelled that evidence, one of them hidden by a self-test that tested memory instead of the file the run reads.*

The 2026-10-05 evidence record left its own largest gap in writing: the confined account had only ever been the listener, the one client-direction run went against a stub, and no run had ever lacked the loopback permit filter. Arm 1 closed that in one sitting with the Lead Architect (LA) at the machine. Six invocations of `spike-wfp.ps1 -TestC`, alternated permit-on, permit-off, each its own process and its own dynamic Windows Filtering Platform session, each starting its own model server as the operator (Qwen3.5-4B-int8 on the Arc 140V, warm load 5.6 to 9.6 s) and running the account's task three times: before the filters, under them, after them. With four filters the account's POST returned HTTP 200 and 32 tokens in about 1.97 s in all three runs while its connect to 1.1.1.1:443 failed with error 10013 in about 20 ms. With the two block filters only, the same POST failed at the socket in 36 to 39 ms with the same 10013, in all three runs, and worked again once the engine closed; the server's own log shows two requests served in those runs instead of three, so the blocked request never arrived. The filters stood 4.2 s (on) and 2.9 s (off), now timestamped at add and at close. On this machine, under this block, loopback is matched at the connect layer and the permit is what keeps it open. Six runs inside seven minutes are a repeat, not replications, and the document says so.

The part worth keeping is what the review found before any of that ran. I had built the client mode, the permit-off switch, the three-phase run and a verdict table with a self-test row for every exit code, and both PowerShell hosts passed every assertion. An independent adversarial reviewer reproduced three defects with fixtures in under ten minutes. The no-baseline path `return`ed from inside the `try`, so the `finally` ran and the report was never saved: the single likeliest first-run outcome would have left the LA with nothing to send me. Exit 9, the counted "the block stopped the loopback POST" result, was reachable on an HTTP 500 or a read timeout, because a server-side failure and a socket-level refusal carried the same `ok=false, status=0` shape; the discriminating field, the Windows socket error code, was recorded and not consulted. And under PowerShell 7 every real result would have failed the strict schema, because that host's JSON parser turns timestamps into `DateTime` objects and the validator demanded strings, while the self-test stayed green because its fixtures were built in memory and never crossed the JSON boundary the real run crosses. All nine findings were fixed in `8db95d00` before the first live run; the self-test now round-trips a result through the JSON serialiser on whichever host runs it, and exit 9 demands a non-zero socket error code or becomes exit 4.

The trade-off I took: the server is `spike_model.py` in serve mode run as the operator, not the product's own model server. The product's server would have meant starting the runtime, which the brief forbids touching, and the question is about the filter, not the server; the cost is that C7 says "a real local model server" and not "the product's". The rejected path was the stub listener from the 10-05 run, which would have answered nothing about a real connection carrying a completion.

**Proposed lesson:** a self-test whose fixtures never pass through the same serialiser, file or parser the real run uses certifies the fixture, not the run; build the self-test's subject the way the run builds it (write it, read it back, parse it on the host that will parse it), or the green means nothing. The earlier Test B path had the same hole and was never caught because every live run so far used the 5.1 host.

The evening's second lesson came from the cleanup, not the experiment. The verify script found a trace the cleanup had reported removed, three times over, and each time the cleanup's own output had said the step was fine. The batch-logon right is listed by account name while the account exists and by bare SID once it is gone; the cleanup matched only the SID form, so at step 5 it said "already absent" and the verify, reading the file the cleanup leaves behind, saw the orphan after step 7 deleted the account. Fixed for the name (`14e5d442`), the re-run then skipped every SID-keyed step because, with the account and the live state file both gone, it knew no SID, while the verify had read the same SID from the cleaned copy (`8559fd79`). Fixed for that, the third run stopped at the permission entries: `icacls` returns error 1332 for a SID it can no longer map to a name, even in SID form, which I proved on a scratch folder before adding a .NET purge by SID (`ce925cf2`). Three defects, one shape: the cleanup and the verify read the same system through different windows, and only the verify's window was honest about an account that no longer exists. The verify was the control that caught all three; a cleanup that had trusted its own "ok" lines would have left a logon right and an orphaned SID on the operator's machine with a green report.

**Proposed lesson:** a cleanup's own success line is a claim; the independent verify that reads the system through a different path is the evidence, and the two must agree on where the subject's identity comes from once the subject is gone.
