### 2026-10-20 — The delegated-group row ran once the account lifecycle was taken out of the code, and the measurement was the token, not the group

*Plain summary: the one row of the nono Windows-backend questions a Claude session could not build (a throwaway account in a privileged group) ran because the Lead Architect did the account work by hand in Windows' own tools and only the probe was code. A member of Network Configuration Operators, launched the ordinary way, holds a filtered token in which the group is switched off, and the filtering engine refuses its filter add exactly as it refuses a standard user; the account's full token could not be reached through Windows' elevation prompt. The same account launched the next morning by a scheduled task he created by hand, a logon Windows does not split, holds the group switched on, and the engine accepts the add and the delete three times out of three. The build took three Bitdefender quarantines, three file names and five review rounds for the driver to get there.*

Three times in a week a safety classifier had stopped a session writing the script that would create a throwaway account, put it in Network Configuration Operators, log on as it and remove it. On 2026-10-19 the Lead Architect ruled the way through: he performs every account step himself, in Computer Management and the System Properties dialog, following a sheet written from Microsoft's own procedures, and a session rebuilds only the half that runs as the account. That split is what this entry is about, because it changed the shape of the code. With no logon in it, the probe became a small standalone C# program that reads its own token, makes one `FwpmFilterAdd0` keyed to a SID that resolves to no account, one `FwpmFilterDeleteByKey0`, and writes a record; the admin driver creates the test sublayer and provider with no filter in them, hands the operator a run sheet, and afterwards collects, validates per token state, and removes by key. Nothing in either file can create, enable, log on, or delete an account, and a parser lock with 248 planted forms says so on every self-test.

The first sitting's measurement was undramatic, which is the point of a control. Four filtered-token runs as `nco-probe`: elevation type limited, integrity medium, the group present with attributes 0x10 (use for deny only), add refused 0x5. Three runs from the operator's own non-elevated console: the same shape with Administrators deny-only, refused. Three from his elevated console: add and delete succeeded. The standard-token control, re-run that afternoon through the matrix's approved password-reset design as `blarai-spike`: refused 3 of 3, identical to C17 of the week before. The one condition that did not run that night is the one the group's engine ACE is about: the elevation request from inside the account's console showed a credential prompt listing only this machine's administrators, with no field to type the account's name, four times. The night's claim marked the full-token case not established and named the routes that could reach it, each of them a logon the ruling had placed in his hands.

He took one of them the next morning. In Local Security Policy he granted the account the right to log on as a batch job; in Task Scheduler he created a task running as `nco-probe`, whether logged on or not, with highest privileges, its action the probe's E line; he ran it three times a few minutes apart. A batch logon is never split, so the token the probe read was elevation type 1 with the group ENABLED (attributes 0x7), integrity medium-plus, session 0, no linked token, Administrators absent, and `FwpmFilterAdd0` returned 0 three times, each filter read back present, each delete read back absent. The engine's `(A;;0x307ff;;;NO)` entry does what it says for a token that carries the group on. Claim C27 now reads that the group's effect is a property of the token, not of the account: the same member is refused under an ordinary launch and accepted under a batch logon, and the elevation prompt is simply not a route from one to the other for a non-administrator on this build. Expected under Microsoft's documentation; not a finding.

Two things from the morning are worth more than the result. The driver's E rule had required elevation type 2, the shape of the first sitting's expectation, so the three records that answered the question would have been rejected as invalid by token state; the rule was amended to accept type 1 with the group enabled (a deny-only group stays invalid under either type), an independent reviewer's fourth round found that the amended rule would also have counted a token with Administrators enabled under E or F, and that the run sheet promised a post-cleanup check of the task and the right that no code performed; both were fixed before `-Collect` ran, and the check is now the session's by hand, named as such. And the driver's own files turned out to be owned by the writing token's user SID, so after a mode the admin-only folder read non-admin-only: `-Prepare` refuses in that state, and `-Collect` ran with its engine enumeration skipped (the 10:28 record, exit 21) until the owner was corrected by hand. The records show that one instance; which file broke the check they do not say, only that it was written after the 09:28 prepare had passed. The structural fix went in twice: `Save-C4Record` gives every record to Administrators through the file seam, and the independent pre-merge review then found the second write path with the same default, the copies `-Collect` makes, which now get the same owner, folder and files, with self-test rows holding both. One fix for the write path I had noticed, found by me; the sibling path, found by the reviewer: the argument for author and verifier being different people in one sentence.

What the review rounds caught is the part worth keeping. The first probe review found the token facts recording the resolved name of every group, and on the operator's token the Microsoft-account group resolves to his e-mail address, a string the public scrub does not rewrite; the fix withholds names for every account-domain, Microsoft-account and Entra family and keeps names only for well-known SIDs. The same review found 0x80320028 mislabelled as an access-denied code in three places, copied from the Rust harness of the week before: it is FWP_E_OUT_OF_BOUNDS, and no banked record carries it, so nothing changes, but the harness still says the wrong thing. The first driver review found the blocking one: a record was counted under its condition on the account alone, so a line typed into the wrong one of the two open consoles would have produced a counted wrong answer to "under which token state"; validation now requires the elevation type and group attributes the condition names, and a reviewer's premise point turned into a design rule: an F record with elevation type 1 (no split token) would be a legitimate measurement, not an invalid record, so only type 2 invalidates F.

The cost was Bitdefender. Its generic PowerShell heuristic quarantined the probe's self-test runner at 42 KB, then the driver three times once the widened account-lifecycle lock put literal `net user /delete` forms into the executed script (two quarantine records name a static signature family), then held every file it had quarantined against write, rename and delete, even for the operator after he restored them. The way out was structural, not an exclusion: the planted forms and pattern tables moved into a JSON data file the script reads but never executes, bound by hash in the driver proof, and the driver shipped under its third name with two file-level scan exceptions the Lead Architect added. A detail from the trail: the file that survived the longest was the one that had never been executed, and the trigger was the launch, so bisecting the content by halves found nothing; the detection name in the quarantine metadata was the fact that settled it.

Two mundane leftovers from earlier arcs surfaced on the way in. The live folder's first read-only check found four filters in S1 keyed to a deleted account; they matched nobody and the matrix remover took them by key. And the live folder had stopped reading admin-only because a later arc's build subfolders were owned by the operator, which the matrix refuses by design; one ownership change and it ran.

**Proposed lessons:** (1) when a safety control refuses to write a step, split the step out to the person it belongs to and build only the half that remains, then lock the split with a parser check so the boundary cannot drift back; (2) a record is valid under a condition only when it carries the token facts the condition names, never when it carries the right account alone; and the rule must name the token the condition is ABOUT (the group enabled), not the shape the author expected to see it in (elevation type 2), or the answer arrives and is thrown out; (3) a test corpus of forbidden command lines is data, not code: keep it in a file the executed script reads, so that an endpoint product sees a data file and the lock stays bound by hash; (4) a "not measured" that names its routes is a work order: the next morning's result came from the first route on that list.
