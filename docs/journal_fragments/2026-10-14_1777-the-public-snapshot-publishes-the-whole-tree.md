### 2026-10-14 — A snapshot that publishes the tree whole turns every tracked file into a publication decision

*Plain summary: the public snapshot is main's tree minus nothing, so tracked material that belongs in a private folder outside this repository was one run away from the public mirror; a tracked exclusion list, a publisher that subtracts it before scanning, and a lock now hold it back.*

I found it while preparing the next snapshot for a different ticket. The publisher takes `main^{tree}` whole and has one filter, the leak gate, which looks for private words. A file that carries none of them passes. On `3e8fa63e` 23 tracked paths were material outside this repository's subject that is kept in a private folder, plus one knowledge-map row that named the folder's location. The public mirror carried none of it.

The control is a tracked list, `.publicignore`, that the publisher reads from main's tree and subtracts before it scans, compares or commits. It excludes itself and 24 other tracked paths today. The matching rules are written once in `scripts/publicignore.py`, re-implemented in the publisher, and held together by a table of 68 cases that both must answer alike; the publisher runs the table before it trusts its own matcher. A list that is empty, a list that does not exclude itself, a list that would drop `README.md` or `LICENSE.md` (a list matching everything would publish an empty tree), a line outside the rules, a failed table case, or a filtered tree that still holds a matched path stops that repository's publish. A `-DryRun` prints the excluded paths and the filtered tree id, writes its new tree objects to a throwaway directory so nothing lands in the repository, and stops before the ref update and the push.

The lock in `tests/security` reads the list from the index, never the working copy, and checks that the list excludes itself, that every tracked path with a private name is matched, and that no unexcluded blob carries a phrase from a shared file of phrase parts. The scan runs under raw, whitespace-collapsed, UTF-16, gzip, HTML-entity and JSON-escape views over 3,989 blobs in about 8 seconds. The publisher reads the tree under a grep per pattern and a normalized view of every blob, and the lock's docstring says which view each side reads. Every journal fragment the list excludes starts with a marker line, and the lock fails if `BUILD_JOURNAL.md` or an archived journal volume ever carries it, so a held-back fragment folded verbatim is caught. Each check has a toggle that proves it can fail.

Things the controls and the independent review found that I would have missed. The first run of the lock failed on its own docstring, which carried one of the phrases it scans for. One phrase matched an unrelated sentence in an archived journal, so the lock uses a longer form. The publisher's scratch-repository test failed its first clean case because the shared case table itself contained a protected word: a control's own files are inside the control's scope. The review then found that the lock read the list from the working copy while the paths came from the index, that the publisher accepted an empty list, that the two sides read different views, and that the numbered phrase had spellings the lists missed. A second round found a misquotation of the external proposal in an ADR (the quotation marks sat on my paraphrase), a phrase file nothing pinned (it is now read from the index and its digest is pinned in the lock), Markdown-escaped and percent-encoded spellings neither side read, and the control's own review quoting the wording it holds back (the review is now on the list). Each is fixed and locked.

The list can also hold back too much, so a tracked anchor file names the public evidence the posts cite (the evidence document, the run-data folder, the containment study, the README and the licence); the lock and the publisher both refuse a list that excludes any path on it, and the publisher refuses a private pattern file that lacks a phrase of the shared phrase file. The honest limit is that the exclusion is a list. I removed one journal fragment from the list in memory and both locks stayed green, because that fragment carries no phrase; only the list holds it. The marker is a tripwire on a verbatim fold, not a block. The rejected paths: a deny-list inside the publisher script (the lock could not see it), an export-ignore attribute (the publisher builds a tree, not an archive), and moving the files out of the repository (their dispositions and the verifier need them). The first dry run on main also failed the gate on older causes unrelated to this ticket: a clearance pin that lapsed with an edit, two name patterns since retired by decision, and a host-name scrub not yet merged. They have their own tickets and are not hidden by the new filter.
