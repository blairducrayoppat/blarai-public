### 2026-08-07 — The audit reported better coverage the less of it actually ran

*Plain summary: One of our automated quality checks deliberately stops early when it runs out of time. But the tests it never got to were simply forgotten rather than recorded, so the check's own score went UP the more of it got skipped. A busy machine could make a weak result look excellent. The fix records what was skipped and counts it against the score.*

I went looking for this in a parked branch and found it in shipped code.

`fix/1231-budget-honesty` had been sitting unmerged, 151 commits behind, conflicting on the one file it changes. Its analysis was sound and its implementation carried three blocking defects, so the disposition I banked was to park the branch and land the fix directly. Reading `main` to write that fix, the defect was plainly there, on the live path, and had been for as long as the budget logic has existed.

The mutation audit mutates a candidate's code and re-runs the job oracle against each mutant: the oracle going RED means it *caught* the wrong code. There is a wall-clock budget, and on expiry the loop `break`s. Everything after the break simply disappeared — counted in neither `killed` nor `ran`. Both the score and the advisory coverage band are computed from those two numbers, so a tighter budget shrank the denominator while the numerator stood. Fewer mutants attempted, higher apparent quality. On a contended box — exactly when you should trust a result *less* — the number goes up.

The part that makes it genuinely dangerous is the part the code already got right. It stamps `partial-budget`, honestly and correctly. So the evidence reads `partial-budget · 1/1 · strong`: a true statement about completeness and a false one about quality, in the same breath, with the honest half lending its credibility to the inflated half. A reader who has learned to check the completeness stamp — which is the discipline this whole arc has been building — gets a green light on the wrong field. An instrument that discloses one limitation trains you to assume the rest is sound.

Two things landed this morning that made the fix cheap, and neither author knew they were building for the other. `feat/1195` added `_mutant_row` and the `EV_MUTANTS` evidence key, which is exactly the home a third outcome needs. And the guard I added at that same merge — the one that stopped `mutated` admitting rows that never ran — means a `not-run` row can never be read downstream as "this subject was put to the question." I wrote that guard for a different reason and it turned out to be the precondition for this one. The halves fit.

The design decision worth recording is what the band scores over. The score itself still reads `killed/ran`, and I deliberately did not retcon it into a completeness claim: "3 of the 4 mutants we ran were caught" is a true sentence and should stay one. But the *band* is a quality opinion about the oracle, and an oracle is not better because we ran out of time before testing it properly. So the band now scores over the selected set: an unattempted mutant counts against it. An unknown must never be able to improve a quality claim. The rejected alternative was folding unrun mutants into `ran`, which would have made the score honest in aggregate and dishonest in detail — claiming we ran things we did not.

The one place I stopped short of fail-closed: when *nothing* ran, the band stays `unknown` rather than dropping to `weak`. Counting unknowns against you is right; asserting a finding from zero observations is not. `weak` would convict an oracle nobody examined.

The existing tests could not have caught any of this, and the reason is worth more than the bug. `test_budget_expiry_mid_run_is_partial_budget` uses a sharp oracle that kills every mutant, so the score sits at a 100% ceiling — and a ceiling cannot detect inflation. The test asserted `ran == 1 and killed == 1` and was perfectly happy while the band read `strong` on a run that had dropped most of its work. It took a mixed-verdict runner, where some mutants survive, for the defect to be observable at all. I then proved the new locks by reverting the band to `killed/ran`: exactly the two coverage tests went red, with the messages I wrote for them, and nothing else moved.

**Recurrence of lesson 330:** *a check that can fail to run needs a third answer that is not "pass"* — here the third answer is a `not-run` mutant row, and the instrument is the mutation audit rather than the parity check. This is the same remedy in a fourth place.

**Proposed lesson:** *An instrument that honestly discloses ONE limitation earns trust for the fields it is still lying about. `partial-budget` next to an inflated score is worse than no stamp at all, because the disclosure is what persuades the reader the rest was checked. When a run is partial, audit every derived figure for whether it silently assumed completeness — the stamp is not the fix, it is the reminder to go looking.*

**Proposed lesson:** *A test whose fixture pins the metric at a ceiling cannot detect inflation, and it will pass forever while the thing it guards drifts. When a lock asserts on a rate, check that the fixture can produce a rate strictly between the extremes — an all-pass or all-fail fixture makes the assertion structurally unfalsifiable in the direction that matters.*
