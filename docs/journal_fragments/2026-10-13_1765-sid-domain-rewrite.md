### 2026-10-13 — An exemption written to protect four reviewed files was the mechanism by which the identifier spread to 87

*Plain summary: the machine's Windows account-domain security identifier (SID) was in 87 tracked files on main, 918 times, and already in four files on the public mirror. One byte-level script rewrote it to the bundle's placeholder domain everywhere, the hashes of the four hash-bound files were re-recorded beside the originals, the bundle test's per-file exemption was removed, and a whole-tree lock now pins the domain by digest and by the live machine so it cannot be committed again.*

The NEP-0005 work (#1763) ended with a deliberate exemption: four code files kept the test account's real SID as a constant their guards compared against, three of them hash-bound to the reviewed run, so the bundle test allowed exactly those SIDs in exactly those files and the README said "rewrite before any public push". The independent review of the publish gate (#1741, hand-back rev2) then measured what a whole-tree snapshot would carry and found the domain in about 80 more files from the Windows containment comparison study, plus the DACL test, the operator tool and a performance summary, and four files already on the public mirror from the 2026-10-09 snapshot. The Lead Architect's decision was to rewrite first and publish by the standard full snapshot afterwards, rather than hand-patch four files into the public tree.

I measured before writing: 85 tracked files carried the prefixed form (the review's 84 counted only files changed since the public snapshot; `shared/tests/test_file_dacl.py` was already public), two more carried the bare digits without the `S-1-5-21-` prefix, 916 prefixed and 2 bare occurrences, every file LF with no byte-order mark, 76 of them JSON run data. The existing sanitiser (`tools/research/sanitize_containment_evidence.py`) is a copy-and-reserialise tool for building the bundle from raw data: it rewrites JSON layout, cuts model text and replaces user and machine names, none of which belongs in an in-place pass over run data whose bytes are evidence. So `scripts/rewrite_sid_domain.py` is a second, narrower tool: byte replacement of the bare digit form only (which also covers the prefixed form), over `git ls-files` only, placeholder from the bundle, domain read from the machine and never written to the script or its log. It rewrote 87 files and 918 occurrences, the log records the sha256 before and after per file, and every JSON file still parses.

The hash-bound files were the real cost. `halfset.rs` ran as bytes hashing `e0d560fc…`; the bundled copy now hashes `cbd6ad65…`. Dropping the reviewed hash would break the chain to the run; keeping only it would make the public copy unreproducible. Both are recorded, in AS_RUN.md and in the performance JSON, with the one-line reason. The alternative, keeping the exemption and hand-patching the public copies, was rejected because a later full snapshot would silently overwrite the public placeholders with main's bytes, which is exactly how the four files reached the mirror the first time.

The independent review of the first commit failed it on two things a byte rewrite cannot know (the record names them R1 and R2; a third, lower item was the truncated quotation below). The Codex-removal tool (`tools/operator/remove_codex_sandbox.ps1`, #1743) pins a sha256 of its own allowlist, and five of the rewritten SIDs were inside that allowlist: the rewrite changed the digits and left the pin, so real mode refused at its first gate and four standing-gate tests failed on the branch while passing on main. A re-pin alone would have been the wrong kind of fix, because those SIDs were what the tool's identity gate compared against. The accounts they named were deleted by the Stage 1 apply on 2026-10-11 and a deleted account's SID never recurs, so the recorded values can never match a live object again whatever digits they hold; the pin is recomputed and the header now says so, naming which gates still refuse (the identity match, in the closed direction) and which scans lost their SID needles. The second thing was a truncated quotation in a review record carrying one of the three numbers alone, which neither the rewrite (it needs all three) nor the lock's first form could see; the lock now also pins each number by digest and tokenises runs of digits so a domain glued behind a leading number is still read as the domain.

The lock had to name the domain without containing it. It pins the sha256 of the bare domain string and also reads the live machine domain from .NET at test time, failing rather than skipping when it cannot. It scans tracked files only: two of the 48 untracked files in the main checkout carry the domain today (review hand-backs that are other sessions' work); the lock fires on whoever commits one. The gate review's two corrections were accepted as written: the `#1753` branch edits the same bundle test at non-overlapping lines and merges over this change by merge, and the untracked files stay untouched.

Not done here, by decision: the user and machine name in about 634 public paths, the four files in public history, and why the publisher's leak gate let the domain through on 2026-10-09, all later #1765 steps with their own predicates. Not scrubbed: the orphan foreign SID `76345465-…` (DATA_MAP §4c says it is not this machine) and the two Codex sandbox domains, which the DACL and removal code are written around.
