### 2026-08-06 — A handoff card written by a session that kept working is not a handoff, it is a fork

*Plain summary: I was handed a landing card and gated on it. While I was presenting the gate, the session that wrote the card merged the branch I was proposing to merge. It had never stopped. Everything downstream of that — my inventory, my plan, my sense of what was mine to do — was stale before I read it.*

I picked up a landing card at 19:57 and did the grounding properly: clock, git log, board, governance surfaces, the card's own verifier. It passed, nine anchors, zero drift. I read the branch it pointed at, confirmed the review was complete, and presented a comprehension gate that said, in effect, *step two is to gate this branch and merge it.* Then I stopped and waited, which is the rule.

At 20:08:37 the branch merged. Not by me.

The Lead Architect caught it before I did and asked the only question that mattered: was it you? If it was, say so, because a gate that says "I am stopping" and then acts means nothing. That is exactly the right question and I want to record that it was asked that way, because the honest answer was available on disk and I did not have to be trusted for it. The merge commit contains a branch gate figure — `10292 passed / 0 failed / 21 skipped / 129 deselected in 594.50 s`. I never ran that. A ten-minute test run cannot hide inside a transcript of reads. The commit's author line said `Blair <mr.blair.do@gmail.com>`, which every agent on this box shares and which therefore proves nothing in either direction; the unrun gate proved it.

It was the predecessor. `claude.exe` PID 12740, alive since 15:51:22, still holding a `tail -f` on the battery log it had launched at 17:09. It had written a landing card and then carried on working. The card was accurate when authored and wrong within the hour, because its author was still changing the world it described.

That is the lesson, and it is not about that session being careless. Our whole handoff discipline assumes a baton: one runner stops, one starts, and the card carries what has no durable home. A card written mid-stride creates two runners holding the same baton and neither knowing it. The failure mode is not that the successor does the wrong work — it is that the successor does *correct* work against a world model that quietly expired, and has no signal telling it so. My branch inventory is the clean example: the card said the landing push had gone from 26 branches to 20, and `git branch --no-merged main` still returns 26, because the six were classified into SUPERSEDED and PARKED, both of which preserve the branch by design. The classification was real. The count never moved. I would have repeated "20" to him as a fact.

The concrete control I would want is cheap: a session that authors a landing card should stop, or the card should say it has not. Nothing in the template asks the author to declare whether they are still running, and nothing in the successor's grounding asks it to check for a live sibling — which is a five-second `Get-CimInstance` away and which I only ran because I had been told the merge happened.

There was a second, smaller error inside the same hour, and it belongs here because it is the *same shape* as one the predecessor had already written up. Its close-out concluded that clause 2 of the behaviour-contract work was unobserved, because "the run exhausted its budget and never reached the capture." The run did exhaust its budget — on its third job. Its *second* job had finished at 19:50:53, run three captures, and emitted a graded verdict quoting the declared selector verbatim. The evidence was on disk, in a completed job, at the moment the conclusion was written. The predecessor's own disposition record from earlier that day says: *a stopped subagent is not one that produced nothing — check its artifacts before inheriting a narrative about them, including your own.* A timed-out run is not one that captured nothing. Same lesson, four hours later, different noun.

And I got it wrong in the other direction immediately after. I told him the graded verdict "has no teeth," which was too strong: `computeHard` includes the behaviour flag, and the finding did drive three automatic fix passes. They failed to coder timeouts, not to being ignored. The real defect is narrower and structural — the capture runs *post-merge*, so a declared failure can never block the delivery, and the fallback when every fix fails is to keep the broken version and report `MERGED`, which is a fail-open on an error path. That went to #1303 as a quality-posture question for him, at a smaller size than my first claim, because shrinking a claim when the code says so is cheaper the same hour than a month later.

The trade-off I made and would make again: with the tree finally quiet I chose not to land #1301 tonight, even though it fits the clock — roughly an hour of work against two and a half hours, with the standing gate measured at 307 s. It rewrites `shared/fleet/dispatch.py` and its neighbours, which is the code path the 23:00 battery runs. Landing an unreviewed rewrite of the dispatch machinery two hours before the nightly fires stakes a night of measurement on being right first time. I parked the merge on an observable predicate — the night's scorecard file existing — and spent the window on the half that carries no risk, an independent review, so the next session inherits a reviewed branch instead of an unreviewed one. The clock was never the argument; the soak window was.
