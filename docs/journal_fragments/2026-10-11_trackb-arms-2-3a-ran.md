### 2026-10-11 — Arms 2 and 3a ran clean; the part that had not run was wrong in three places, and one test certified a sentence I had not checked

*Plain summary: the long-hold test (7,200 s, 120 of 120 probes refused) and the persistent-filter add-and-remove test both ran live and passed; the restart test did not run, because an independent review found that the restart command is forced (it closes applications without asking), that its arming script left a gap with no cleanup, and that privileged tasks ran scripts from a folder ordinary processes can edit. The code fixes pass their self-tests against fakes; none of it has been exercised against a real restart, task scheduler or the real engine.*

I built the scripts for arms 2 and 3 and the lead ran them. Arm 2 held the four-filter block for 7,200.9 s with Bitdefender running: 120 samples, 120 refused, every one with Windows error 10013, probe time 24 to 116 ms, the operator's own watchdog 3,421 connects with no failure, and three filter exports each holding all four keys. The only Bitdefender signal was weak: three of its install folders had their timestamps move between 14:42 and 16:42. One hold is one observation, and I wrote the claim row that way (C9, OBSERVED 1 of 1) instead of letting 120 samples read as 120 trials. Arm 3a added the persistent set (flags 0x1 on all four objects), read it back present, got the account refused (10013, 82 ms), removed it by key in 20.9 s, and the absence check refused to start the account both on the empty fence and after the removal. The follow-up removal found all four keys already gone.

The review of the same scripts, which I did not write and could not talk out of its findings, found what my own self-tests were built to agree with. The worst was a sentence of mine: "`shutdown /r /t 600` without `/f` protects unsaved work". I wrote it in the design note, in the script header and in a bundle test, and the test passed, because it asserted that the argument list contained no `/f`. `shutdown /?` on this machine says that a timeout above 0 implies `/f`. The check was one command away and I reasoned from the argument list instead, which is the proxy mistake the standing rule names. I replaced the sentence everywhere it appeared, and the test now asserts the argument list AND that every document states the restart is forced (with a toggle test that fails on the old wording). Whether a forced restart of the operator's machine is acceptable is his decision, not mine, so 3b stays unrun.

Two independent reviews of my fixes then found more: the wrapped script's text was still evaluated from a user-writable default path before any hash or proof check (code execution as the operator when elevated, reproduced), the ancestors of the script folder were not checked for owners or delete rights, and arm 3a itself had run the pre-fix scripts, which I had not said plainly. Those are fixed in later commits, with the as-run provenance banked in `AS_RUN.md`, and the restart decision is now enforced in code instead of only written down. The other findings were of a different kind: ordering and trust, not wording. The arming script added the persistent set and then registered the tasks that would clean it up, so an exception, a kill or a power loss in between would have left a persistent block with nothing to remove it, and the exit code would have said "nothing was added". The tasks now come first and an arming that never completed is recognisable. SYSTEM and elevated tasks ran scripts from a folder a non-elevated process of the operator can write; they now refuse unless only administrators can change the folder, and the SYSTEM tasks pin the hash of the wrapped script before its text becomes code. The rollback proof did not cover the wrapped script that builds the security descriptor (a one-token edit there would have made the filter match Everyone, with the proof still valid), and it accepted a file written without any self-test run; it now binds the wrapped script and requires the evidence a real run leaves. The post-reboot check depended on the network and could have kept a SYSTEM startup task alive forever and then reported a false "did not survive"; verification is now the engine reading absent, attempts and age are bounded, and a repeat run or an unrecorded add is reported as inconclusive.

I also have to record a slip of my own. Before the live runs (about 14:21, some 27 minutes before arm 2 started) I ran the live `-Check` and `-Remove` entry points of the persist script in both hosts, expecting them to refuse because I assumed my session was not elevated. It was. They opened a real BFE session and issued four delete-by-key calls for objects that did not exist; all returned not found, nothing was added, and it is now in the handoff record. It also happened to show the real not-found statuses mapping correctly. I should have run `IsInRole` first, and I did not.

One thing I could not explain: three times a Windows PowerShell 5.1 self-test process spun at full CPU with a 36 MB working set for more than five minutes under a harness that redirects the temp folder and the module path. Re-runs under the same environment finished in about two seconds. I capped each run and retried once, and I am not claiming a cause.

**Proposed lesson:** a test that checks a belief about an operating-system tool against the author's own argument list passes forever; when the tool can be asked (`shutdown /?`), ask it, and make the test assert the documented behaviour and the documents' disclosure of it. (Recurrence of the "direct check, not proxy" rule in the standing instructions.)
