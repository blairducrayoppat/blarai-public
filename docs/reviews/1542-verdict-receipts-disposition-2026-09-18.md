## What the reviewer attacked and could not break

- **The migration claim, verified CROSS-COMMIT.** It extracted `4ca4a659^:shared/security/audit_log.py`,
  wrote a 20-record chain with the **parent's code only**, then verified it with this commit's code:
  new code verifies 20 parent-written records, the mixed 20+13 chain verifies in process and again
  after a reload from disk, and the v1 canonical bytes are **byte-identical** between parent and
  child — not merely equivalent. This is the ticket's "must be traced first", settled.
- **The no-payload claim, driven rather than read.** A real dispatch carrying
  `CANARYARG-9f3b-tool-argument-secret` and a real `_adjudicate` on a URL carrying `CANARYPATH-7e21`
  and `CANARYQUERY-4d09`: no canary reaches either door's records. Re-measured after the fixes, now
  through the registered production sink: still absent, `resource` still the bare host.
- **Receipt tamper detection**, with an untouched control passing.
- **The ingest chain across the one-ladder refactor**: same filename, signer selection, verification
  and record ceiling.

## The honest note

Findings 1 and 2 are the same defect — a control that exists and is called by nothing — and I
shipped it twice in one day, the second time in a file whose docstring cites the first time. The
lesson is not "write locks"; I wrote six. It is that a lock over SOURCE TEXT cannot distinguish a
call from a comment, and I reached for one exactly where driving the real loop was inconvenient.
Every lock that drove real code in this change (the egress door's) survived review. Every lock that
read source text (the dispatch door's) was defeated in one edit.
