## Context

Decision 1(b) (2026-07-10) is a separate limited Windows account for dispatched code (`blarai-coder`) plus a per-account outbound block, adopted as the floor for all dispatched code, with a hybrid later (cross-platform jobs in the network-less Alpine guest). On 2026-07-10 the four-check proof ran green under the accepted-gap mode: outbound WARN (accepted), operator secret paths ACL-denied PASS, loopback to the live OVMS as the coder PASS, SID on the real spawned child PASS (#775 comment 1654). Bitdefender owns packet filtering on this machine, so Windows Firewall rules, including the per-SID rule, were inert; the LA kept Bitdefender and accepted the coder-egress gap (comment 1653), with re-visit triggers a Bitdefender posture change, the VM leg going live, or an egress incident.

**The `containment` flag was never decided "off".** On 2026-10-04 read-only forensics (`coder-containment-lapsed-deferral-2026-10-04.md`) found that `"off"` is the dormant day-one default shipped in agentic-setup `4c91809` (2026-07-10). The LA approved deferring the flip on 2026-07-11 for sequencing (the ACP driver had just gone live; stacking containment on that night's battery would have confounded it), with a stated bound of 2026-07-18 and "re-surface to the LA if it slips". The last update on #775 was 2026-07-15. The bound was about 78 days past with no re-surfacing: a lapsed deferral. Bitdefender explains the separately accepted egress gap, not the flag. What `off` does today: its only reader is `Resolve-WorktreeBase` (which worktree folder is used); the production coder path (`Invoke-AcpCoderRun`) does a plain `Start-Process`, so model-written code runs as the operator's own account with open egress and operator secrets readable. The account, ACL secret denial, worktree relocation and a dormant `\BlarAI\BlarAI-Coder-Leg` scheduled task exist; the fused leg (a full dispatch running as `blarai-coder`) had never been wired. The forensics' finding is that the deferral lapsed with no owner.

The 2026-10-05 pre-flight (read-only; `775-preflight-2026-10-05.md` in `C:/Users/mrbla/blarai-research-data/ideation/`, not in this repository; comment 3879) found the state stale and more holes: no `verify-coder-containment.ps1` run after 2026-07-10 in any log; `C:\blarai-fleet` is Modify for Authenticated Users inherited from `C:\` (#1686); the coder still has Modify on all 45 child directories of `C:\Users\mrbla\projects` (#1678); the `verify-fleet-driver` suite had been red since the 2026-07-11 driver flip because it asserted `driver == stdin`.

## Decision

1. **Containment is account-level, and that is the non-cooperative seam.** The dispatched coder runs as a dedicated account whose rights the operating system, not the agent's own program, enforces: NTFS ACLs for files (proven, check 2) and a kernel-level per-account egress block (see 4). By design both bind everything that runs inside the account, child processes included; only a single probe process was tested for egress. They do not give per-action semantic governance, and they bind only what runs inside the contained account. A limited account is an ACL boundary, not a kernel or VM boundary: a local privilege-escalation exploit escapes it (threat model §5.2); the hybrid direction remains the answer for that.
2. **The fused coder leg** (agentic-setup, merged with containment `off`: `d026f5c`, flip-blocker fixes `39dc7e9`). With `containment = restricted_account`, only the coder step moves to `blarai-coder`; the gate, git and merge stay with the operator:
   - Job and prompt are written to a queue; the `\BlarAI\BlarAI-Coder-Leg` task is started (with the `0x41303` start diagnosis); the result is awaited, bound by job id, kind, SID, boolean `ok`, file owner and creation time, and rebuilt into the shape `Invoke-AcpCoderRun` returns so the gate and merge are untouched.
   - **Fail closed everywhere; no operator fallback and no stdin fallback.** Missing account or task, task never started, timeout, missing or unusable result, an unreadable manifest while the task is registered, a queue tree writable by other accounts, links in paths: all throw. The coder-leg task is stopped on timeout or cancel; a single-instance task means best-of-N candidates take turns behind a named mutex. With `off` and a readable manifest behaviour is byte-identical to main (reviewer-verified).
   - **One funnel per kind of operator-side use of a path the coder can write** (`docs/fused-leg-operator-uses.md`): git through `Get-WtGit` (identity, no link, `.git` pointer and gitdir fingerprint re-verified, hardened argv with pinned git-dir and work-tree, hooks and fsmonitor off), commands through `Assert-OperatorWorktree`, file writes through `Get-OperatorWorktreePath`, worktree removal through `Remove-WorktreeSafe`, result and transcript reads through one held handle. A lint fails when a new use skips its funnel; a mutation harness proves the funnels are what the tests exercise.
   - **ACL work is LA-run:** account and ACL changes are blocked for the harness, so the session prepares scripts and exact commands (provisioning stages, the deny commands for the coder on the worktree-base folder itself) and the LA runs them.
   - **In progress, not merged: the post-coder window.** The round-3 review reproduced (N1) that a worktree swapped for a junction after the identity check made the hardened `git add -A` stage a victim file into the agent worktree's index (reproduced in a temp sandbox; the review calls a coder process outliving the leg a hypothesis, since the real task could not be run). The swap window after the coder returns is the open flip blocker; the job-object fix below is in progress and not merged. The first fix (`49bd0d9`, branch `fix/1691-n1-n3-n5`) held a handle on the worktree and enumerated and killed every process owned by the coder SID, which needs an elevated orchestrator; the orchestrator is launched by `dispatch.py` as `pwsh -NoProfile -NonInteractive -File` with no RunAs, from which the session INFERRED it is not elevated (not observed: a child inherits its parent's token, and whether the orchestrator itself runs elevated was not checked). The decided design (`d0120f5`, same branch) needs no elevation: the runner, which runs as the coder, creates a Windows job object (kill-on-close, no breakaway) and starts the ACP client inside it, drains and confirms the job empty, and writes `job_zero_confirmed` into the typed result; the operator refuses a result without it and quarantines the worktree on failure or timeout, and clearing a quarantine takes `Clear-FusedQuarantine -ClearedBy <name>`, which writes an audit line (the control is a name parameter plus the audit entry; it accepts any non-empty string and does not check identity). The same branch carries the AST-based lint (N2), the fingerprint locks (N3), the audited critic and battery consumers (N5), and one strict shared JSON parser with typed schemas for jobs, results and the dispatch envelope (`b4627ed`). **Implementation status: in progress, not merged**; `Stop-ScheduledTask`'s real-OS guarantee is documented "verify live" because it needs a registered task.
3. **The lapsed deferral is closed by ownership, not by a new date.** The remaining steps are tickets (#1691, #1686, #1678, #1682, #775) and are listed in 6; the session owns the technical steps and the LA owns only the flip (#775 comments 3858, 3861). The session's reading, offered as reasoning and not as a recorded rule: CLAUDE.md `deferral_discipline` already requires a `blocked-by` predicate someone can observe for review findings, and a bound that names only a date and no owner is the shape that lapsed here.
4. **The raw WFP per-account egress block is the egress leg, and is to be productionised (#1682).** Evidence (#1671, LA present, 3 of 3 runs, 2026-10-04 23:59 to 2026-10-05 00:00 -04:00): a raw Windows Filtering Platform BLOCK filter keyed to `blarai-coder` (ALE_AUTH_CONNECT V4 and V6, matched on the account's SID through a security descriptor; one provider, one sublayer, weight 0xFFFF; loopback PERMIT keyed to the coder) enforces while Bitdefender owns filtering. In each run: operator baseline 6 of 6 connects to 1.1.1.1:443 and 8.8.8.8:443 OK; coder baseline `outbound_blocked=False`; with the filters in place the coder's outbound connect was blocked, its loopback connect succeeded, its SID was the coder's, and the operator's traffic was unaffected (watchdog every 2 s, 0 failures); after the engine was closed the filter objects were gone and coder egress was open again, so the block is attributable to the filters and not to the probe's exception-counts-as-blocked rule. **How thin this is:** each run is one TCP connect from the coder to 1.1.1.1:443 (8.8.8.8 was never probed from the coder), with the filters active for about 3 to 5 seconds (`hold_seconds` was 100, but the probe finished and the engine closed within seconds), and the operator watchdog took 3 samples about 1.5 s apart to 1.1.1.1 only; "3 of 3" is three connects across about a minute, IPv4 TCP port 443 only. **Conditions:** Bitdefender processes present (`bdagent`, `bdntwrk`, `bdredline`, `bdservicehost`, `bduserhost`), Windows Firewall profiles enabled, `mpssvc` and BFE running, elevated shell, Windows PowerShell 5.1, uptime about 19 h, Windows 11 Pro 10.0.26200. **Loopback was exercised against a stub listener the script started on 127.0.0.1:8000** (`loopback_stub_started: true` in all three result files), not against the live OVMS. **NOT tested:** persistence across reboot (the filters were dynamic by design), IPv6 destinations, UDP and DNS, non-443 ports, behaviour under a Bitdefender update or restart, and a real coder dispatch under the block. Scope of #1682: persistent filters (persistent provider and sublayer, or a boot-time elevated task, chosen by a reboot and Bitdefender-restart survival test); fail closed (filters absent means the fused leg refuses to run and `verify-coder-containment` check 1 becomes HARD again, no `-AcceptedEgressGap`); IPv4 and IPv6 TCP, plus UDP and DNS and other ports; loopback permit scoped to the coder user; install, rollback and verify scripts with a dead-man removal, added to provisioning as an LA-run stage, with a toggle test (filters off makes verify fail) and an operator-unaffected control.
5. **Relation to ADR-042.** ADR-042 rests on the finding that every enforcement seam a third party can reach on Windows is cooperative, and that the one non-cooperative seam probed (a per-process firewall rule) failed silently. #1671 is new evidence on one dimension, on this machine only (3 of 3): a per-account kernel filter is enforced under Bitdefender, and NTFS ACLs on a dedicated account are the same kind for files. A third-party open-source agent sandbox has a draft proposal for the same shape on Windows. It does not make per-action governance non-cooperative. **This ADR does not reopen the venture.** ADR-042 sets no check-back and no resumption condition; whether this evidence reopens anything is the LA's decision, and no work is implied (noted on #1682, comment 3880).
6. **Criteria for the flip** (`containment=restricted_account`, an LA-present go-live in a window that is not a battery night; assembled from #775 comments 3862 and 3886, #1691 comment 3887 and #1682):
   - the fused-leg flip blockers closed and re-reviewed: N1 (job object, in progress), N2, N3, N5 (in progress, same branch);
   - #1686: `C:\blarai-fleet` tightened to the operator, `blarai-coder`, SYSTEM and Administrators; a third local account cannot write, Authenticated Users has no ACE (LA-run);
   - #1678 (LA decision 2026-10-05, comment 3892: narrow): the `blarai-coder` Modify grant on `C:\Users\mrbla\projects` (`provision-coder-account.ps1:298-301`) removed; the coder gets write only on its worktree base `C:\blarai-fleet\worktrees` and the per-job paths the fused leg needs, and read-only elsewhere (how repositories under `projects` that it legitimately needs to read are granted read-only is decided in the stage); the session prepares the provisioning stage (a targeted undo of the existing grant plus the narrowed grants) with a dry-run listing of exactly what changes, batched with #1686, and the LA runs it; a NEGATIVE verify check is added to `verify-coder-containment.ps1`: a write by the coder outside its worktree (probing a sibling repository under `projects`) must be DENIED. Ordering: after the #1691 N1 fix merges (same scripts);
   - #1682 built, and verify check 1 hard;
   - the coder's own setup: a coder-owned opencode configuration with the same read denies, read grants for opencode, node, git-bash and the venv, a probe of the repair proxy at 127.0.0.1:8099 (verify and probe test only :8000), research-log write, git trust for coder-owned worktrees;
   - the wait budgets registered on the BlarAI side (`shared/timeout_registry.py` and its nesting test; written up in agentic-setup `docs/fused-leg-budgets.md`, not yet registered);
   - `verify-coder-containment.ps1` green in real mode (OVMS and proxy up), checks 2 to 4 hard;
   - the coder cannot read `~/.ssh`, `%LOCALAPPDATA%\BlarAI` or the operator's opencode configuration; account or task missing fails closed with no coder running as the operator; orchestrator-side git can read, merge and clean coder-created worktrees;
   - one watched fused dispatch of a small task, merged, with the coder SID in transcript and result, using a process-scoped override and not the production file; a rollback drill (`provision-coder-account.ps1 -Rollback`);
   - the full 117-mutant harness pass, not yet completed (about 2 hours at throttle 3, to run in a quiet window).

## Alternatives considered

- **Leave containment off** (the status quo that lapsed). Model-written code runs as the operator with secrets readable and egress open. Rejected.
- **Accept the egress gap permanently** (the 2026-07-10 position). Reasonable when no enforcing mechanism existed. The LA's re-visit triggers (comment 1653) were a Bitdefender firewall-module change, the VM leg going live, or a fleet-code egress incident; none has occurred. #1671 is new evidence, not one of those triggers (see Re-visit triggers).
- **Disable Bitdefender's firewall module so Defender Firewall enforces per-SID rules** (the 2026-07-10 recommendation). The LA kept Bitdefender; the raw WFP filter makes the question unnecessary.
- **Adopt a third-party open-source agent sandbox** (#1669, not adopted): no native Windows enforcement (no release in the range examined ships a Windows binary), its "Windows support" is WSL2 which is not installed here and cannot enforce on C: files, its own security policy says production use is not recommended, and it has 12 published advisories (3 high) since May. Watch trigger: a release carrying a Windows asset, or its Windows proposal leaving draft, or its tracking issue for Windows closed. Anthropic's sandbox runtime ("srt") was not evaluated. A guest-fit spike (#1670: Landlock in the Alpine guest plus synthetic hostile fixtures on a throwaway runner) is ticketed (#1670, open, no result recorded).
- **Elevated enumeration and kill of the coder's processes after the leg** (the first N1 fix). Superseded by the job object because the orchestrator is inferred not to be elevated (from its launch command line).
- **Move the whole dispatch, not only the coder step, to the coder account.** Rejected in the plan (#775 comment 3862): the gate runs model-written code as the operator by design, but the funnels re-verify everything coder-writable before each operator-side use.
- **Run the coder in the Alpine guest only** (threat model §5.4, hybrid). Cross-platform jobs only; Windows-native jobs (WinUI, .NET) cannot build there. Designed, not built; the RAM benchmark cleared on 2026-07-10 (peak 27.5 GB against the 31.323 GB ceiling).

## Consequences

- Flipping the flag is a go-live ceremony with a concrete list (6), not a date.
- The accepted egress gap (comment 1653) stays in force until #1682 is built and verified; none of the LA's named re-visit triggers has occurred; #1671 is new evidence that the gap is closable (recorded by the session on #775 comment 3874), and nothing is enforced yet.
- Until the flip, the production coder path is unchanged: the coder runs as the operator.
- **Residuals** (threat model §5.2 and the reviews): destruction within the coder account's own reach (worktree and temp); local privilege escalation; the target repository's own contents; the dependency trade-off once egress is blocked (a pre-staged local mirror is needed for `npm install`, `uv sync`, `pip`); the stall monitor's ability to read another account's process CPU is unmeasured (hypothesis, review L8); the 2026-08-14 `blarai-coder` logon is unexplained (the Security log only reaches back to 2026-10-02).

**Source disagreement (loopback):** the #1671 result comment first read "loopback OK" and #775 comment 3874 repeats it; the three result files show the loopback probe reached a stub listener the script started on 127.0.0.1:8000, not the live OVMS (#1671 comment 3891 corrects the result comment; #775 comment 3874 stands uncorrected as of this record).

## Re-visit triggers

**The LA's triggers for the accepted egress gap (#775 comment 1653):** a Bitdefender firewall-module posture change, the VM containment leg going live, any fleet-code egress incident.

**New evidence, not an LA-named trigger:** #1671 (a raw per-account WFP block enforced under Bitdefender) was recorded by the session on #775 comment 3874 as making the gap closable and productionising it (#1682) as joining the plan. Whether it changes the acceptance is for the LA when he re-records the acceptance for the go-live.

**Other reasons to reopen this design (the session's, not the LA's):** a bypass of the funnels or the job object in review or use; a Bitdefender update or restart that drops the filters (the persistence test in #1682); a release of that sandbox with a Windows asset (#1669); the start of the three-account work (ADR-046).
