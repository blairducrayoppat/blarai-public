# ADR-043 — Commit Protection Is Enforced in Layers: Git-Native Hooks for Main, a Best-Effort Text Guard for Staging

**Status:** Accepted (session decision 2026-10-05; LA informed, #1687 carries the plain-language explainer). **No BlarAI runtime change**: this governs how the repository is developed, not what BlarAI does.
**Date:** 2026-10-05
**Deciders:** The session (all technical decisions); the LA is informed and owns the install step and the override. No capability, quality or runtime posture changes, so no LA decision gate applied.
**Related:** #1690 (the work) · #1687 (explainer) · #1689 (three-account design, the long-term answer for the coder fleet) · `docs/governance/git-rules-guard.md` · `docs/governance/commit-protection-explained.md` · `docs/governance/rules-corpus.yaml` · CLAUDE.md `git_discipline`

## Context

CLAUDE.md `git_discipline` says: never commit work directly to main (the one sanctioned commit is the merge commit that lands a reviewed branch, plus its atomic ticket/journal companions), and never `git add -A` (blanket staging sweeps other sessions' untracked files into a commit). The rules were written down and still failed by memory: sweeps of other sessions' files, and direct commits to main. The user-level destructive-git hook covers other verbs only and fails open on parse errors.

Four things shaped the design. (1) Git has no hook for `add`, so blanket staging can only be seen as command text. (2) Text guards have a parser differential: over four review rounds an independent reviewer and a seeded fuzzer (real bash and PowerShell with a recording git shim, 4000+ variants) found 24+ ways around the text guard, each fixed and locked. (3) A hook that lives in `.git/hooks` is not versioned. (4) Sessions run as the operator, so permissions cannot separate them from the repository.

## Decision

1. **Commits on main are controlled inside git.** A `pre-commit` hook and a `reference-transaction` hook (git 2.28+) in `scripts/githooks/`, installed by `scripts/install_git_hooks.py` through an absolute `core.hooksPath` (a relative path does not resolve when `git push .` runs hooks from inside `.git`).
   - **Scope is the repository identity recorded at install** (git common dir + root commit hashes), never `CLAUDE.md` content and never HEAD: a merge that deletes `CLAUDE.md` or an orphan HEAD cannot switch the guard off. An update with an all-zero old value (`branch -f`, deletions) is judged from the ref's real current tip.
   - `pre-commit` on main/master: staged set non-empty and entirely companion; detached HEAD, unborn main and `--allow-empty` refused.
   - `reference-transaction` (state `prepared`) judges EVERY update of `refs/heads/main|master`, by any route: allowed only for (a) a two-parent merge whose first parent is the old tip, second parent on a local non-main branch, tree equal to `git merge-tree --write-tree` (a real `merge --no-ff`), or (b) a fast-forward made only of single-parent companion commits; deletion, creation, rewind, cherry-pick, revert, am, rebase, pull, fast-forward of code, `commit-tree` + `update-ref`, `branch -f`, `push .` abort. `pack-refs`/`gc` pass.
   - **Companion allowlist** (one definition, `scripts/hooks/rules_common.py`): journal fragments, ledger, journal, anthology, lessons, field notes, active sprint, roadmap, decision register, archive, performance log and data, reviews, research; plain 100644 files of data/prose extensions only, <= 2 MB, safe path shape; no symlinks, gitlinks, executables, mode changes or dotfiles. The 56 existing `.py` files in those dirs stay; new or modified ones ride a branch.
   - **Install location and integrity (amended 2026-10-05 after review round 3):** the installer COPIES the hook files from main's tip (`git show main:<path>`, blob hashes verified) into `<git-common-dir>/blarai-hooks/{githooks,hooks}` and sets `core.hooksPath` to that absolute directory, so no branch checkout in any worktree can change or remove them. `<git-common-dir>/blarai-install.json` records the identity, every file hash, the interpreter (absolute path + hash) and the main commit copied; the shims verify the installed files against that record (`_lib.sh` first, before sourcing it) and run the recorded interpreter as `python -I -S -B`. `--update` re-copies after a legitimate change on main (logged); `--check` fails if files differ from the record, are missing, or differ from main's tip; `--status` says in plain language whether protection is ON and which three facts would turn it off.
   - Fail closed everywhere; override `BLARAI_GIT_RULES_OVERRIDE=<reason>` in the process environment (logged; operator-set).
2. **Blanket staging and attempts to disable the hooks are blocked by a best-effort text guard**: a Claude Code PreToolUse hook (`scripts/hooks/git_rules_guard.py`, wired by `.claude/settings.json`, fail-closed): `add -A/-u/.`, `commit -a`, wrapper and expansion forms, `--no-verify`, `core.hooksPath` changes, `--uninstall`. It is a help, not a boundary. It also refuses, before git touches any file, `git merge` on main without `--no-ff`, `--ff-only`, `pull`, `cherry-pick`, `revert`, `rebase`, `am` and `reset --hard/--keep` (these would otherwise fail only at the ref update and leave files changed); a blocked update names `git reset --merge`.
3. **Traceability:** `enforces-rule:` markers in the hook modules feed `rules-corpus.yaml` and the gap list.
4. **Process rule:** work lands on main only by `git merge --no-ff <branch>` (never fast-forward); conflicts are resolved by merging main into the feature branch first.

## Alternatives considered

- **(a) Text/command guard only.** Rejected: parser differential; every round found new bypasses. Kept only for staging, where nothing better exists.
- **(b) Git hooks only.** Rejected: no hook on `add`; `--no-verify` skips pre-commit; `.git/hooks` is unversioned. Chosen: versioned hooks via `core.hooksPath` plus reference-transaction (which `--no-verify` does not skip) plus the text guard for staging and for `--no-verify` itself.
- **(c) Server-side protection / pre-receive.** Rejected for now: no hosted remote is in the loop (the public mirror is an unrelated history patched via a temporary worktree) and the project is local-first. Can be added for the mirror later.
- **(d) File-system permissions or ACLs.** Rejected: the agent runs as the operator; denial needs a separate account. The three-account design (#1689) is the long-term answer for the coder, not for interactive sessions.
- **(e) Signed commits.** Rejected: a session with key access signs anything; proves origin, not intent.
- **(f) Claude Code deny rules on `Bash(git commit:*)`.** Rejected: text patterns again, and it would block the legitimate merge ritual.
- **(g) Do nothing, rely on discipline.** Rejected: the rule was already in CLAUDE.md and failed by memory.
- **(h) A bare "gatekeeper" repository** where sessions push and only a gatekeeper process updates main. The strongest option; a topology change. **Not chosen now; recorded as the next step.**
- **(i) Relative `core.hooksPath` / PATH-resolved python / no integrity check.** Rejected on evidence: `push .` skipped the hooks; a planted `python` and `PYTHON*` variables took the guard over; an edited `_lib.sh` ran unverified.
- **(j) Hooks run from a checkout's `scripts/githooks`, scope from `CLAUDE.md`, integrity against HEAD.** Rejected on evidence (round 3): a checkout on a branch without the hooks turned every hook OFF repo-wide, a checkout on a guard-edit branch blocked every merge, and a merge that deleted `CLAUDE.md` unscoped main. Replaced by the installed copy + record described above.
- **(k) Harden the hooks with the TPM (a signed hook manifest). NOT ADOPTED. The reasons are the session's reasoning, recorded here as the session's call (the LA said it is the session's to make).** (1) A TPM key cannot be copied off the machine, but it can be USED by any process running as the same OS user: ADR-018 states the boundary itself ("TPM-signing defends at rest, not against an attacker with code execution on the host as the BlarAI user (who could ask the TPM to re-sign)"), and `shared/security/tpm_signer.py` is software-invoked CNG signing with a non-exportable key and no presence requirement, so a session could sign a tampered hook manifest unless the key's authorisation policy demanded something the session lacks (a human-present ceremony). (2) The verifier, the hooks and the install record under `.git`, is writable by the same user, so a signature would not protect the checker. (3) The rule's real failure mode was accidents and drift, which hash pinning and git-native hooks cover; a hostile session needs a privilege boundary (a separate account: #1689, #775), not a signature. (4) Cost: a ceremony per legitimate hook change and a recovery mode, the brittleness the LA cited on 2026-07-15 when declining PCR sealing and measured boot (tickets #103-#106 and #627 closed WON'T-DO). (5) TPM signing (`tpm_signer.py`, `require_signed_manifest=true`) is the signing tier the LA kept, not the declined sealing / measured-boot tier (`tpm_sealer.py` is DEK wrapping for ADR-025), so adopting it would not reopen that decision: it is simply not worth it here. **Revisit triggers:** sessions run non-elevated or under a separate account, when an administrators-only ACL on the installed hooks folder (outside the user-writable tree) is the cheaper and stronger hardening, and a TPM-signed manifest becomes meaningful only if its use is gated by a human-present ceremony. The ACL idea belongs in the three-account notes (#1689): to be carried into ADR-046's consequences, which is not on this branch.

## Consequences

- **The `--no-ff` rule.** Fast-forward merges to main are refused; the merge commit is the evidence of a reviewed landing. Companion commits (journal, ledger, reviews) go on main directly, staged in a separate call from the commit.
- **Install step.** One time per clone, from any checkout (hooks come from main's tip): `python scripts/install_git_hooks.py`, then `--check` and `--status`; `python scripts/prove_commit_protection.py --live --i-am-the-lead` proves it end to end in a throwaway repository. It records the identity, hashes and interpreter and chains any previous hooks (the dirty-log post-commit hook keeps running). Not installed means OFF. After a legitimate hook change merges to main, run `--update --dry-run`: it stages main's tip ONCE into a unique temp folder inside the git common dir (a concurrent review cannot touch it) (every blob read from the one resolved commit, hash-verified) and prints a SANITISED review: the source commit with its subject, author and date; BASELINE, the installed files against the install record (a file whose hash differs is flagged DRIFT, MISSING or UNRECORDED, and an unreadable record counts as drift); PROPOSED CHANGE, the installed files against the staged copy as a unified diff in which every non-printable and non-ASCII character is shown as an escape (`\xNN`, `\uNNNN`), carriage returns as `\r`, a long line CONTINUES on `[cont]` lines and is never cut (every byte is shown; a changed file whose review output passes 64 KiB, or 256 KiB in total, is refused with exit 4 and the operator is told to review the file by hand), and each changed file's byte length and sha256 are printed; the added, removed and case-renamed files; the interpreter pin (resolved real path, `pyvenv.cfg` sha256, base interpreter path with its git hash and sha256, all recorded and re-verified by `--check`; the hooks themselves run the BASE interpreter by its recorded full path, never the venv launcher, so `pyvenv.cfg` is irrelevant to them); the previous hooks path that is chained to, with the sha256 of every hook file in that folder (`--check` and `--status` compare the config key and the mirror file with the record: a mismatch is DEGRADED, not ON); every drifted installed file with its sha256; and a DIGEST over the source commit, the sorted `path:sha256` of every file to install and all those facts, with the exact lines it covers printed under DIGEST COVERS. Names that differ only in case, and any file in `scripts/githooks` outside the allowlisted hook names (it would become a live git hook without the shim's checks), are refused with exit 4. A changed file containing NUL, ESC, a bidi control or non-UTF-8 bytes is refused (exit 4) whatever flags are given. The lead reads that output: this reading is the review on which the guard's strength rests. Applying is `--update --reason "<why>" --approve <digest>` (plus `--accept-drift` when drift was shown): the installer stages main afresh, recomputes the digest, refuses on any mismatch (exit 3, nothing changed: main moved or a blob changed after the review) and installs FROM that staged copy, re-hashing it just before the swap; reason, digest, diff stat, drift and source commit go to the install log. The swap builds the new copy in a unique sibling temp folder in the git common dir and verifies its hashes, keeps the old folder as `blarai-hooks.prev`, moves the record aside, switches the files in one by one with `os.replace` (no installed file is ever deleted first), and writes the new record last. On any failure the old files are restored by the same atomic replacement and VERIFIED by comparison before the old record is put back; if the restore cannot complete (a file stays locked) the record stays aside and the install FAILS CLOSED: with the record absent every shim refuses every commit and main update until `--update` succeeds, and `.prev` holds the previous state. Crash and power-cut states are the same latch. A directory cannot be renamed over a non-empty directory (POSIX) and not at all over an existing one on Windows, so rename-old-then-rename-new would leave an instant with no hooks; per-file replacement keeps `core.hooksPath` pointing at the same folder with hooks in it throughout, and every intermediate state (record absent, files not matching the record) refuses commits on main. Worst case is refusing main for the length of the swap (or until `--update` after a crash), never allowing it; tests inject a failure at EVERY step of the swap in three modes (one transient failure, every failure from that step on, a power cut) and a lock on each hook file, and assert a code commit on main is refused each time, plus a commit loop from another process during `--update`. **Interpreter enforcement (review round 2):** `_lib.sh` runs the recorded base interpreter only after verifying its sha256 itself (the system `sha256sum` through `command -p`, which never consults the caller's PATH, with no fallback tool a caller could choose; no verifier means refuse), and a guard ALLOWS only by printing `BLARAI-GUARD-OK <sha256 of the guard script it ran>`, which the shim recomputes independently: an exit 0 without that exact token (a fake python, a replaced guard) is a refusal. What this does NOT stop: an attacker who can rewrite the record's interpreter fields AND supply a program that computes the token (it can read the guard file), or one who rewrites the installed shims together with the record; the base interpreter's own DLLs and standard library are not hashed. The three-account design (#1689) is the structural answer. Before the first install save `git config --get core.hooksPath` to a file. The ORIGINAL hooks path is kept in `blarai.originalhookspath` (written once, never overwritten while set), which survives loss of the install record: the installer never records its own folder as the "previous" path, `--update` rebuilds a lost or damaged record from main's tip and that key (logged), and `--uninstall` restores it exactly or refuses rather than guess. A corrupted record or interpreter field blocks commits on EVERY branch and worktree until `python scripts/install_git_hooks.py --update` runs (fail closed, by design); `--status` and every recovery message name `--update` when the hooks are installed and the plain install only when not.
- **Residuals** (in `git-rules-guard.md`): not installed, or `core.hooksPath` / the files inside `.git` edited by someone with shell access (`--check` and `--status` show it, nothing prevents it); editing BOTH shims in the installed copy; programs that run git internally; the install record is itself unsigned; Edit/Write-tool edits of `.git` files are not seen by the text guard; `--no-verify` defeats pre-commit (reference-transaction and the text guard still hold); the text guard stays bypassable. A blocked merge may leave files changed: `git reset --merge`. **Honest statements (review, 2026-10-05):** (1) the record and the copies live in `.git`, which a model can write: pinning catches drift and single-file edits and any record that disagrees with the repository blocks main, but it is NOT a boundary; (2) `--update` installs whatever main holds, so the guard is only as strong as the review of changes to the hook files: the installer shows a sanitised two-baseline review and binds the approval to a digest over everything it will install or accept, but the reading is the lead's; (3) during install/`--update` every intermediate state refuses main (tested), so there is no unprotected window; (4) `--i-am-the-lead` is a typed flag, harmless because `--live` only reads. A missing or unreadable record blocks every commit and main update (stricter than the allowed pass-through for "no record at all", which is not implemented).
- **Cost.** About 4 s per commit on main on this machine (each git process spawn is ~0.3 s on Windows). The new tests add roughly 25 minutes to the standing gate; mutation tests are opt-in (`-m slow`).
- **Re-visit triggers:** a bypass of layers 1-2 observed in use; any need to serve a hosted remote (then add pre-receive); starting the three-account work (#1689); a session that routinely needs the override. Any of these reopens option (h).
- **What this does not settle:** whether (h) should be built. The cost/benefit is the LA's to weigh when a residual bites.
