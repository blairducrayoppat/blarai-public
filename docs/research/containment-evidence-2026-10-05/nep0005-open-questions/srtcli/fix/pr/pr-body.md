TITLE: windows: `wfp status` reads `partial` when the set is incomplete, so a plain `install` repairs it

`srt-win wfp status` read `installed` whenever one `block-user` filter existed under the sublayer. With one address family's block filter deleted, the set still read `installed`, `srt-win install` returned early with "already installed (... filters=3); no changes", and that family stayed open. With the IPv4 block deleted, `initialize()` throws `wfp_fence_inactive` with "Re-run `srt-win install`", and the re-run changes nothing. #359 covers the case where every filter is gone (`wfp verify` fails closed at `initialize()`); this is the partial case, where one block is gone and the other still stands.

- `filter_status` reads `installed` only when a `block-user` and a `permit-loopback-user` exist at both the v4 and v6 connect layers; `partial` when some of those are present; `absent` when none. Extra filters under the sublayer are still ignored, as the comment says. `port_range` is now read from the first permit tag rather than the last, which is what the comment already said
- `install`: the early return applies only to `installed`, so a `partial` set falls through and is re-added. The config-drift refusal (exit 13 without `--force`) now applies to a `partial` set too; a partial set with no permit left has no range to compare, so it falls through instead of refusing with `port_range=<unknown>`. Both messages name the state
- `WindowsWfpStatus` gains `partial`, and `checkWindowsDependencies` names an incomplete set in its message, with a fake-stdout test beside the existing ones
- Unit test `fence_parts_state`, with `note()` reading the layer names from `ALE_LAYERS`. `cargo test`, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, both `tsc` configs, eslint over `src/` and `bun test test/sandbox/winsrt.test.ts -t checkWindowsDependencies` (3 cases, the new one included) pass locally
- Measured on one Windows 11 build (26200) with srt-win's own `install` under a test sublayer, 3 of 3 passes per state, with the status change alone (before the drift-refusal and `ALE_LAYERS` edits above): with one block filter deleted, or both permit filters deleted, `wfp status` read `partial`; a plain `install` then exited 0, `wfp status` read `installed` with `filters=4` and all four roles present, and `wfp verify` read `blocked` on both 127.0.0.1 and [::1]. Not tested: a partial set with a different requested range or user name (code reading only), other Windows builds, a restart with a half-set in place, a non-elevated `status`
