# R1 — Q2: The deep-integration path (brief seam 10)

Where could a third-party governor live on Windows 11 so that agents cannot go around it, and what does each location require?

Study date: 2026-09-17. Machine of record: Windows 11 Pro 25H2, build 10.0.26200 (from RULES.md). Evidence grade for this whole report: **REPORTED**. I ran nothing on the machine; every claim below comes from a document read on the public web, and each carries its source and the date the source shows (`ms.date` for Microsoft Learn pages, post date for blogs). Where a Learn page also shows a later `updated_at`, I give both. Secondary sources (trade press, vendor blogs, personal blogs) are marked *(secondary)* and are discounted against Microsoft's own artefacts.

Web-search budget note: the session's shared search quota ran out partway through. Everything after that point came from direct fetches of known URLs; three guessed URLs (a Learn page for "Agentic Processes", the Windows 11 26H1 what's-new page, and the Visual Studio Magazine Build 2026 article) returned 404/403 and are recorded as not verified.

## 0. Outcome first

**Can a third party register as the authorising component in Windows's Model Context Protocol (MCP) layer today? No.** The Windows on-device agent registry (ODR) and its MCP proxy are documented as Microsoft's gateway that performs "authentication (verifying the MCP client…), authorization (enforcing permissions and policies), and auditing (logging every interaction)" (Windows Developer Blog, 2025-11-18). Across every Microsoft page read for this report — the MCP overview (ms.date 2025-12-06, updated 2026-06-04), containment (2025-11-11), server registration (2025-08-12), package-identity registration (2025-11-10), manual registration (2025-08-12), host quickstart (2025-08-12), the `odr.exe` tool page (2025-10-31), the WindowsAI Policy CSP (2026-06-22, updated 2026-08-18), and the two Build 2026 developer-blog posts (2026-06-02) — there is **no policy-provider interface, no third-party authoriser slot, no documented event/ETW channel for the proxy, and no consumer-editable policy surface**. A third party can be a *server* (an "agent connector") or a *host* (an app that calls `odr.exe`). It cannot be the thing that says yes or no.

Five findings that shape the rest:

1. **The native MCP layer is Insider-only and not on the study machine.** Every MCP-on-Windows page names "Windows build 26220.7262 or higher" as the prerequisite; the machine is 26200 (25H2 GA). The WindowsAI CSP still tags every agent policy "Windows Insider Preview" and "❌ Pro / ✅ Enterprise / ✅ Education" as of ms.date 2026-06-22. No GA date is documented anywhere read. (REPORTED; not measured.)
2. **Microsoft's own agent-governance product does not use a deep OS seam.** Defender for Endpoint's "AI agent runtime protection" (Preview; ms.date 2026-09-16) inspects Claude Code, Codex CLI, GitHub Copilot CLI and the Copilot app through the *vendors' own hook interfaces* (user-prompt / pre-tool / post-tool), and falls back to network inspection (OpenClaw) for agents without hooks. That is the same seam any third party can occupy. Microsoft's enterprise advantage is tamper protection, the Defender portal, and licences (Plan 2 / M365 E5 / Agent 365 / M365 E7) — not a private OS hook.
3. **The only documented "third-party policy provider" hook in the Windows AI stack is the Recall Data Loss Prevention (DLP) Provider API** (ms.date 2025-12-01): an Authenticode-signed DLL loaded in-process by `AIContext.exe`, returning Allow / AuditAndAllow / Warn / Block per capture, selected by the `SetDataLossPreventionProvider` policy (Enterprise/Education only). It is the existence proof that Microsoft will adopt a provider-DLL contract for a policy decision — and the template a specification proposal should copy.
4. **Every route with real enforcement power that is open to an individual today is a *launcher* route** (restricted token, AppContainer, Windows Sandbox `.wsb`, Microsoft Execution Containers (MXC), job objects) or a *vendor-hook* route. Both are bypassed by starting the agent some other way; neither is a location the agent cannot go around. The only routes that agents cannot go around (kernel minifilter/WFP callout, ELAM/PPL, WSC, WESP) require a company with an EV certificate at minimum and Microsoft Virus Initiative (MVI) membership for anything AV-shaped — and Microsoft's stated direction (Resiliency Initiative, 2025-06-26; 2025-11-18) is to move security vendors *out* of the kernel.
5. **Distribution is cheap and open; identity is the only real cost.** Store registration is free for individuals and companies (Learn, ms.date 2025-09-17; blog 2026-05-07); winget is a free pull request; Azure Artifact Signing (formerly Trusted Signing) is open to self-employed individuals in the US/Canada and organisations in 12 regions with no minimum organisation age (Microsoft employee answer 2026-08-17), at a widely reported ~US$9.99/month *(secondary)* — the official price page shows placeholders.

## 2. Route-by-route evidence

### 2.1 Windows's native MCP layer (route 1 in the brief; table rows 7–8)

**What it is (artefact text).** "MCP on Windows provides the Windows On-device Agent Registry (ODR), a secure, manageable interface to discover and use agent connectors from local apps and remote servers" (MCP overview, ms.date 2025-12-06, updated 2026-06-04, still headed "Some information relates to prereleased product"). The Ignite blog (2025-11-18) describes the proxy: "All communication between agents and agent connectors from the Windows on-device registry will go through the MCP proxy, a trusted gateway… The proxy handles authentication (verifying the MCP client…), authorization (enforcing permissions and policies), and auditing (logging every interaction for compliance)."

**Extension points found — none for a governor.**
- *Server side:* register through an MSIX `uap3:AppExtension` named `com.microsoft.windows.ai.mcpServer` with a `.mcpb`-format `manifest.json`; the `_meta.com.microsoft.windows` block must carry `static_responses` for `initialize` and `tools/list` so the registry can answer tool listings without starting the server (mcp-windows-identity, ms.date 2025-11-10). Production requires "a certificate that is part of the Microsoft Trusted Root Program". Contained servers run "in a separate Windows session using a separate agent user account"; they can "access the internet", read/write the agent's own files, run executables in the agent session, and reach user files only after consent — and **"Permissions to user files are granted for the host and not per server"** (containment, ms.date 2025-11-11). Unpackaged servers and `.mcpb` bundles are only reachable after the user turns on "Settings > System > Advanced > AI components > Reduce protections for agent connectors".
- *Host side:* the quickstart (ms.date 2025-08-12) shows a host app doing `odr.exe list`, parsing JSON, then opening a plain stdio transport to the server command — i.e. the proxy is not visibly in the host's code path in the sample; the package-identity requirement for hosts "is not enforced in the public preview release but it will be in the stable release".
- *Policy side:* WindowsAI CSP (ms.date 2026-06-22) — `AgentConnectorAccessPolicy` ("Allow the following MCP Server/Host connections. The format of this list will be a JSON string that adheres to the example schema at https://go.microsoft.com/fwlink/?LinkId=2363700"), `AgentConnectorMinimumPolicy` (0 User in control / 1 Restricted / 2 Bypass), `AgentConsentDuration` (default 720 h), `ConfigureAgentConnectors`, `DisableAgentConnectors`, `DisableRemoteAgentConnectors`, `DisableAgentWorkspaces`, `OnDeviceRegistryLoggingLevel` (0 Error+ / 1 Information+ / 2 Debug+). Every one is Device-scope, "❌ Pro ✅ Enterprise ✅ Education", "✅ Windows Insider Preview". The fwlink for the JSON schema redirected to the CSP page itself on 2026-09-17 — **the schema is not published at the advertised location** (not verified further).
- *Audit side:* `OnDeviceRegistryLoggingLevel` proves a log exists; no channel name, ETW provider, or file path is given in any page read. `odr.exe` has `--verbose` and `mcp configure <server id>` (odr-tool, ms.date 2025-10-31) — what `configure` can set is not documented on that page.
- *App Actions / Agent Launchers:* "Agent Launchers are built on the Windows App Actions framework" and registered through the ODR; they are entry points for interactive agents, "not for background services or silent automation" (agent-launchers, ms.date 2025-01-05, updated 2025-12-12). No policy hook.
- *Windows AI Foundry:* the Ignite blog lists Windows ML GA and new APIs; nothing agent-governance-related.

**Shipped status as of 2026-09-17.** Public preview since Insider Dev/Beta build 26220.7262 (the prerequisite on every page; Windows Central *(secondary)* dates MCP support to 26220.7344 in Dev and Beta). The Ignite blog (2025-11-18) lists MCP support, the ODR, and the File Explorer/Settings connectors as **public preview**, Agent Workspace as **private preview**, and says "Policy support for MCPB will be available in the coming months." No page read announces GA; the CSP page (updated 2026-08-18) still carries the Insider banner. The Build 2026 developer blog (2026-06-02) does not mention GA of the MCP layer. Insider posts of 2026-06-08, 2026-06-19 and 2026-07-31 carry no agent items. **On the study machine (26200) none of this layer is expected to exist** (REPORTED from build prerequisites; not probed).

**Verdict for a governor.** A third party can *be governed* (as a server) or *do the governing of its own agent* (as a host). It cannot be the proxy's authoriser or a policy provider; the policy surface is enterprise-MDM only; and Claude Code / Codex / Copilot CLI reach their MCP servers without the ODR, so the layer does not sit on their path at all.

### 2.2 Agent workspace and agent accounts (brief route 2; table row 9)

The Windows Experience blog (2025-10-16) defines the agent account ("a separate standard account on your device is provided to agents when acting on your behalf, enabling agent-level authorization and access control") and the workspace ("a contained environment where agents can work in parallel with a human user"). The Support article (updated 2025-12-05) says the toggle enables agent accounts, agent workspace, and read/write to Documents, Downloads, Desktop, Videos, Pictures, Music; per-agent permissions live at "Settings > System > AI Components > Agents > [Agent name] > Files" with Allow always / Ask every time / Never allow; per-agent management needs build 26100.7344+. The only named consumer is Copilot Actions (Windows Insiders, Copilot Labs). The Ignite blog (2025-11-18) calls the workspace "private preview" and says policy exists to "enable/disable agent workspace at device level" (`DisableAgentWorkspaces`, Enterprise/Education, Insider). **Third-party agent enrolment, third-party scope-setting, and third-party observation of scopes are not documented anywhere read.** Build 2026 (2026-06-02) adds "Windows assigns agents a local ID or a cloud provisioned identity backed by Entra" and Intune-gated session isolation — again with no third-party enrolment API named.

A search-result snippet (source not recoverable after the quota ran out) claimed a preview "Agentic Processes" feature that "lets authorized components assign opaque agent identifiers to process tokens". A targeted re-read of the 2026-06-02 security blog found none of those phrases, and a guessed Learn URL returned 404. **Treat as unverified.** If real, "authorized components" is the phrase to chase: it would decide whether a third-party governor can ever read or set agent identity on a token.

### 2.3 Security-product registration: WSC and MVI (brief route 3; rows 12, 14)

- **Categories.** `WSC_SECURITY_PROVIDER` (ms.date 2018-12-05) enumerates FIREWALL, AUTOUPDATE_SETTINGS, ANTIVIRUS, ANTISPYWARE, INTERNET_SETTINGS, USER_ACCOUNT_CONTROL, SERVICE; "As of Windows 10, version 1607, WSC continues to track the status for antivirus, but not for anti-spyware." A Microsoft engineer's blog (textslashplain, 2026-08-31 *(secondary)*) confirms third parties register only as "Virus and Threat Protection" or "Firewall" products and that the APIs are "not fully public, and only callable by members of the MVI program". A red-team write-up (ipurple.team, 2026-09-09 *(secondary)*) describes the private `IWscAVStatus::Register` path requiring a PPL-Antimalware caller and a signed product binary, and Defender flipping to `PassiveMode`. **A governor that is not an antivirus or firewall has no category to register in.**
- **MVI eligibility (Learn, ms.date 2024-12-02, updated 2026-09-10).** Verbatim criteria: (1) "Your commercially available security solution must provide real-time protection that detects, prevents, and remediates malicious software"; (2) you develop and distribute Windows-compatibility updates; (3) "active in the antimalware industry with a positive reputation, shown by participation in industry conferences, membership in industry organizations, or reviews in reports like AV-Comparatives, OPSWAT, or Gartner"; (4) NDA; (5) programme licence agreement; (6) active in the programme; (7) "requires use of Trusted Signing"; (8) certified within 12 months by one of AV-Comparatives, AVLab, AV-TEST, MRG Effitas, SE Labs, SKD Labs, VB100, West Coast Labs, with minimum scores listed. "Not all applicants are accepted." Applications via a Forms link, "reviewed monthly". Not stated: revenue, customer count, engine independence, VirusTotal participation, AMTSO membership (AMTSO appears only in trade press). Scale *(secondary, Field Effect PR 2025-11)*: "under 100 members in 20 years".
- **2025–2026 changes.** MVI 3.0 effective 2025-04-01 requires partners to "test incident response processes", follow Safe Deployment Practices, use "deployment rings" and monitoring (Resiliency blog 2025-06-26; Ignite security blog 2025-11-18). The **Windows endpoint security platform** went to "a set of MVI partners" as a private preview in July 2025 (Bitdefender, CrowdStrike, ESET, SentinelOne, Sophos, Trellix, Trend Micro, WithSecure named); as of 2026-03-02 Cybersecurity Dive *(secondary)* wrote "It remains unclear when Microsoft will publish APIs that vendors can use to build user-mode software"; Microsoft's Resiliency Initiative page (fetched 2026-09-17) says only that WESP "enables Windows protection and security solutions to run outside the kernel". The Artifact Signing quickstart (ms.date 2026-05-21) exposes a "Program Type" field to "change… only if you're enrolled in the Windows endpoint security platform program" — the platform is real, gated, and undocumented publicly.

### 2.4 ELAM, PPL, ETW-TI, kernel drivers (brief route 4; rows 11, 13)

- **ELAM.** "Microsoft requires that Early Launch Antimalware vendors be members of the Microsoft Virus Initiative (MVI)… Your submission will fail if you are not an MVI member" (ELAM prerequisites, ms.date 2017-04-20, updated 2025-07-18). Submission: HLK validation, kernel signing policy, Partner Center; "Each driver .sys file must be code signed by Microsoft, using a special certificate indicating that it is an Early Launch AM Driver"; single binary; 0.5 ms callback, 128 KB footprint (ELAM submission, ms.date 2017-04-27).
- **PPL anti-malware-light and ETW-TI.** The 2026-06-19 deep dive *(secondary)* states the kernel checks `PsProtectedTypeProtectedLight` + `PsProtectedSignerAntimalware`, that the service binary must chain to the same ELAM certificate (`InstallElamCertificateInfo`), and that `Microsoft-Windows-Threat-Intelligence` delivers cross-process reads/writes, thread-context changes, executable allocations, APC queuing, driver loads. "No pathway exists for non-MVI vendors to legitimately access this provider through documented means." Microsoft's own pages read do not document ETW-TI at all.
- **Minifilter / WFP callout.** Altitude by e-mail to fsfcomm@microsoft.com with company name, product URL, load-order group (e.g. "FSFilter Activity Monitor", "FSFilter Content Screener"); "Allow Microsoft 30 business days"; no fee stated (ms.date 2024-12-18). Hardware Developer Program registration (ms.date 2026-08-11): organisation Entra tenant global admin, legal contact, D-U-N-S or manual company details, questionnaire, and "You must have an extended validation (EV) code signing certificate… You only need the certificate to register". Attestation signing (ms.date 2025-07-15): EV-signed CAB, Partner Center, Microsoft re-signs; "Attestation signed drivers that target retail audiences aren't published on Windows Update"; no fee stated. Code-signing requirements (ms.date 2025-05-29, updated 2026-08-26) list Certum, DigiCert, GlobalSign, IdenTrust, Sectigo, SSL.com as EV sources; "Azure Trusted Signing currently does not support EV certificates, nor does it support signing Windows drivers" *(secondary, sslinsights 2026)*. Direction: "significant reduction in code that runs in kernel mode" across AV, networking, camera, USB, printer, battery, storage, audio driver classes (Ignite security blog 2025-11-18).

**What a third party can still do today:** a company with an EV certificate can ship attestation-signed minifilter and WFP callout drivers to Windows 10/11 clients without HLK and without MVI. Those drivers can veto file and network operations and cannot be bypassed from user mode. They cannot obtain ELAM/PPL protection, cannot register in WSC, and are on the wrong side of Microsoft's stated trajectory.

### 2.5 Application-control levers with no programme (brief route 5; rows 2–5)

- **App Control for Business.** `CiTool` ships in Windows 11 22H2+: `--update-policy`, `--remove-policy`, `--list-policies`, `--refresh` (ms.date 2024-09-11). Feature availability (ms.date 2026-03-29): "App Control PowerShell cmdlets aren't available on Home edition, but policies are effective on all editions"; multiple/supplemental policies since 1903; rule types publisher, path (with runtime user-writeability check), hash, managed installer, ISG reputation, AppId tagging; enforceable file types .sys .exe .com .dll .msi .ps1 .vbs .js .appx. Security caveats verbatim (design page ms.date 2025-03-09): "Any process running as administrator can replace or remove unsigned policies without consequence"; "unsigned supplemental policies can alter the 'circle-of-trust'…"; mitigation is signed policies on UEFI. **No per-action semantics: it decides which files may execute, never what an executing agent may do.**
- **AppLocker** (ms.date 2026-03-29): "not considered a defensible Windows security feature"; per-user rules; included in all editions.
- **Windows Sandbox `.wsb`** (ms.date 2026-03-29): vGPU, Networking, MappedFolders (read-only flag), LogonCommand, AudioInput, VideoInput, ProtectedClient (AppContainer isolation of the RDP session), PrinterRedirection, ClipboardRedirection, MemoryInMB; requires the optional feature (RULES.md forbids enabling reboot-requiring features on the study machine).

Processes are contained only when launched through `wxc-exec.exe` / `lxc-exec` / `mxc-exec-mac`. Build 2026 blog (2026-06-02): "Developers define what to constrain in their apps and agents, and Windows enforces those constraints consistently at runtime through MXC"; partners Hermes, Manus, NVIDIA, OpenAI, OpenClaw; GitHub Copilot CLI adopted process isolation. - **Windows Firewall / WFP user-mode.** `INetFwRule` properties ApplicationName, ServiceName, Direction, Action, Remote/LocalAddresses, Ports, Protocol, Profiles; "All configuration changes take place immediately" (ms.date 2018-12-05). WFP user-mode API can add permit/block filters without a callout driver; callouts are needed only to inspect or modify payloads (WFP start page, ms.date 2018-05-31).

## 3. Tiers, with cost and time ranges

Assumptions: one developer or a small team; Windows 11 target; costs in US dollars at 2026 list prices from the sources above (secondary where marked); "time" is calendar time to unlock the route, not to build the product.

**(a) Open to an individual or small company today, no programme.**
Routes: vendor hooks (row 1); launcher containment incl. MXC (row 2); AMSI provider (row 3); Firewall/WFP user-mode (row 4); WDAC/AppLocker (row 5); observation feeds (row 10); registering as an MCP server/host on Insider builds (row 7); Store, winget, direct download (§2.6).
Cost: **$0 – ~$450/yr** (a code-signing identity: Artifact Signing ~$9.99/month if in the US/Canada, else an OV certificate ~$220–440/yr; Store and winget free). Time: **days to ~4 weeks** (identity validation 1–20 business days; Store company verification 2–5 business days; winget PR days).
Honest limit: nothing in this tier is a place an agent cannot go around. Enforcement is exactly as strong as the user's decision to launch the agent through you or to keep your hook config intact.

**(b) Needs a company plus a certificate.**
Routes: attestation-signed kernel minifilter / WFP callout (row 11); Recall DLP-style signed provider DLLs if Microsoft ever adds an agent-policy provider (row 6 as precedent); Company Store account for financial features.
Cost: **~$300–$700/yr EV certificate** *(secondary)* + a legal entity + Entra tenant + engineering; no Microsoft fee stated for Hardware Developer Program registration, attestation signing, or altitude allocation. Time: **2–4 months** (EV vetting 1–4 weeks; Partner Center approval and questionnaire; altitude 30 business days; driver signing turnaround days) before the first signed build; kernel driver engineering and HVCI/Memory-Integrity compatibility are on top.
Honest limit: this buys the only true "cannot go around" seam, on the side Microsoft is dismantling; no PPL protection, so a local admin can stop the service.

**(c) Needs MVI / ELAM / a Microsoft partnership.**
Routes: WSC registration (row 12); ELAM + PPL + ETW-TI (row 13); WESP private preview (row 14).
Cost: the price of *being an antivirus company* — an independently certified real-time AV product (lab certification fees not verified), NDA, programme licence, Trusted Signing, MVI 3.0 safe-deployment obligations. Time: **1–3 years** from a standing start; applications reviewed monthly; WESP by invitation only. A governor that does not "detect, prevent, and remediate malicious software" does not meet criterion 1 and has no WSC category.

**(d) Only Microsoft.**
The MCP proxy's authorisation and audit; the consent dialogs; agent accounts and workspace enrolment; agent identity on tokens; the WindowsAI policy semantics and SKU gating; Smart App Control; SmartScreen reputation; Defender's tamper-protected hook enrolment; Agent 365 / Entra Agent ID; the Store's certification decisions.

## 4. Where a specification, not a product, is the only thing a third party can offer

1. **A policy-provider contract for the MCP proxy and the agent workspace.** Today authorization is Microsoft's alone and the enterprise policy is a static JSON allowlist whose schema is not even published. The precedent Microsoft has already shipped — the Recall DLP Provider API: an Authenticode-signed DLL, loaded in-process, answering `Allow / AuditAndAllow / Warn / Block` per query with process, window, file and label context, selected by one Group Policy string — is the exact shape a third party should propose for per-tool-call decisions in the proxy (context: host identity, server identity, tool name, arguments, agent account). Nothing a third party ships can occupy that slot until Microsoft creates it; the only lever is a written contract Microsoft could adopt, ideally carried under an existing vendor-neutral banner (the OWASP Agent Control Standard or the MIT Agent Hooks contract named in the brief) rather than a company.

2. **A cross-vendor pre-action hook contract (the "AMSI for agent actions").** Microsoft's own enterprise product sits on the agents' vendor hooks, one bespoke interface per vendor. A third party cannot make Claude Code, Codex, Copilot CLI and the Windows ODR expose one interface; it can publish the interface — payload schema, block semantics, tamper-evidence expectations — and let Defender's dependence on those hooks do the persuading. This is the single place where a small actor's reach can equal a platform's, because the platform is already consuming the same seam.

A third, weaker candidate: a token-level **agent identity claim** (the unverified "Agentic Processes" item). If Microsoft is putting agent identifiers on process tokens, a spec for how *any* governor may read them (a `TokenInformation` class) and how Microsoft-signed launchers set them would let user-mode governors (WFP filters, minifilters, AMSI providers) key decisions on agent identity instead of executable path. Not pursuable until the primary source is found.
