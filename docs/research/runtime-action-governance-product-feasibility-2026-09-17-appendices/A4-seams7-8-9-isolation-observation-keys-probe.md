## Outcome first

1. **Observation (seam 8) is real, cheap to reach and useless for stopping anything.** Without a kernel driver, an admin-started Event Tracing for Windows (ETW) session on the three inbox kernel providers gave a process-start receipt (process id, parent id, full image path, integrity label, elevation — **no command line**), a network receipt (process id, local and remote IP:port — **no hostname, no URL, no content**) and a file receipt (process id, full file path, create options). Every receipt arrives after the fact. On this machine the three providers together wrote **290 MB of trace in 60 seconds** at the keywords chosen; the System process's CPU share roughly tripled in that minute (confounded, see below). A non-admin cannot do it: the session can be created by a member of Performance Log Users, but **enabling any of the three kernel providers is denied** — their security descriptors grant enable rights only to SYSTEM, LOCAL SERVICE and Administrators (measured from the registry). The Security event log offers nothing here: Process Creation auditing is off, command-line logging is off, Sysmon is not installed, and the 52 event-4688 records present are all boot-time artefacts. The EDR-grade provider (Microsoft-Windows-Threat-Intelligence) needs an anti-malware Protected Process Light backed by a Microsoft-signed ELAM driver, which only anti-malware vendors can obtain (reported).

2. **Isolation (seam 7) is the one OS seam a third party can actually operate today, and it is a blunt instrument.** AppContainer works from user mode with nothing installed: a 200-line Python script created a container, launched probes in it, and the OS denied the container's writes to the user's files, its reads of the user's profile, and its network access (until the `internetClient` capability was granted, after which HTTPS to example.com succeeded). The profile was deleted cleanly. The cost is the whole point: an agent in an AppContainer cannot see the person's files, credentials or tools — right for an unknown agent, wrong for the developer's coding agent, which is exactly the unpackaged Win32 kind (`claude.exe`, `copilot.exe` are plain executables, not MSIX packages) and therefore also outside Microsoft's Win32 app isolation unless repackaged. Token restriction alone (`runas /trustlevel`) only removes admin: the process kept a High label, lost all privileges but one, could not write Program Files or C:\Windows, and could write C:\Windows\Temp and the user's folders. Application control (WDAC/App Control for Business, AppLocker, Smart App Control) decides only *whether code may run*, never *what an action may touch*: WDAC is already enforcing four Microsoft policies on this consumer Pro machine and can take a third-party `.cip` via `CiTool` without any MDM; AppLocker has zero rules; Smart App Control is off and is Microsoft-operated with no third-party surface. Windows Sandbox is disabled and would need a feature enable plus a possible restart, so it was not run.

3. **Identity and keys (seam 9) work as-is on this machine and would on any Windows 11 with TPM 2.0 — but the TPM is a bottleneck, not a per-action signer.** Windows Hello reports `Available` (face and fingerprint devices present). The two BlarAI modules use only public, portable Windows surfaces (WinRT `UserConsentVerifier` through a C# helper; CNG `NCrypt` against the Microsoft Platform Crypto Provider through ctypes) with no hard-coded machine facts. A throwaway TPM ECDSA P-256 key signed in **77–94 ms median (warm handle)** and **131–157 ms median in the open-provider-open-key-sign-free pattern `tpm_signer.sign()` uses**; software ECDSA signs in **0.027 ms** — a 3,000–5,000× gap. A governor that wants a hardware-rooted receipt per agent action cannot ask the TPM for every one; it must sign a hash chain or batch heads.

**Cost at agent call rates (plain statement).** The TPM executes one command at a time. At ~80–95 ms per warm signature this chip delivers about 10–12 signatures per second at full occupancy, and the BlarAI open-per-call pattern halves that. A coding agent that emits tens of tool calls a minute could be signed per action, but a governor serving several agents, or one signing every file/network receipt from seam 8 (thousands per minute), cannot use the TPM per event. The workable shapes are: a software signing key whose private half is sealed by or derived under the TPM, signing every receipt in microseconds, with the TPM signing the hash-chain head on a timer; or a per-turn/batch signature. The 130–160 ms cold cost also matters for `tpm_signer.sign()` as written — a persistent key handle saves ~60 ms per call.
