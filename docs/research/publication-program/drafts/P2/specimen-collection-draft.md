# When two correct things collide

*A field catalog of composition failures from one small, heavily-instrumented local AI system — eight documented cases where two controls that were each individually correct interacted to produce a failure, each with the structural fix that shipped.*

---

On June 12th, 2026, this project's web-ingest feature was one command away from its first live use. Two of its security controls were about to meet for the first time. The first control arms an egress kill-switch at process entry: any network touch that is not on the allowlist trips it and re-air-gaps the machine. The second control is the egress door's anti-SSRF ordering (SSRF: server-side request forgery — tricking a server into fetching an internal address): the door resolves a URL's hostname *before* widening the firewall for it, so a hostname that secretly resolves to an internal address can be refused without the allowlist ever opening. Both controls are correct. I would defend either in review today.

Together, they were fatal. Under the armed kill-switch, the door's own DNS lookup of a not-yet-allowlisted host is itself off-allowlist network activity. The build journal recorded it the day it was found:

> Those two facts are individually correct and together fatal: under the armed guard, the door's own DNS lookup of the not-yet-allowlisted host is itself off-allowlist egress, so the guard trips the kill-switch on it.

The very first real fetch would have been denied — and would have tripped the alarm, air-gapping the machine into a state that needs a recovery ceremony. The door would have knocked and the house would have called the police on the door.

This piece is a catalog of eight of these. Not eight bugs — bugs are usually one wrong thing. Eight documented cases from one system where *two individually-correct mechanisms* composed into a failure neither could produce alone, each presented the same way: the setup (both controls, each defended), the collision, the root cause, the structural fix that actually shipped (with the commit), and the rule we took away.

## This failure class is old. The catalog is the contribution.

Nothing about the *phenomenon* here is new, and it matters to say so precisely. Pamela Zave and the feature-interaction community established decades ago that features which are individually correct do not, in general, compose correctly — it is the founding problem of that field, with a workshop series to its name (the Feature Interaction Workshop books, IOS Press). Charles Perrow's *Normal Accidents* (1984) made interactive complexity plus tight coupling a named cause of system accidents. Richard I. Cook's "How Complex Systems Fail" (1998) put "catastrophe requires multiple failures — single point failures are not enough" into every reliability engineer's vocabulary. In security specifically, the cryptographic-composition literature (Canetti's Universal Composability line of work) formalized the uncomfortable fact that secure components do not automatically yield a secure composition. And Kelly Shortridge and Aaron Rinehart's *Security Chaos Engineering* (O'Reilly, 2023) built a whole experimental methodology on the observation that security failures come from factors working in concert, not from single causes. Hillel Wayne's essay "Feature Interaction Bugs" is the best short modern statement of the class for working engineers.

So if the idea is thirty-plus years documented, what is left to add? Worked examples, at field strength. What I could not find anywhere in that literature is the middle layer between the abstract phenomenon and the methodology: a curated collection of *control-composition* failures — security and policy controls, the verification apparatus around them, and the substrate under them — from *one* fully-instrumented running system, where every specimen is documented as it happened (dated journal entries, commits, measured before/after numbers) and every specimen ends with a structural fix that actually shipped, checkable in a public repository. Zave's material is formal and telecom-rooted; Cook and Perrow are domain-general theory; the chaos-engineering books teach you how to run experiments; the postmortem collections (danluu's is the genre model) aggregate single incidents across many organizations. This is one system, eight specimens, all receipts.

One system is also the honest limitation. This is a single-project case study — n=1. These are the collisions we *caught*, on one architecture, with no way to estimate the ones we missed. The fixes are what worked here, not laws. Where I generalize, I say so and hedge it.

## The system, briefly

The specimens come from a personal research project: a long-term, local-first AI system built to run entirely on the owner's own hardware (a Windows 11 laptop with an Intel Core Ultra 7 258V, its integrated Arc 140V GPU, and 32 GB of RAM — local models on the OpenVINO GenAI runtime, no cloud anywhere in the model-inference path; the system's only network access is a single deliberate, policy-gated door, whose first live use is specimen 5). Two properties make it a productive specimen farm for exactly this failure class.

First, control density. The system is built security-first: fail-closed error paths, deny-by-default allowlists, a single policy-adjudication door for risky actions, provenance tags on all externally-sourced content, an output validator screening everything that leaves, signed model manifests at boot, and multiple independent locks on the one network door. Composition failures need controls to compose; a system with this many controls per square meter grows more seams than a permissive one.

Second, instrumentation of the *process*. The project keeps an engineering journal (465 dated entries over its first 58 days of journaling, 2026-05-21 to 2026-07-17), a numbered-lessons file, decision records, and per-incident regression tests. Every specimen below links to the entry written the day it happened and the commit that fixed it. Quotes from the journal are verbatim. That record is public in the project's mirror repository, so every claim here is checkable — the receipts section at the end explains how.

A note on scope before the catalog: "control" below is broader than "security control." Five specimens are collisions between security/policy controls in the narrow sense. Two are collisions between a production safety mechanism and the *verification apparatus* (the test gate) — I include them because the colliding parts were each deliberate, correct designs, and because a verification system that can collide with production is very much a security-relevant property. The eighth is two features of the underlying inference runtime — included because it is the same failure shape one floor down, and because its fix was merged upstream, which makes it the most independently-checkable specimen in the set.

## How specimens qualified

Three criteria, applied to the full journal record:

1. **Both colliding parts individually correct.** Each side would pass review on its own; several sides were themselves security fixes. Incidents where one party was simply defective (a wrong type, an import-time side effect, a missing ACL re-grant) were excluded — those are ordinary bugs wearing a composition costume.
2. **Fully documented.** A dated journal entry written at the time, plus the tickets/commits to reconstruct it.
3. **Structural fix shipped.** Not a tuned threshold or a "be more careful" note — a change to the structure (a derived constant, a new provenance tier, an isolation boundary, an upstream patch), landed and test-locked.

The project's own documentation audit had enumerated seven; re-deriving from the journal against these criteria admitted an eighth (the runtime specimen). Several near-misses failed criterion 1 on inspection — one party turned out to be simply defective, or a single principle mis-scoped — and were excluded rather than rounded up. Three later recurrences of specimen 1's class are discussed after the catalog rather than padded into it.

## Specimen 1 — The replay window between two correct components

**2026-06-09 · capability-token replay protection · fixed in commit `73746050`**

**Setup.** The system's policy agent mints short-lived capability tokens (ES256-signed JWTs — JSON Web Tokens) for privileged operations; consuming services validate them. Replay protection is by nonce: every minted token carries a unique 128-bit nonce, and the validator rejects any token whose nonce it has already seen. The seen-nonce store garbage-collects entries by TTL (time to live) — a 5-second window, a perfectly reasonable default for a bounded-memory store. The token's own validity period was 30 seconds — a perfectly reasonable token lifetime. Two components, two defaults, two different files.

**Collision.** The validator forgets a nonce at 5 seconds. The token stays valid to 30. A token replayed in the 5-to-30-second window finds its nonce already evicted (passes the replay check) and its expiry not yet reached (passes the validity check). The single-use guarantee had a 25-second hole.

**Root cause.** In the journal's words, the hole "existed precisely *because* the two components were each individually correct: a 5s nonce-seen window is a fine default, and a 30s token is a fine token, but the seam between them was never specified." Nothing in either component's tests could see it; each component honored its own contract. The guarantee lived in the *pair*, and the pair had no owner. (A bonus finding from the same fix: only one service in the whole system turned out to be a live runtime validator — the minting agent's own validator construction was a boot-time check that discarded the object. Knowing which seam is real is half of specifying it.)

**Structural fix.** Not a bigger window — a *derived* one: the nonce store's TTL is now computed from the token validity (`aligned_nonce_ttl(validity) = validity + skew_margin`), and the validity constant was promoted to a single shared source of truth that both the minter and the validator read. The two numbers can no longer drift apart, because there are no longer two numbers. The fix also kept a deliberately-contrastive regression test that reconstructs the *old* shape and asserts the replay is *accepted* — documentation of the exact bug, wired to fail loudly beside the test that proves the new shape rejects it.

**Transferable rule (ours, hedged).** When a guarantee is jointly defined by two constants in two places, the pair is the control. Derive one from the other or lock their relation in a test; independently-defaulted values that must agree, won't, forever.

## Specimen 2 — The door that would have tripped its own alarm

**2026-06-12 · egress kill-switch × anti-SSRF ordering · fixed in commit `c6fe7e97`**

**Setup.** As in the opening: control A is the egress kill-switch, armed at process entry, tripping on any off-allowlist network activity — the system began life fully air-gapped, and the kill-switch is the enforcement that egress happens only through the one deliberate door. Control B is that door's SSRF pre-check ordering: resolve the hostname first, inspect the addresses, refuse internal ones — and only then widen the per-fetch allowlist. The ordering exists so that a malicious hostname is refused *without the allowlist ever having been widened for it*, even briefly. A test asserts exactly that property. Both controls are the kind you keep.

**Collision.** The pre-check's own DNS resolution of a not-yet-allowlisted host is, to the armed kill-switch, off-allowlist egress. The first operator-driven fetch would have been denied and would have tripped the kill-switch — denying the action *and* punishing the system for attempting it, forcing a re-arm ceremony. The proof harness that had validated the door a week earlier never saw this: it had (reasonably) run with the guard unarmed. What surfaced it was the project's operator asking to run the real thing in production — "the request was the test."

**Root cause.** Two controls watching the same wire, one of them performing a read that is observationally identical to the behavior the other exists to stop. The pre-check *looks like* the exfiltration attempt. No allowlist state exists yet in which the pre-check is distinguishable — that's what pre-check means.

**Structural fix.** The tempting fix — widen the allowlist before resolving, so the lookup is sanctioned — was rejected by name, because it spends the exact property the ordering was built to keep (no momentary hole for an unvetted destination). The shipped fix keeps the ordering and gives the pre-check a legitimate, narrow seam: the door's inspect-and-refuse lookup goes through the guard's own pre-arm resolver — a path that can only inspect resolved addresses and refuse; it never connects. The actual fetch still resolves and connects through the armed guard and the per-fetch widen, unchanged. A regression test now runs the door *with the guard armed* — the configuration production actually has.

**Transferable rule (ours, hedged).** When two controls observe the same channel, decide explicitly which reads belong to whom. A safety pre-check that is indistinguishable from the attack will eventually be treated as the attack — give it an auditable private seam, or the controls will fight.

## Specimen 3 — The knowledge bank that could only be written to

**2026-06-14 · provenance lock × leakage detector · fixed in commit `6bc0994a`**

**Setup.** The system lets its operator save web articles into a local knowledge bank for later recall. Control A is the provenance rule — *provenance is not trust*: operator approval curates content into the bank but does not promote web-sourced bytes into the trust boundary. Saved chunks stay tagged untrusted, which keeps the action-lock armed — a prompt-injection buried in a saved article can never fire a tool. Control B is the output leakage detector: if a generated answer is ≥ 0.85 cosine-similar to an untrusted chunk in context, hold it — near-verbatim echo of untrusted content is the exfiltration signature of a fooled model. The journal's assessment of the pair: "Two controls I would defend separately, each correct on its own terms, met in the knowledge bank and quietly turned it write-only."

**Collision.** A faithful recall of a saved article *is* near-verbatim to its source — that is what recall means. So every honest recall scored as a leak and was held. The operator found it the honest way: saved an article, opened a fresh session, asked for it back, and got "Response held by the output validator — LEAKAGE_DETECTED." You could save anything and retrieve nothing. For a feature whose entire pitch is "save articles, recall them later," the journal called it what it was: a clean kill.

**Root cause.** A category error, not a malfunction: the detector cannot distinguish "leaked what you didn't ask for" from "answered using what you deliberately saved for the purpose of asking." Both are high cosine. The axis that separates them is provenance and intent, and the detector only had a score.

**Structural fix.** Three tempting fixes were rejected by name: promote saved content to trusted (drops the action-lock — trades an annoyance for a real injection regression); disable the leakage control globally (re-opens the exfiltration surface for pasted external text); raise the threshold (a faithful recall trends toward cosine 1.0 — no number separates it from an echo). The shipped fix is a *fourth provenance tier*: knowledge-bank content is untrusted everywhere the untrusted tier is untrusted — action-lock, content datamarking, injection scan, all of it — with exactly one carve-out: it is exempt from the leakage detector's comparison feed. Trust was not promoted; one output check was scoped. The tests are the load-bearing half, in both directions: a rigged recall scoring 0.97 against its source is delivered, and the same content tagged as ordinary untrusted external text at 0.97 is *still held* — proving the carve-out is provenance-scoped, not a global softening.

**Transferable rule (ours, hedged).** The project minted it as a numbered lesson that day: *when two individually-correct controls collide, add a tier — don't lower a bar.* Resolve control collisions by adding a distinction the controls can see, never by weakening either control.

## Specimen 4 — The over-denial that turned out to be unreachable ALLOW

**2026-07-02 · three fail-closed defaults · fixed in commits `24a1ebd4` → merge `51182e4e`**

**Setup.** Every risky action in the system passes a policy classifier whose model path produces a verdict plus a confidence; the decision matrix requires `ALLOW` *and* confidence ≥ 0.75 to approve. Three components, three separately-correct decisions: (1) an earlier hardening pass had zeroed the *fallback* confidence defaults — if the model's output states no confidence, assume 0.0, not 0.995; fail closed (that hardening landed 2026-04-17). (2) The prompt demanded exactly one output line — `DECISION: <LABEL>` — clean, parseable, no rambling. (3) The generation cap was 10 tokens — tight budget for a one-line answer. Each is the kind of default a reviewer approves without a second look; the first one *was itself a security fix*.

**Collision.** The parser was built to read a `CONFIDENCE:` line. The prompt never asked for one, and the 10-token cap couldn't have fitted it anyway. So every model `ALLOW` parsed with confidence 0.0, failed the 0.75 gate, fell through the escalation band, and landed on DENY. The measured symptom looked like model behavior: 26/30 on the golden set, all four misses false-denials of benign actions — "the model is over-cautious, tune the prompt." The arithmetic said otherwise: on the model path, ALLOW was *structurally unreachable*. In the journal's words: "it was three components each individually fail-closed composing into a policy that could never say yes." The unit tests had modeled the two-line format all along — mock outputs in the test suite carried `DECISION: X\nCONFIDENCE: 0.9` — so every component's tests passed while the composition could not emit its most common legitimate verdict.

**Root cause.** Fail-closed defaults compose into fail-shut. Each component honored its contract; the pipeline's end-to-end property ("a benign action can be approved") belonged to no component and was tested by none of them. It took a full-pipeline evaluation harness — measuring the real model through the real parser through the real matrix — to make the composition visible.

**Structural fix.** Discipline first: before loosening anything, five new deny-side probes went into the golden set (credential reads, persistence writes, log destruction — each verified to slip past the deterministic rules so the *model's* judgment is what's measured), so the fix would be scored in both directions. Then the prompt asked for what the parser could read (two lines, with calibration guidance), and the token cap went 10 → 24 so the second line physically fits. The thresholds, the matrix, and every deterministic rule stayed byte-identical. Measured with the production model (Qwen3-14B on the Arc 140V GPU), same golden set, 13 of the 35 cases exercising the model path: 31/35 before, 35/35 after — false-denials 4 → 0, false-allows 0 → 0 across every deny-side probe old and new. The entry names the trade-off honestly: making ALLOW reachable at all necessarily opens the false-allow surface that the broken composition had welded shut *by accident* — which is why the deny-side probes doubled first, and why the fixed pipeline's behavior is pinned in a committed eval baseline that fails loudly on drift in either direction.

**Transferable rule (ours, hedged).** When a measured miss is 100% one-sided, audit the deterministic plumbing around the model before tuning the model. And test the pipeline as a pipeline: no component test can see a property that only the composition has.

## Specimen 5 — The answer the door let through and the validator swallowed

**2026-07-02 · untrusted-web provenance × leakage detector · fixed in commit `4373e95d`**

**Setup.** The first live web search — a go-live ceremony with the operator present, the system's first sanctioned network fetch through the one egress door. Control A: web content stays untrusted (the same provenance-is-not-trust rule as specimen 3 — an injected instruction in a search result must never gain standing to fire a tool). Control B: the same output leakage detector — don't let the model echo untrusted content verbatim out of the system.

**Collision.** The ceremony worked end to end: the model reached for the search tool unprompted, the deterministic allowlist released the approved search domain, the endpoint returned HTTP 200, and the model composed a faithful answer with the requested fact in it. Then the output validator held the answer: leakage score 0.930 against a threshold of 0.85. The operator never saw it. The journal: "The feature we had just proven worked had, in the same breath, proven it could not deliver an answer." Same shape as specimen 3, two weeks later, one tier further out — a faithful relay of a search result is, by construction, similar to that result.

**Root cause.** "The control was not wrong about the similarity; it was wrong about the *direction*." Exfiltration is content flowing *out* to an untrusted destination. This was public content flowing *to the operator who asked for it*. A cosine score has no direction in it.

**Structural fix.** The same mechanism as specimen 3's fix, aimed at a new source — a *fifth* provenance tier for web-search results: untrusted for everything that matters (action-lock, datamarking, per-dispatch deny), exempt from the leakage comparison feed only. Two shortcuts were rejected by name. Reusing the knowledge-bank tier (its gating is byte-identical today) was rejected for audit legibility: web results are transient lookups the model requested this turn, not the operator's curated bank, and a future per-source policy — retention, expiry-at-turn-end, injection-scan aggressiveness — will need to tell them apart in the audit trail. And broadening the exemption to all untrusted-external content was rejected harder, because operator-pasted external text is exactly what the detector must keep screening — the operator did not request that content as a public lookup, so a verbatim echo of it *is* still the signature. A regression test pins the split: pasted-external stays in the feed; web-search results leave it.

**Transferable rule (ours, hedged).** An output validator has a direction, not just a similarity — "leaked what you didn't ask for" and "delivered the public thing you asked for" are different events that score identically. The durable separation axis is provenance, never a threshold: a faithful relay trends to cosine 1.0, so no number can both pass the relay and catch the echo. (This was the day the specimen-3 lesson earned its first recurrence tally.)

## Specimen 6 — The gate that vanished at 76 percent and reported green

**2026-07-04 · single-instance lock × tests that drive real code · fixed in commit `3df53522`, merge `b9e0aca2`**

**Setup.** This one is a collision between a production safety mechanism and the verification apparatus itself. Control A: the launcher's single-instance lock. Its origin is itself a composition story — two weeks earlier, four concurrently-launched instances had each re-minted the system's per-boot certificate authority into one shared directory, stomping each other's trust chains. The lock's refusal path is deliberately violent: a second launcher hard-exits via `os._exit(1)` *without* running cleanup, because a refused instance that ran the normal teardown would stop the live instance's virtual machine. That no-cleanup hard exit was reasoned, reviewed, and is correct in production. Control B: the launcher test suite drives the *real* startup entrypoint with dependencies mocked — the project's hardest-won testing doctrine ("mocks lie; drive real objects through real entry points"), earned across multiple incidents where mock-shaped tests passed and production crashed.

**Collision.** The standing test gate ran on the main checkout while the operator's live instance was up — legitimately holding the lock file of that same checkout. The unmocked lock step inside the real entrypoint met a genuinely-held lock, took the production refusal path, and `os._exit(1)` killed the entire test process mid-run. The gate's output stopped at 76% with no failure and no summary — and because the run was piped, the exit code the session read back was the pipe's, not the test runner's. The journal: "not red, not green, but *absent*, wearing green's clothes." A second uninvited passenger rode the same unmocked stretch: the real privilege-hardening step permanently stripped twenty privileges from the *test runner's own process token*.

**Root cause.** "An intentionally violent exit path and a test that drives real code are each fine alone — the audit question is *what stands between them*." Nothing did: nobody had ever run the gate from the main checkout with the app open, so the boundary between production semantics and test execution had never been exercised, and its absence was invisible.

**Structural fix.** The production hard-exit was deliberately *not* softened into something test-friendly — it is load-bearing exactly where it is. The test boundary was the defect, so the test boundary got the fix: an always-on isolation fixture for the launcher suite patches the lock step and the privilege strip as bound in the real entrypoint, so tests can no longer read, write, or refuse on the real lock file, and can no longer mutate the runner's token. The suites that exercise the lock and the privilege strip directly and on purpose are untouched. And a new refusal-path regression test re-pins the *production* semantics so the isolation can never quietly erase them: on refusal, `os._exit(1)` fires, the VM is never started, and — the assertion the entry says it cares most about — the lock-release routine is never called, because a refused instance deleting the live holder's lock would be the worse bug.

**Transferable rule (ours, hedged).** Wherever a deliberately-destructive production path and a drive-the-real-code test policy coexist, something explicit must stand between them, and the production semantics must be pinned by a test so the isolation can't drift into weakening them. Corollary, now house doctrine: a gate run with no summary line is a failed run, whatever the shell's exit code says.

## Specimen 7 — The recovery that killed the patient

**2026-07-07 · boot-time swap recovery × the standing gate · fixed in commit `72de8d40`**

**Setup.** Overnight, the system swaps its resident 14-billion-parameter model out to run a larger coding model, driven by a detached process; a crash mid-swap would strand the machine in a broken state. Control A: boot-time swap recovery — when the assistant service boots and finds a swap in flight, it assumes the swap crashed, stops the model server, restores the baseline model, and stamps the state RECOVERED. Correct for its designed case; recovery-on-boot is how the machine heals from a genuine mid-swap crash. Control B: the standing test gate, which (per the same doctrine as specimen 6) drives the real service-boot path in tests. The test configuration leaves the fleet-state roots empty, and — the third correct-in-isolation piece — the empty-roots code path falls back to the box's real fleet root, a reasonable default for production robustness. The project already redirected the user-data directory in all test runs (a control built after an earlier incident where a test run corrupted the real session database) — but that redirect never covered the fleet's state directory.

**Collision.** A standing gate run during a live overnight coding run: the boot-recovery reconcile inside a service-start test "recovered" a *healthy* swap — stopped the real model server mid-request, stamped RECOVERED over the live run's state, and left the very-much-alive driver dispatching tasks into a world with no model behind the socket. The diagnosis went through three wrong suspects before file timestamps settled it: the RECOVERED stamp landed at 11:09:17, inside the author's own 11:07–11:12 gate run. The journal's verdict: "The killer was me."

**Root cause.** Two, honestly. The test-isolation gap: the gate had been silently capable of this since the reconcile shipped; it needed a live dispatch under it to fire, "and night-2 never had one because nobody runs pytest at 3 a.m." And a production assumption exposed as too strong: "an AO booting while a swap is in flight means the swap crashed" is false whenever the service boots *beside* a healthy detached driver — which the operator would eventually have done himself by opening the app while the nightly run was active. The test collision was the messenger; the flawed premise was also reachable in ordinary production life.

**Structural fix.** Both halves, same day. Test side: an always-on root-level fixture stubs the reconcile seam for every collected test (with an explicit opt-out for the tests that exercise the seam against fakes), a second belt covers direct sub-suite invocations, and an identity-lock test fails loudly if either guard is removed — deliberately *without* calling the seam, because a broken guard plus a probing call would be the hazard itself. Production side: recovery now verifies the death certificate before acting. The swap driver stamps its process ID and process-creation-time into the swap state at takeover; the reconciler probes liveness (creation-time matched, to guard against PID reuse) and keeps hands off a live driver — while failing *closed to recovery* if liveness can't be established, so a genuinely crashed swap is never stranded. The entry records the rejected cheaper path: gate only the test side and leave production recovery alone — rejected because the operator-boots-mid-run case was real and imminent.

**Transferable rule (ours, hedged).** Recovery is an actuator, and an actuator's premise needs a liveness check: "is the thing I'm about to recover actually dead?" Assumption-based recovery composes badly with anything else that can legitimately boot beside it — and a fail-closed direction still exists (when unsure, recover), so the check strengthens rather than weakens the guarantee.

## Specimen 8 — The crash that only happens when two right things run together

**2026-07-04 characterization · substrate: inference runtime · upstream fix: openvino.genai PR #4082, merged 2026-07-08**

**Setup.** One floor down from policy controls, the same shape. The inference runtime under the system (OpenVINO GenAI) offers two features this project runs: grammar-constrained structured output (an xgrammar-based matcher that guarantees tool calls parse — an output-integrity control in the tool-call trust chain), and speculative decoding (a small draft model proposes tokens the large model verifies in batch). Each individually proven: speculative decoding had been the production default for weeks; the grammar constraint, with speculation off, ran crash-free in controlled elimination runs.

**Collision.** Together, rare crashes at end-of-sequence — nondeterministic, first seen when a live turn died. Controlled elimination on the real hardware isolated it to the pair: speculation off, no crashes; both on, the crash lives at the seam "where the draft model proposes tokens past a stop the grammar matcher has already terminated on, and the runtime asks the terminated matcher to mask them."

**Root cause.** Each feature keeps its own private notion of "we're done" — the sampler's stop handling; the matcher's terminated state — and the integration path between them never consulted the other's terminal state. Nobody's unit tests own the off-diagonal cell of the feature matrix: precisely the specimen-4 lesson recurring at substrate scale.

**Structural fix — merged upstream.** The project characterized the bug with a sanitized, dependency-minimal reproducer (generic prompts, a stock tool schema — nothing internal), filed it, and submitted the fix; the maintainers reviewed and merged it on 2026-07-08 (openvino.genai pull request #4082 — github.com/openvinotoolkit/openvino.genai/pull/4082, merge state re-verified via the GitHub API on the drafting date; merged, with no claim here about tagged-release inclusion).

**Place in the catalog.** Specimen 8 of 8 — the specimen-4 pattern one floor down, kept deliberately compact here because its canonical full account is the companion piece in this series: *The crash we found and fixed upstream* (`/posts/the-crash-we-found-and-fixed-upstream` — home-base relative path, written as inline code rather than a markdown link **because the target does not exist yet**: `test_doc_pointers_and_banners` gates markdown links against the real tree and a link to an unpublished post is a dead pointer by that gate's definition, which is correct. The final path is pinned at ceremony packaging, and it becomes a link then) carries the isolation table with run counts and crash rates, the reproducer, and the verification methodology. **Transferable rule (ours, hedged).** Feature interaction is not just an application-layer problem — your substrate has feature pairs too, and the off-diagonal cells of its feature matrix may be nobody's test responsibility. If your system depends on a pair (here: structured output × speculative decoding), soak *the pair*, not each feature. This specimen is also the catalog's control against a tempting misreading: the composition-failure class is not an artifact of one project's architecture. It found us from below.

## The class keeps firing: what happened after the catalog

Cataloging a specimen does not retire its class. Specimen 1's shape — two independently-set time values whose *pair* defines a guarantee — recurred three more times as live failures over the following five-plus weeks, in different clothes each time:

- **2026-07-09:** a dispatch monitor's 90-second no-progress kill window sat inside a verification step's own 600-second granted budget; the step's workers write nothing until they finish, so a *working* verify was indistinguishable from a dead run, and the monitor killed a healthy job at one-seventh of its promised time.
- **2026-07-11:** a boot handshake's retry schedule summed to ~15–18 seconds inside the system's own documented 180-second cold-start ceiling — a boot that promised three minutes and granted eighteen seconds.
- **2026-07-15:** a nightly scheduled task's hand-typed 16-hour execution ceiling sat about three hours under the six-job worst case its own runner had grown into.

The project's lessons file distilled the family the day the first recurrence was diagnosed, and it is the best one-sentence statement of this whole catalog: "Neither number was wrong in isolation; the PAIR was incoherent, and nothing owned the question." By that lesson's own tally the class was met once more in the same stretch — a fourth encounter, caught at design time rather than in production, when a new readiness wait (2026-07-11) shipped only after every window-and-budget pair it touched had been enumerated and proven to fit. And per the project's escalation rule (a third instance of a lesson's class must ship a structural control, not another fix), the structural response arrived in two installments: *relation* locks in a timeout registry — tests that assert one budget exceeds another, so the pair itself is pinned — shipped at the class's third instance by the lesson's count (the boot-handshake recurrence), and outer limits *derived* from the inner budgets they must dominate, instead of hand-typed near them, at the fourth (the nightly-ceiling recurrence). Whether those controls hold is a question for the next quarter's data, and this catalog will be wrong somewhere too; that is what the journal is for.

## What eight specimens agree on

Cross-cutting reads, offered as interpretation from one system's record — patterns we observed, not laws:

**1. Review approves parts; failure arrives in pairs.** Every specimen passed review because every part deserved to pass review. Several parts *were* security fixes (the zeroed confidence fallback; the no-cleanup hard exit). The unit of review — the diff, the component, the control — is systematically smaller than the unit of failure. On this system, the honest conclusion was that "both sides are correct" is the *beginning* of the audit, not the end of it.

**2. The seam never has an owner until it fails.** Nonce-TTL × token-validity; kill-switch × pre-check; detector × recall; window × budget — in every case, each side had an owner and the relation had none. The fixes that stuck all gave the *pair* an owner: a derived constant, a relation lock in a registry, a full-pipeline eval, an isolation fixture with an identity test.

**3. The fix grammar is small.** Eight specimens, and the shipped fixes reduce to about six moves: derive one value from the other (1); give the conflicting read its own legitimate seam (2); add a distinction the controls can see — a tier — rather than lowering a bar (3, 5); evaluate the composition, not the components (4); put an explicit boundary between the colliding pair and pin both sides' semantics with tests (6, 7); make one component's terminal state queryable by the other (8). None of the eight fixes weakened either colliding control — that constraint turned out to be satisfiable every time, which we did not expect and cannot promise generalizes.

**4. Composition failures surface at composition time.** Not one specimen was found by a component test. The finders were: a ticket that made someone read two files together (1); the operator asking to run the real thing (2); the operator's first honest use of a feature (3); a full-pipeline evaluation harness (4); a go-live ceremony (5); a truncated gate run (6); a live overnight run under a test gate (7); a live tool-call turn (8). If the pattern transfers at all, it is that you need instruments that run the *whole* system — live-fire ceremonies, end-to-end evals, production-posture harnesses — because that is where compositions exist.

**5. Fail-closed composes into fail-shut — and that is still the right default.** Specimens 3, 4, and 5 are all cases where correctly-conservative controls composed into a system that couldn't do its job (couldn't recall, couldn't approve, couldn't answer). It would be easy to read this catalog as an argument against strict controls. Our read is the opposite: every one of these failures was *loud, safe, and diagnosable* — a held answer, a denied action, a refused boot. The dual — two correct controls composing into a silent *hole* in a shipped guarantee — appears here only as specimen 1. (Specimen 6's entry does say "three sound decisions composing into one silent hole," but that hole opened in the verification plane — a gate reporting green while absent — not in a production control's guarantee; we scope the two apart deliberately.) We suspect the asymmetry is the survivorship effect of building fail-closed: "too much no" announces itself; "too much yes" waits quietly to be found. We read it as evidence the deny-by-default posture pays for its annoyances — with the honest caveat that this argument cannot distinguish "the posture makes failures loud" from "the quiet holes are still unfound." A catalog of caught collisions has no denominator, and neither does this inference.

## Limits

Everything above is one project, one architecture, one operator, five and a half months old (first commit 2026-02-04), with the journal covering its most active 58 days. The specimens are the collisions we caught; there is no denominator, and nothing here estimates what we missed. The catalog over-represents fail-closed collisions for the reason just given. The fixes are documented events; the rules drawn from them are our interpretations and are hedged accordingly. This is a field report from a personal research project — a long-term local AI system — offered because the failure class is easier to teach from specimens than from theory, not because eight cases prove anything general.

## Prior work, properly

The map this piece stands on, with what each neighbor is and isn't:

- **Pamela Zave — the feature-interaction problem** (pamelazave.com/fi.html, accessed 2026-07-19; the Feature Interaction Workshop series, IOS Press). The founding statement that individually-correct features need not compose. Formal-methods and telecom lineage; the thesis ancestor of everything here. This catalog differs in evidence type (operational security incidents, not formal analysis) and register (field report).
- **Hillel Wayne — "Feature Interaction Bugs"** (hillelwayne.com/post/feature-interaction/, accessed 2026-07-19). The best modern practitioner essay on the class, with a constructed illustrative case; explicitly general-software rather than security, and an essay rather than a specimen collection.
- **Charles Perrow — *Normal Accidents* (1984).** Interactive complexity + tight coupling as the precondition for system accidents. The theory backbone; no security-control specimens.
- **Richard I. Cook — "How Complex Systems Fail"** (how.complexsystems.fail, accessed 2026-07-19). Eighteen numbered truths, the register model for "short, transferable rules from operational failure." Medicine/ops lineage; not composition-of-security-controls specifically.
- **Ran Canetti — Universal Composability** (eprint.iacr.org/2000/067). The formal proof-level version of "secure components, insecure composition" for cryptographic protocols. Same thesis in a different universe of discourse; no operational catalog.
- **Kelly Shortridge & Aaron Rinehart — *Security Chaos Engineering*** (O'Reilly 2023; securitychaoseng.com). The security-native methodology for *discovering* exactly these interactions experimentally. This catalog is complementary: it is what the found objects look like when you keep them, not a method for finding them.
- **danluu/post-mortems** (github.com/danluu/post-mortems). The genre model for curated failure collections; cross-organization and general-reliability, where this is one system and control-composition-specific.
- **The 2025–2026 agent-guardrail literature** — e.g., "Provably Secure Agent Guardrail" (arXiv:2605.29251) and the 2026-04-20 practitioner survey "AI Agent Security in 2026" (both accessed 2026-07-19). The most timely neighbors: composed guardrails that bypass, over-refuse, or cascade in LLM-agent systems. Those papers propose defenses and taxonomies; this piece contributes the documented single-system field data such work usually lacks.

What none of these contains — and the only thing this piece claims as new — is the artifact: a single-system, fully-instrumented specimen catalog of control-composition failures with shipped, cited, checkable structural fixes.

## Provenance, method, and receipts

This piece was drafted with the AI development fleet it describes, working from the project's build journal, decision records, and measured performance logs; the human author directed, reviewed, and approved every claim.

Method, briefly: the specimen set was derived from the project's complete journal record against the three criteria in "How specimens qualified"; every quote is verbatim from the journal entry named beside it (re-flowed from the source's hard line-wrapping, otherwise untouched); every date, count, and commit hash was re-derived from the repository history rather than from memory or summaries; the upstream pull request's merge state was re-verified through the GitHub API on the drafting date. Candidates that failed the criteria — and there were more collisions than qualified — were excluded rather than rounded up.

What the mirror does resolve directly: every entry title above, and the fixed source files the entries name.
