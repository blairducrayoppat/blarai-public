# Microsoft agent-governance surfaces beyond Agent Framework, AGT and ACS — documentation survey

**Scope.** This is a documentation-level survey, as of 2026-09-16, of the Microsoft surfaces (and the `responsibleai` GitHub organisation that publishes the Agent Control Specification and the Agent Hooks contract) that govern what an AI agent is allowed to DO, bind approvals to actions, record auditable decisions, or give agents identity — OTHER than Microsoft Agent Framework (including FIDES and Agent Hooks as consumed by it), the Agent Governance Toolkit (AGT) and the Agent Control Specification (ACS), which are covered in the four existing documents in this folder (`cava-and-microsoft-agent-framework-grounding-2026-09-16.md`, `cava-vs-microsoft-agent-framework-vs-blarai-trust-spine-2026-09-16.md`, `agt-vs-policy-agent-adjudicator-verdict-2026-09-16.md`, `acs-vocabulary-adoption-design-2026-09-16.md`). Only official sources were read: learn.microsoft.com, devblogs.microsoft.com, microsoft.com, commandline.microsoft.com, github.com/microsoft, github.com/responsibleai, and for Dapr the CNCF blog, blog.dapr.io, docs.dapr.io and github.com/dapr. Nothing was measured or run; every claim below is what a page says, quoted where load-bearing, and anything that could not be read on an official page is listed at the end under "Not found / not verified". Each item is assessed against five criteria: (1) is there an action identity object at the decision point, (2) does an approval bind to a specific call, (3) is a decision record (receipt) written and in what form, (4) is there an enforcement seam that actually stops the action, (5) does it run locally/offline. Dates are the `ms.date` or publication date printed on the page.

## 1. The `responsibleai` GitHub organisation

**What it is.** A GitHub organisation displayed as "Responsible AI", bio "Building Responsible AI Tooling", website link `https://aka.ms/responsible-ai-governance`, 26 followers. The organisation page does not state who operates it. The `aka.ms` link (a Microsoft short-link domain) returns `301 Moved Permanently` to `https://www.microsoft.com/en-us/ai/responsible-ai`.

**Is it Microsoft?** Yes in authorship, deliberately not in packaging. Evidence read:
- The Agent Hooks announcement on commandline.microsoft.com (2026-08-27) is authored by "Mohammad Abuomar, Caitie McCaffrey, Sarah Bird, and Responsible AI at Microsoft" and states: "the spec and SDKs are MIT-licensed under an open organization".
- The ASSERT README says it is built by Microsoft's Responsible AI organization and that trademarks are subject to "Microsoft's Trademark & Brand Guidelines".
- The spec document's metadata line reads "Editors: Responsible AI / Agent Governance Toolkit".
- `GOVERNANCE.md` of agent-hooks names a single maintainer, `@MohammadHaroonAbuomar`, with decision authority; it calls the single-maintainer state "a documented limitation, not an implicit norm" and plans a second code owner. It contains no Microsoft mention and no Contributor License Agreement requirement. Design changes go through written proposals (P-NNN), `main` is protected, releases are tag-driven with provenance attestation and SBOM via OIDC trusted publishing.

**Repositories (all five, as listed on the org page on 2026-09-16).**

| Repository | Description (org page) | Language | Stars | Licence | Last updated |

There is no separate `agent-hooks-sdk` repository and no separate conformance-kit repository: the README states the SDKs and the Conformance Test Kit live inside `agent-hooks` (Python reference implementation with the complete CTK runner; Rust core with TypeScript, .NET and Go bindings). The older repository name `responsibleai/AgentControlSpecification` now returns HTTP 404.

**Agent Hooks contract (AGENT-HOOKS-0.1).** URL: https://github.com/responsibleai/agent-hooks. Status: README badge "Draft · Spec: AGENT-HOOKS-0.1"; spec file metadata "Status: Draft · Version: 0.1.0-alpha · Date: 2026-07-09". Licence MIT. Runs locally: it is an in-process library contract, not a service.

- Interception points (eight): `agent_startup`, `input`, `pre_model_call`, `post_model_call`, `pre_tool_call`, `post_tool_call`, `output`, `shutdown` (the blog spells the last `agent_shutdown`). Verdicts (three): `allow`, `deny`, `transform`. README: "warnings ride on any verdict; deny + approval block = liftable via the seam."
- Action identity at the decision point: at `pre_tool_call` the AgentContext carries `"tool_call": { "id", "name", "args" }` with `target` pointing at `tool_call.args`; optional `tool_call.content_hash` (format `sha256:<hex>`, host-opaque), `session.id`, `session.turn`.
- Approval binding: an ApprovalRequest carries `context_identity`, computed by an identity provider over the redacted context shown to the approver; the default `jcs-sha256` provider computes `"sha256:" + lowercase_hex(SHA-256(RFC_8785_canonical_json(context_projection)))`, where the projection includes only required and conditional fields. The ApprovalResolution "must echo the request's context_identity byte-for-byte"; a mismatch raises `host_error:approval_identity_mismatch`. Blog wording: "The approval block above carries a context_identity: a SHA-256 over the canonical JSON of exactly what the approver was shown."
- Decision record: "Every emission also produces an InterceptionRecord, which is payload-free by design." "It never carries customer content." Fields include `interception_point`, `mode` (`enforce` | `evaluate_only`), `verdict` (payload-free projection), `input_identity`, `enforced_identity`, `identity_provider`, `session_id`, `sequence`, `decided_by`, `composition`, `verdicts[]`, `resolved_by` (`approval` | `rejection` | null). Projection rules: `transform.value` is dropped, `message` fields are truncated to 256 UTF-8 bytes, approval presence is kept but members stripped. The record carries hashes; the spec does not define a signature over the record or a storage obligation. Form: hashed JSON, unsigned.
- Host obligations: `allow` "Proceed with the action using target unchanged"; `transform` "Apply the transform to target ... then proceed with the transformed value"; `deny` "NOT proceed with the action. At pre_* hooks the guarded call MUST NOT be dispatched." Blog: "A deny at pre_tool_call means the tool is not invoked. A deny at post_tool_call means the result is discarded and never enters agent state." On interceptor crash, timeout or invalid return the host must "synthesize a deny" with reserved reasons `host_error:interceptor_failed`, `interceptor_timeout`, `verdict_invalid`.
- Composition profiles (closed set): `sequential/first_deny`, `sequential/run_all`, `parallel/strictest`, `parallel/unanimous`; defaults `on_approval: "stop"`, `on_disagreement: "deny"`, `on_transform_conflict: "deny"`.
- Trust model, verbatim: "This specification constrains a cooperating host. It is not a security boundary against a hostile or buggy host, and conformance is not a security certification." README: the contract "is a cooperative contract, not a security boundary"; interceptors run in-process and "there is no mechanism to detect a host that skips interception points or ignores verdicts."
- Conformance: "Forty-seven scripted scenarios drive a host through the contract"; conformance requires "100% of the CTK vectors applicable to its declared surface", no tiered profiles. Certified hosts: "the Agent Control Specification policy runtime and Microsoft Agent Framework's core implementation" (47 of 47). "The .NET implementation is in review with the same test discipline." "AGENT-HOOKS-0.1 is versioned, the schemas are published, changes go through public proposals".

**ASSERT.** URL: https://github.com/responsibleai/ASSERT. MIT. Evaluation-only: generates behaviour-specific test cases from natural-language requirements, runs them, scores with LLM judges; "local-first artifacts" (every stage writes JSON/JSONL locally). It does not govern runtime actions; it can emit ACS policies for discovered failures. `assert-ai-action` gates pull requests in CI on paired safety regressions.

## 2. Microsoft Agent 365

**What it is.** URL: https://learn.microsoft.com/en-us/microsoft-agent-365/overview (ms.date 2026-08-19). "Microsoft Agent 365 provides the ability to observe, govern, and secure the growing number of agents within organizations." "As of May 1, 2026, Microsoft Agent 365 is generally available for the Commercial segment on a per user basis." Licensed per user; "works best when using Microsoft E5 as a pre-requisite"; included in Microsoft 365 E7. Cloud service only. The registry is the Microsoft 365 admin center; identity is Entra; data governance is Purview; threat protection is Defender.

**Registry, lifecycle and control-plane controls** (https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions, ms.date 2026-08-20; https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-365-overview, ms.date 2026-08-20). Agent actions: Install and uninstall; Block and unblock ("Restrict access to an agent across the organization, preventing any user from using it"); Delete; Start and stop ("Start or stop the underlying Azure infrastructure to govern Foundry agents"); Assign a new owner; Add/Remove an owner; Publish to store; Reject submission. Rules-based governance: "Leverage rules-based agent management to automatically enforce lifecycle policies, such as flagging ownerless agents, or blocking risky agents." Governance cards: Pending requests, Agents at risk (aggregated from Entra, Defender, Purview), Agents without owners, Agents with exceptions. Copilot Studio agents can additionally be quarantined per agent through the Power Platform API (`SetAsQuarantined`, roles: Global admin, AI admin, Power Platform admin). All of these are per-agent, not per-action.

**Tool-level controls.** Agents > Tools registry in the admin centre (https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent, ms.date 2026-07-30): per tool/MCP server Block and Unblock. Bring-your-own MCP server (preview): a developer registers a remote MCP server with the `a365` CLI (URL, auth type, declared tools); an admin approves and grants Entra consent; "Server-Level Block | Admin can block approved servers at any time; blocked servers are enforced at runtime." "Runtime Enforcement | Blocked MCP servers can't be invoked at runtime across any client surface." Supported client surfaces in preview: Copilot Studio, VS Code, Claude Code, GitHub Copilot CLI; "Azure AI Foundry and Microsoft 365 Declarative Agents aren't yet supported." Work IQ MCP (preview, ms.date 2026-08-10): "Policy enforcement: Enforce rate limits, payload checks, and security scans at runtime." "If an MCP server is blocked, it's blocked for every user and every agent." Each MCP server "corresponds to a permission on the Agent 365 application". These are server-level allow/deny; there is no per-call approval object.

**Action-level governance.** Exists only through Microsoft Defender real-time protection over the Agent 365 tooling gateway: "Agent 365 tool invocations: Defender integrates with Work IQ MCP to evaluate tool invocations before they run, including invocations of customer MCP tools onboarded to Agent 365. Agents that rely on unsupported tools or don't integrate with Work IQ MCP aren't covered." (see item 9).

**Audit.** Agent 365 observability (https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts, ms.date 2026-09-02) is OpenTelemetry trace data: a run is "a tree of OTel spans sharing a traceId"; accepted `gen_ai.operation.name` values are `invoke_agent`, `execute_tool`, `chat`, `output_messages`. The agent identity is bound: "The {agentId} in the URL must equal the calling application's appId"; "every span you send must set gen_ai.agent.id to the same appId; the server validates the in-payload agent identity against the authenticated agent and rejects mismatches." Data lands in Defender (`CloudAppEvents`, `ActionType` in `InvokeAgent`, `InferenceCall`, `ExecuteToolBySDK`, `ExecuteToolByGateway`, `ExecuteToolByMCPServer`), the Microsoft 365 admin centre, and Purview. In Purview's unified audit log the Agent 365 activities are `AIExecuteTool` ("Agent executed a tool call."), `AIInvokeAgent`, `AIInferenceCall`, `AIGuardrail` ("A guardrail was applied to an AI agent's request or response to enforce safety or compliance policies."). Records are plain telemetry/audit rows; no signing or hashing is documented. "A 200 OK isn't proof of ingestion." Ingestion is rejected with `tenant_not_licensed` unless at least one user has an Agent 365 or E7 licence assigned. Windows 365 for Agents (ms.date 2026-06-02) inherits the same: "Agent activity, including prompts, tool usage, and outcomes, is recorded and correlated across Microsoft Entra, Microsoft Defender, and Microsoft Purview".

**Criteria.** Action identity: only in telemetry (`execute_tool` spans) and in Defender's evaluation; no approval object; receipt = plain audit/telemetry rows; enforcement seam = server-level block plus Defender pre-execution rules on the gateway; cloud only.

## 3. Microsoft Entra Agent ID

**What it is.** URL: https://learn.microsoft.com/en-us/entra/agent-id/what-is-microsoft-entra-agent-id (ms.date 2026-04-14). "Microsoft Entra Agent ID is an identity and security framework that extends Microsoft Entra capabilities to AI agents." Status: Entra release notes, April 2026 entry "General Availability - Microsoft Entra Agent ID platform ... The Microsoft Entra Agent ID platform is now generally available." "Agent ID is available for all Microsoft Entra customers." "Extending Microsoft Entra security features to agents requires Microsoft Agent 365." Cloud service only.

**Identity primitive.** Three objects, each mapped onto an existing Entra type (https://learn.microsoft.com/en-us/entra/agent-id/sign-in-audit-logs-agents, ms.date 2026-04-28): the agent identity blueprint ("Analogous to an app registration", `agentType` = `agenticApp`), the agent identity ("a special service principal in Microsoft Entra ID", `agentType` = `agenticAppInstance`), and the agent's user account ("This identity lets an agent act as a user with user-delegated permissions", `agentType` = `agentIDuser`). Foundry's description: "Agent identity | A Microsoft Entra ID service principal that represents the agent at runtime." Blueprints support inheritable permissions granted once for all instances.

**Authentication.** OAuth 2.0. Unattended: client-credentials against the blueprint (secret, certificate, or federated credential such as a managed identity), then a token for the specific agent identity, then a scoped access token for the downstream audience. Attended: on-behalf-of flow carrying both the agent identity and the user's delegated permissions. Foundry's four-stage runtime exchange ends with: "Agent Service passes the scoped access token to the MCP server or A2A endpoint. The downstream resource validates the token and checks the agent identity's RBAC role assignments before granting or denying access." Protocols named: OAuth 2.0, MCP, A2A.

**Authorization granularity.** Role/scope at grant time, not per action. Entra "blocks agents from being granted many high privilege roles or permissions" (Global Administrator, Privileged Role Administrator, User Administrator cannot be assigned; no custom roles; no role-assignable groups); Graph permissions `Application.ReadWrite.All`, `RoleManagement.ReadWrite.All`, `User.ReadWrite.All`, `Directory.AccessAsUser.All` are blocked "even an administrator can't consent". "Agents can only do what a regular user could consent to, or what an administrator explicitly grants in a controlled, scoped manner." Conditional Access and Identity Protection apply to agent identities at sign-in. Per-action or per-tool-call authorization: not found on any Agent ID page read; the resource that receives the token makes the per-request decision from RBAC, Entra does not see the tool call.

**Decision record.** Audit logs record directory operations on agent objects (Add/Update/Delete application, service principal, user) with `agentType` and `blueprintId` on `initiatedBy`, `performedBy`, `targetResources`; sign-in logs carry the `agentSignIn` event type. "All agent authentication and activity is logged for compliance and audit." These are token issuance and directory events, not per-API-call records; plain logs, Graph `/beta` for the agent filters.

**Criteria.** Action identity: no (identity of the actor, not of the action); approval binding: no (admin consent to scopes at grant time); receipt: sign-in and audit logs, plain; enforcement seam: token issuance and Conditional Access; cloud only. Licence: Entra (platform free to all Entra customers; agent security features need Agent 365).

## 4. Microsoft Purview for AI agents

**What it is.** URLs: https://learn.microsoft.com/en-us/purview/ai-agents (ms.date 2026-05-27) and https://learn.microsoft.com/en-us/purview/ai-agent-365 (ms.date 2026-05-01). Cloud service; requires Microsoft 365 E5 and, for API integration, pay-as-you-go billing. Coverage table: Microsoft 365 Copilot, Copilot Studio, Foundry, Entra-registered agents and others get information protection and compliance management; Copilot Studio and Foundry agents specifically get "Data classification, sensitivity labels, data loss prevention, Insider Risk Management".

**Audit.** "When you create an agent instance for Agent 365, it's automatically enabled for audit, detection of sensitive data with data classification, and included with the Assessments for AI regulations". "Audit an agent instance as you would a user." "Supported interactions: All agent-to-human, human-to-agent, agent-to-tools, and agent-to-agent interactions." Records go to the unified audit log; the Agent 365 activity names are `AIExecuteTool`, `AIInvokeAgent`, `AIInferenceCall`, `AIGuardrail` (see item 2). For Copilot Studio (https://learn.microsoft.com/en-us/microsoft-copilot-studio/admin-logging-copilot-studio, ms.date 2026-08-18) the only usage event is `CopilotInteraction`, and "The audit logs in the Audit solution don't include the full text or transcript of the interactions between a user and the agent, only the transcript thread ID." The Copilot Studio governance page adds that "Telemetry such as agent invocation events, tool and action calls, policy enforcement decisions, and runtime activity signals is processed by the Microsoft Purview audit logging pipeline" (stated as a Customer Lockbox exclusion). Record form: plain audit rows in the unified audit log; nothing signed or hashed is documented.

**DLP for agent actions.** "Supported interactions: Block or audit agent-to-human and human-to-agent for Microsoft Teams, OneDrive or SharePoint, and emails." "Because an agent instance is unaware of the block action, the agent owner must actively monitor a DLP policy that uses this configuration and understand the impact to subsequent workflows." DLP therefore blocks data movement on Microsoft 365 channels, evaluated on content; it is not a tool-call gate and has no agent-to-tool DLP.

**Purview APIs (the runtime seam).** https://learn.microsoft.com/en-us/purview/developer/use-the-api (ms.date 2026-04-15). Two Graph calls: `protectionScopes/compute` (which activities need evaluation for a user) and `processContent` (evaluates content, "returns policy actions your app must enforce"). Activities are `uploadText`, `downloadText`, `uploadFile`, `downloadFile` — there is no tool-call or action activity type. `executionMode` `evaluateInline` "means your app's main thread must block until the call returns from processContent"; `evaluateOffline` is asynchronous. Response example: `"policyActions": [{"action": "restrictAccess", "restrictionAction": "block"}]`. "If you are building agents, the agent must also block before calling another agent when the action is set to restrictAccess." Enforcement is the calling app's job; Purview returns a verdict over text/file content and logs the activity. DLP policies for Entra-registered apps must be created with `New-DlpComplianceRule` (portal unsupported). The Agent Framework Purview middleware (ms.date 2026-07-28) wraps the same APIs and intercepts "prompts and responses" only.

**Criteria.** Action identity: no (content and activity type, never the tool call); approval binding: no; receipt: plain unified-audit-log rows (`AIExecuteTool` exists when Agent 365 observability feeds it); enforcement seam: the calling app must honour `restrictAccess`; cloud only.

## 5. Microsoft Foundry Agent Service

**"Trust Boundary" as a named feature: not found.** No learn.microsoft.com page for Foundry names a feature called "Trust Boundary" or an "external governor". The phrase appears generically: "When you use delegated isolation, your service is the trust boundary" (hosted-agent session isolation, search snippet); the Build 2026 post says "Every session runs in its own sandbox, isolating every agent execution with dedicated compute, memory and filesystem"; the toolboxes post (2026-07-22) says "Because Foundry manages every tool call, it can enforce policy at the boundary — not per-agent code". The "policy stages" AGT and the PCAA paper refer to map onto two real things: (a) Foundry Guardrails intervention points, and (b) ACS, which the Build 2026 post (2026-06-02) describes as turning risks "into enforceable runtime guardrails across input, model, state, tool execution, and output". The Tech Community post "Build a SAFE Agent on Microsoft Foundry" could not be rendered; from its search snippet, SAFE = Scope, Anchored Decisions, Flow Integrity, Escalation, "SAFE is a design framework, not a Foundry feature", and "ACS evaluating policy at runtime boundaries, before protected tool calls and before the final response leaves the host".

**Guardrails intervention points (the real policy stages).** https://learn.microsoft.com/en-us/azure/foundry/guardrails/guardrails-overview (ms.date 2026-07-31) and https://learn.microsoft.com/en-us/azure/foundry/guardrails/intervention-points (ms.date 2026-03-02). Four points: "User input", "Tool call (Preview)", "Tool response (Preview)", "Output". Agent guardrails are in preview. Tool call: "The tool call consists of which tool is called and the arguments it's called with, including data being sent to the tool." On detection: "the tool call won't be executed, and the agent stops functioning until there is another user input." For agents the only action is "Annotate and block". Controls are Azure AI Content Safety classifiers (hate, sexual, self-harm, violence, prompt attacks, indirect attacks, protected material, PII) plus Task Adherence; "approximately 50-100ms of latency" per point. Supported tools for tool-call and tool-response moderation: Azure AI Search, Azure Functions, OpenAPI, SharePoint Grounding, Fabric Data Agent, Bing Grounding, Bing Custom Search, Browser Automation; "If you configure controls at tool call or tool response intervention points but your agent uses tools not in this list, those controls won't take effect for those specific tools." MCP tools are not in the list. Guardrail block events are recorded as Defender behaviours ("Block events from Microsoft Prompt Shields for Foundry ... are also recorded as behaviors") and as the Purview `AIGuardrail` activity. The guardrail system "currently applies only to agents developed in the Foundry Agent Service".

**Task Adherence (the one action-aware classifier).** https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/task-adherence (ms.date 2025-08-13, updated 2026-06-05), preview. It evaluates the planned tool call against user intent and returns e.g. `{"taskRiskDetected": true, "details": "Planned action deletes calendar events, but user only requested to view them."}`. Its stated purpose is "To provide a signal for downstream tool invocation blocking and escalation to human-in-the-loop review". It is a signal, not an enforcer, unless wired into a guardrail with "Annotate and block". "customer data might be routed to and processed in US and EU regions outside their specified region." Cloud only.

**Tool approval.** Toolbox (https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox, ms.date 2026-08-26) and hosted-agent guide (https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/use-toolbox-hosted-agent, ms.date 2026-07-29). Each MCP tool in a toolbox version carries `require_approval` = `"always"` | `"never"`, surfaced in `tools/list` as `_meta.tool_configuration.require_approval`. Required runtime behaviour for `always`: "Show the proposed tool name and arguments to the user, wait for an explicit approval, and invoke the tool only after approval. Repeat this process for every call." "The toolbox MCP endpoint doesn't block tools/call when require_approval is always. Your agent runtime must enforce the setting before every invocation. A system-prompt instruction alone doesn't enforce approval." "Use require_approval: never unless your runtime can pause the pending tool call, collect the user's decision, and resume or reject that exact call." The .NET SDK exposes `McpToolCallApprovalPolicy` with `GlobalMcpToolCallApprovalPolicy.AlwaysRequireApproval`. Binding: the user is shown the name and arguments; no hash, token or approval record is defined; enforcement and any record are the runtime's responsibility. The toolbox version is immutable and can carry a guardrail: "The guardrail runs at the toolbox layer, independently of any model-level content filter."

**AI Gateway tools governance (preview, ms.date 2026-08-19).** Routes new MCP tools (not managed-OAuth ones) through Azure API Management; policies are APIM XML (rate limit, IP filter, header removal, routing). "AI gateways don't log tool traces." Audit is APIM diagnostics; policy-blocked calls appear as 429/403.

**Identity and audit.** Foundry provisions an agent identity blueprint and agent identity per project (shared for unpublished agents; distinct on publish, "Agents that need independent audit trails"). Tool calls are authenticated with tokens scoped to the downstream audience; RBAC on the downstream resource decides. Tool-call audit is tracing (Application Insights/OpenTelemetry), Agent 365 observability, Defender behaviours and Purview activities; nothing signed. Foundry Control Plane (ms.date 2026-05-06, preview items) adds fleet inventory, a Compliance pane with Azure Policy, Defender and Purview integration, and "Apply versioned policies and track assignments to maintain full auditability and traceability across agents and environments" — configuration policy, not per-action decisions.

**Criteria.** Action identity: yes at the Tool call intervention point (tool name plus arguments) and in `require_approval` prompts; approval binding: per-call prompt with name and arguments, unhashed, enforced by the runtime not the service; receipt: guardrail block events as Defender behaviours and Purview `AIGuardrail`, tool-call spans in tracing, no signed receipt; enforcement seam: guardrails (listed tools only, content classifiers plus Task Adherence) and the hosted runtime; cloud only; Azure consumption pricing.

## 9. Microsoft Defender for AI agents and Security Copilot

**Cloud agents (Defender XDR).** https://learn.microsoft.com/en-us/defender-xdr/security-for-ai/ai-agent-real-time-protection (ms.date 2026-07-01, updated 2026-09-10). "Real-time protection inspects AI agent activity throughout the agentic loop and blocks risky actions before they execute." **Copilot Studio webhook.** Microsoft Security Blog, 2026-01-23: "Before any tool, topic, or knowledge action is executed, the Copilot Studio generative orchestrator initiates a webhook call to Defender" carrying "the current component's parameters, outputs from previous steps in the orchestration chain, user context, and other metadata"; Defender "decides in real time whether to allow or block the action"; a block is "logged in the Activity History" and "an XDR informational alert will be triggered". **Local agents (Defender for Endpoint, preview).** https://learn.microsoft.com/en-us/defender-endpoint/ai-agent-runtime-protection-overview (ms.date 2026-09-16). **Criteria.** Action identity: yes, the tool invocation with parameters is what Defender evaluates; approval binding: none (allow/block by detection type, not human approval); receipt: `BehaviorInfo` rows / alerts, plain; enforcement seam: pre-execution rule on the gateway/orchestrator, and on-endpoint hooks for supported CLIs; local: interception on the endpoint for the four hook-exposing agents, decision logic and records in the cloud.

## 10. Dapr Verifiable Execution (Dapr 1.18)

**What it is.** Announced on the CNCF blog on 2026-06-11 (https://www.cncf.io/blog/2026/06/11/introducing-verifiable-execution-in-dapr-1-18/), released 2026-06-10 (https://blog.dapr.io/posts/2026/06/10/dapr-v1.18-is-now-available/). Three capabilities: Workflow History Signing ("Dapr can generate cryptographic signatures over workflow history records."), Workflow History Propagation, and Workflow Attestation ("Dapr allows workflows and activities to receive cryptographically verifiable execution context."). Licence: Apache License, Version 2.0 (dapr/dapr LICENSE). Status: History Signing and Propagation are stable in 1.18; signing is "disabled by default" behind the `WorkflowHistorySigning` configuration feature flag.

**What is signed** (https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-history-signing, v1.18, last modified 2026-09-11). Each `HistoryEvent` is marshaled with "protobuf's deterministic mode"; the signing input chains "the SHA-256 digest of the previous HistorySignature protobuf message" with "a SHA-256 hash computed over the batch of marshaled events, with each event length-prefixed (big-endian uint64)". Algorithms: Ed25519 (default for Sentry-generated keys from 1.18), ECDSA P-256, RSA. Key: "the sidecar's SPIFFE X.509 private key" issued by Sentry; SPIFFE ID `spiffe://<trust-domain>/ns/<namespace>/<app-id>`.

**Receipt form.** Per workflow in the state store: `history-NNNNNN` (HistoryEvent), `signature-NNNNNN` (HistorySignature: signature bytes, certificate reference index, covered event range `[start, end)`, previous-signature digest), `sigcert-NNNNNN` (own DER X.509), `ext-sigcert-NNNNNN` (foreign certificates from attestations), `metadata`. Cross-app attestations `ActivityCompletionAttestation` / `ChildCompletionAttestation` carry `parentInstanceId`, `parentTaskScheduledId`, `ioDigest` (SHA-256 of input/output), `signerCertDigest`, `terminalStatus`, activity name. Verification walks the whole chain: linkage, contiguity, digest recomputation, signature, certificate validity at event time, chain to the Sentry trust anchor, SPIFFE app identity equals the workflow's owning app, full coverage from index 0. On failure "the actor appends a terminal ExecutionCompleted event with the well-known error type DAPR_WORKFLOW_HISTORY_TAMPERED, terminates the in-flight workflow". Once a workflow starts signed it must stay signed.

**Caveats.** mTLS is required: "Without mTLS, signing is silently disabled." In self-hosted mode "mTLS is disabled by default" and Sentry must be run explicitly (`./sentry --issuer-credentials $HOME/.dapr/certs --trust-domain cluster.local`). Self-hosted operation is supported (docs give self-hosted and Kubernetes instructions); the whole stack is local open-source code with no cloud dependency.

**Relation to agent tool calls.** The 1.18 `MCPServer` resource (https://docs.dapr.io/developing-ai/mcp/mcp-server-resource/) exposes MCP tools as workflows: "Tool calls run as workflow activities backed by Dapr Scheduler reminders." Hooks `beforeCallTool` (can deny), `afterCallTool`, `beforeListTools`, `afterListTools` support "argument-level authorization, audit logging, and PII redaction"; `WorkflowAccessPolicy` is "coarse-grained, appID-keyed, enforced at the workflow boundary". The MCPServer page does not mention history signing; that signed histories and completion attestations therefore cover MCP tool-call activities is derived from the two pages together, not stated by either.

**Criteria.** Action identity: activity name plus `ioDigest` in the attestation, workflow history events; approval binding: none (no approval concept); receipt: yes, SPIFFE-signed hash-chained history and completion attestations, verifiable offline against the Sentry CA; enforcement seam: MCPServer hooks and WorkflowAccessPolicy (alpha per release notes); local: yes.
