How Windows keeps a program in its box

A plain-language primer for the coder-containment decision. Written 2026-10-10 for the Lead Architect and updated 2026-10-11 with the measured results (#1740). Reading time about 15 minutes.

The short version

Windows has one lock system for files, called access control lists, and several ways to give a running program an identity those locks can recognise: a dedicated user account (what BlarAI uses today), a restricted token, an AppContainer, and Microsoft's new agent container (MXC), which is built on the AppContainer idea. They are not rivals. The locks are the same; the three differ in what the program is allowed to touch before anyone writes a lock for it. A dedicated account starts with everything ordinary accounts can reach and has to be narrowed. An AppContainer starts with very little: it can read Windows and Program Files through a built-in group, and everything else has to be granted. That single difference is why another project, nono, prefers AppContainer, and why BlarAI has spent weeks closing folders that a plain account could write.

1. The building

Picture Windows as an office building. Every program that runs is a person walking around inside it. Two things decide where that person can go:

  • The badge they carry. Windows calls it an access token. It says who the person is (their security identifier, or SID, an internal name tag), which groups they belong to, and which special powers they hold.
  • The guest list on each door. Every file and folder has one. Windows calls it an access control list (ACL). Each line on it is an entry that says "this identity may read" or "this identity may write" or "this identity is refused".

When a program tries to open a file, Windows itself (not the program) compares the badge to the guest list. The program cannot skip the check, argue with it, or crash its way past it. That is the whole reason BlarAI's containment work uses these mechanisms: the study of earlier ideas found that protections the agent's own software runs can be skipped, and these cannot.

A child program started by a program carries a copy of the parent's badge. So a badge is a way to bind everything a program starts, including build tools the agent launches.

2. NTFS access control lists (the locks)

NTFS (New Technology File System) is the format of your C: drive. It is what stores a guest list on every file and folder.

  • Allow and refuse lines. Windows reads the lines in order and the first one that matches decides. The standard order is: refusals written on the folder itself, then allows written on the folder itself, then the lines inherited from above, nearest level first, with refusals before allows at each level. So a refusal written on the folder beats an allow, but an allow written on the folder comes before a refusal inherited from above. A refusal is reliable when it is written on the folder itself.
  • Inheritance. A folder's lines flow down into everything created inside it. This is convenient, and it is also how a broad line at the top of a drive reaches a folder you thought was private. BlarAI found exactly this: C:\blarai-fleet inherited a line letting every signed-in local account modify it (ticket #1686).
  • What they cover. Every object Windows protects: files, folders, the registry, processes, pipes, shared memory. They do not stop a program from connecting to the internet. That needs a different tool: BlarAI's network block uses the Windows Filtering Platform (WFP), a rule engine inside Windows that can say "connections from this identity are refused".
How BlarAI uses them

The coder account has no allow line on your secrets (your SSH keys, BlarAI's keystores), so Windows refuses it. That was tested and passed on 2026-07-10 (check 2).

3. Dedicated user account (the design BlarAI chose)

Create a separate Windows login, blarai-coder, and run the coder under it. Its badge carries a different name tag from yours, so every guest list that names only you refuses it. Anything it starts carries its tag, which is also what lets the network rule single it out without touching your own traffic.

Strength: everything normal software expects (a profile folder, a temp folder, a registry) still exists, so the coding tools just work. It is cheap and well understood.

Weakness: a new account is not empty-handed. It belongs to broad groups such as Users and Authenticated Users, and every place that lets those groups in, lets it in. BlarAI has already found these on record: a throwaway restricted account could write the model folder B:\models and C:\Windows\Temp on 2026-10-05 (#1689, #1692). C:\Windows\Temp has carried a protected list naming only SYSTEM and Administrators since some time after 2026-10-08 21:59 and still does (ticket #1742); the folder itself cannot say when it was locked. Also found: the fleet folder as above (#1686), and the coder held write rights on all of your projects folder (#1678). Containment here means finding and closing each one. It also does not hold against an attack on Windows itself.

4. Restricted token (your badge, with parts crossed out)

Instead of a new identity, you run the program as you but hand it a weakened copy of your badge. Windows lets you do three things to the copy: switch a group off so it can only be used to refuse, strip special powers (for example administrator powers), and add a second, shorter list so that every door must pass both the normal check and the short list.

Strength: no extra account, no login, can be made per launch.

Weakness: it is still you. The simple form (what the 2026-09-17 study measured) removes administrator powers and little else: the process could still write freely to the user folders. Measured in #1740 with the same test program in every setup:

  • Write-restricted form (the second list is checked only when the program writes; this is what OpenAI's Codex uses). It confined writes to the one folder named in the list and refused every folder that broad groups can write (all 6 such folders, in each of 3 runs; the predictions matched 48 of 48 over all 16 folders). It does nothing for reads: your secrets stayed readable, and the internet stayed open.
  • Fully restricted form (the second list is checked on reads too, with a broad list as Chromium uses). It refused all five secret paths, because only your own account is allowed to read them, but it still read what broad groups can read and still wrote where broad groups can write (B:\models, the fleet folders).
  • Network rule. A write-restricted token looks exactly like you to a network rule and cannot be singled out. A fully restricted token can: a rule that blocks "you plus the extra identity" and a higher-priority rule that permits "you alone" blocked only the fully restricted program (three of three runs; the rule was limited to one test program so it could not touch your own traffic). OpenAI's statement that Windows Firewall rules cannot do this concerns firewall rules; the lower-level filter can.
  • Tools. node, git and Python start under both forms. git-bash does not (its runtime creates an object in a shared Windows namespace that a restricted token is refused), and opencode's launcher failed under the fully restricted form.
  • Getting it to start at all. A restricted token only launches when it is made in one step from the launching program's own token, and its own default access list must name the extra identities; without that the program dies in a twentieth of a second.

5. AppContainer (the sealed room)

AppContainer was built for Microsoft Store apps, but any program can be started inside one. Instead of "a person plus a list of rooms to refuse", it is "a person who starts in a sealed room that has a window onto Windows and Program Files, and is handed keys one at a time".

  • Default deny. Windows checks the usual badge and a second identity belonging to the container. A folder that merely allows "all signed-in users" does not admit it; the folder has to name the container, or the built-in group "ALL APPLICATION PACKAGES" (for the stricter low-privilege container, "ALL RESTRICTED APPLICATION PACKAGES"). Windows grants that group on its own folders and Program Files: on this machine it covers C:\Windows, most of Program Files and System32, so a folder that grants it admits the container. A regular container can read what that group is granted and nothing else unless granted by name. On this machine that group can read C:\Program Files\Git but not C:\Python314 or C:\Program Files\nodejs, and a launched container could not start Python or node from their real folders.
  • Refusals cannot carve it out. A refusal line naming the container, the group "ALL APPLICATION PACKAGES" or one of the container's capabilities does not refuse the container, while a refusal naming your own account still does. Lines that name the container can only add access. No Microsoft page states this; the container-naming refusal held in Windows' access check, in a real file open, and in 12 of 12 launched containers; the group and capability forms were checked in the access check only.
  • Network is a permission. No internet unless granted (measured: blocked until the internetClient permission was added). Connections to your own machine (localhost, which is how the coder reaches the model) are also blocked unless a special exemption is set; the exemption worked from an administrator console and was removed afterwards. A network rule can single out one container by its identity (measured: it closed the internet again after internetClient opened it).
  • Lower trust level and its own private corner of the registry and of Windows' internal object names.

Strength: it removes the "everything the broad groups can reach" problem at the start: in the tests only the folders granted by name were writable, and secrets were refused. It needs no extra account.

Weakness: most developer tools were not written for it. With copies of the tool folders made readable to it, node, git and Python started; git-bash did not (under a restricted token it failed with a different recorded error than the container's shared-namespace one) and opencode's launcher script failed. Every folder the tools need must be granted or copied (so it still relies on the access lists above). A container profile is kept per user until deleted; the tests created and deleted it each time.

6. Microsoft's agent container (MXC)

MXC is Microsoft's open-source container for running agents' code on Windows (version 1.0.0, released 2026-10-07; OpenAI's Codex documentation now recommends it over its own sandbox). Its first tier uses an operating-system container API: no administrator preparation, a separate network rule per container made by Windows itself, and a signed launcher. Measured on this machine (Windows build 26200.9457):

  • The launcher's signature is valid (Microsoft), its release archive matches the published checksum, and its self-check reports the operating-system container tier with no change to any access list.
  • The container is as strict as the AppContainer: secrets refused, only the work folder writable (even the throwaway folders that grant broad groups write access were refused), no network unless allowed.
  • Its default turns off Windows' graphics layer, which stopped node, git and Python's ctypes; with that setting relaxed node, git and Python started. git-bash and opencode's launcher failed.
  • It cannot reach localhost on this Windows build: the launcher refused the setting ("not supported by this version of Windows"), including the proxy form. The coder reaches its model over localhost, so this build cannot use it for the coder.
  • Granting folders did not change their access lists, and each run left no registry key behind.

8. What this means for the decision

Be clear about the limits

The coder's tools have not been run inside any of these setups with the model in the loop, and the dedicated account itself has not been run on the same test program (only you can run that; the script is arm_a_operator.cmd). The numbers come from one machine, one Windows build, one antivirus, three runs per setup.

  • nono's proposal (a draft, number NEP-0005) says: network block first, then AppContainer as the main way to confine files and processes, with a dedicated user plus restricted token plus file locks as the documented fallback. Its open question 1 is "Does AppContainer hold up?"; its open question 3 is uninstall and repair of persistent state. BlarAI's design is that fallback plus that first phase. This was read from the raw file at commit 62bb720b on 2026-10-10. Measured here: an AppContainer holds on files and network, and does not run the coder's git-bash.
  • The practical question was whether the coder's tools can run inside an AppContainer or Microsoft's container here, reaching the model over localhost with only the work folder granted. Answer so far: node, git and Python can; git-bash and opencode's launcher cannot; the model cannot be reached from Microsoft's container on this build and needs an administrator exemption from an AppContainer. The recommendation is in docs/research/windows-containment-comparison-2026-10-10.md.
  • The ceremony is not waiting for this. Flipping containment on is still the next step and is strictly better than today, where the coder runs as you.
