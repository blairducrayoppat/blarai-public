# Runtime action governance for AI agents: the landscape measured against BlarAI's trust spine

*Written 2026-09-16. Compiled from the four documentation-level surveys of the same date (`landscape-anthropic-agent-governance-2026-09-16.md`, `landscape-openai-google-agent-governance-2026-09-16.md`, `landscape-microsoft-other-agent-governance-2026-09-16.md`, `landscape-standards-academic-oss-agent-governance-2026-09-16.md`) and the five research documents on #1537 (the grounding read; the comparison; the placement of Proof-Carrying Agent Actions (PCAA); the verdict on the Agent Governance Toolkit (AGT); the design for adopting the Agent Control Specification (ACS) vocabulary). BlarAI's facts are the claim register's (`docs/governance/trust-spine-claim-register.md`, rows cited by number) and code read at commit `12e3b651`. Nothing here is built. Every recommendation is marked [PROPOSED], and every one that rests on a documentation-level survey is marked "source read required before design".*

## The name and the five questions

"Runtime action governance for AI agents" (short form: agent action governance) is the engineering layer one level below organisational AI governance. Organisational AI governance (the NIST AI Risk Management Framework, ISO/IEC 42001, accountability structures) has adopted nothing yet about the object studied here. This layer asks five questions about one runtime:

1. **Action identity.** What is the action at the decision point: a display string, a tool name plus arguments, an opaque call id, or a canonical object with a content-derived fingerprint?
2. **Approval binding.** When a human says yes, what does the yes attach to: a pattern, a tool name, a call id, or the exact content that will execute, checked again before it executes and consumed once?
3. **Receipt.** What record of the decision survives, does it include denials, and is it hashed or signed so that it cannot be edited afterwards?
4. **Enforcement seam.** Where in the runtime is the decision enforced, does code in the path stop the action, and what happens on error?
5. **Local operation.** Does the decision run on one machine with no vendor call, or does some part of it (the verdict, the model, the metering, the record) leave the host?

Out of the name, and out of this matrix except where they touch an action decision: model governance, organisational AI governance, content safety (prompt-injection and toxicity classifiers), and observability. In BlarAI's own terms this is the trust-spine landscape: the Policy Agent's deterministic checker, the two live doors, the per-turn Windows Hello envelope, the escalation-consent path, and the signed audit chain, measured against everything the surveys found.

## Outcome first

**No surveyed vendor ships all five.** Across the 110 rows scored below, exactly one artefact scores Y on identity, binding and receipt together, and it is a single-author open-source reference (the Agent Passport System). Six more have the canonical identity and the content-bound approval with a hashed but unsigned record: the open core of Canonical Action Verification and Attestation (CAVA), OSuite's governed-action core, the `responsibleai` Agent Hooks contract, Microsoft Agent Framework's implementation of that contract, the Agent Control Specification crate, and the Agent Governance Toolkit that pins that crate. None of the four large vendors' hosted governance surfaces produces a content-bound approval identity or a signed per-decision receipt; their combined count on those three questions is zero.

**On action identity and approval binding, the field's best is small, specific, and already designed into BlarAI's queue.** The strong pattern appears six times in the surveys and in every case is the same idea: hash a canonical form of the action, hand the hash to the approver, re-derive it immediately before execution, refuse on mismatch, consume the approval once. Agent Hooks (`context_identity`), the Agent Control Specification (§17.1), CAVA's `verify.js`, OSuite's hash-bound lease, Mastra's `beforeToolCall` approval, and Agent Framework's Flow Integrity Deterministic Enforcement System (FIDES) all do this. Most of the field does not: Claude Code persists approvals as text patterns, the OpenAI Agents SDK's `always_approve` deliberately unbinds arguments for the rest of a run, Managed Agents and Google's Agent Development Kit bind to opaque ids, and Foundry's `require_approval` shows the arguments and records nothing. BlarAI today binds an escalation approval to a tool name and a rule label (register row 27, Gap A, #1541); the canonical hash that would close it is defined on the Canonical Action Representation and never computed on the live path. This is the one question on which the field's best is clearly ahead of BlarAI, and the fix is the design already on disk.

**On receipts, BlarAI has stronger machinery than any big-four surface and it is wired to the wrong door.** Every large vendor's decision record is a plain row: OpenTelemetry events and plaintext transcripts (Anthropic), spans shipped to the vendor by default (OpenAI), Cloud Logging entries (Google), Purview and Defender rows (Microsoft). Signed, hash-chained per-decision records exist only in open source and academic work: Dapr 1.18, Aegis, the Agent Control Protocol, the Agent Passport System, Pipelock, Audita. BlarAI's `AuditLog` is in that second class, with a Trusted Platform Module signer rather than a software key, but it serves the ingest path and a vestigial adjudicator while the two live doors write log lines (register row 28, Gap B, #1542). Two further facts read from code for this document: the chain's `verify()` is called only from test files and by no production code, and the load path restores the chain head from the last record without verifying anything. The field's one verify-on-load pattern (Dapr, which terminates the workflow on tamper) is the single most useful new idea in the surveys for BlarAI, and it is proposed below.

**On the enforcement seam and local operation, BlarAI leads the field, and by a wide margin.** The surveyed seams are cooperative in-process hooks (ADK callbacks, Claude Code `PreToolUse`, Agent Hooks, Semantic Kernel filters, OpenAI tool guardrails), network gateways (Google's Agent Gateway, Defender, the MCP-gateway crowd), or OS sandboxes for shell commands (Claude Code, Codex). No surveyed item has a process-wide socket guard, a single exempted network importer enforced by a scan, an empty-by-default adjudicator slot that denies every fetch, signed weight manifests verified at boot, or born-encrypted stores. Every big-four governance service is hosted; the local ones still call home for something (Claude Code's `WebFetch` hostname check, Prompt Shields' metering, OpenAI's default trace exporter, every model call). The field is also moving toward model-judged verdicts (Google's semantic governance policies, whose documentation says verdicts "may not be accurate"; Anthropic's auto-mode classifier and Managed Agents' `auto` policy; Foundry's Task Adherence). BlarAI's rule in Architecture Decision Record (ADR) 041 that the probabilistic layer may only tighten a deterministic allow is the opposite posture, and this compilation found nothing in the field that argues for changing it. The open seam-level item is Gap C (#977): the agreement between the two egress layers rests on one boot-time check, and the door slot's docstring says first-wins while its body implements last-write-wins (register row 2).

**Which external ideas join the proposed list: four small ones, none of them new capability.** They are stated in the [PROPOSED] section: verify the audit chain at boot and fail loud on tamper; a `decision_source` field on the receipt; a regression lock that approval text arriving inside untrusted context never lifts an escalation; and the six-question Auditability Card as the shape of the coverage-disclosure table. Everything else the field does either BlarAI already has, is already on the eleven-item list, or is rejected with a reason. Adopting no external software remains the settled call: not Agent Framework, not the Agent Governance Toolkit, not any hosted control plane, not a Model Context Protocol (MCP) gateway (BlarAI has no MCP surface, and adding one would be a capability decision, which is the Lead Architect's (LA's)).

## How every row was scored

The four surveys closed with three different legends (prose cells in the Anthropic and the OpenAI-and-Google surveys; Yes/Partial/No with a cloud-versus-local column in the Microsoft survey; Y/P/N in the standards survey). Every cell below was re-scored under one legend from the survey's prose, not copied from its table, so a survey "Yes" can read "P" here; where that happened the cell's qualifier says why. Cooperativeness is not a demotion on the seam column: every in-process hook is cooperative, and only a documented gap (partial coverage, annotate-only, a selectable fail-open, a default-allow library, records without gating) moves a row from Y to P. Documentation-level rows carry the surveys' own caveat: nothing was run, and every "unsigned" or "bound" is what the documentation says.

| Column | Y | P | N |
|---|---|---|---|
| Identity | A canonical object or content-derived fingerprint of the action (hash over a normalised form) exists at the decision point | Tool name plus arguments, an opaque per-call id, or a partial object; no canonical fingerprint, or one that is internal and never surfaced | No action object; the surface governs content, identity, or nothing at the action level |
| Binding | The approval carries a content-derived identity of the action, re-derived or compared before execution, single-use | The approval attaches to a specific call (opaque id, or the in-flight object) but without a content identity, or it can be widened to future calls (pattern rules, "always approve", a multi-call window), or the pending approval is stored unsigned | No approval concept |
| Receipt | A per-decision record that is signed or hash-chained, verifiable after the fact | A per-decision record exists but is plain (unsigned, editable), or is only what an integrator's hook writes | No decision record is defined |
| Seam | Code in the execution path blocks the action before it runs, covering the calls the surface claims to govern; an in-process hook the host must honour still counts, because every surveyed seam is cooperative | Partial: only some tools are covered, the surface annotates or scans content rather than blocking calls, a fail-open mode is selectable or the library's default is allow, or it records without gating | A document, a design or position paper with no artefact in the path, an evaluation harness, or an identity system with no action seam |
| Local | Runs on one machine with no vendor call for the decision, the model, or the record | Part of it leaves the host (the model, a metering call, a hostname check, a default exporter, a cloud record) | A hosted service |

Read depth: **S** = source read and, where possible, run locally (the five #1537 documents); **D+S** = documentation plus specific published source files read; **D** = documentation-level survey; **D-** = search-result summaries only, marked n.v. (not verified) in the survey; **Paper** = the paper read in full. Form: cloud service, local code, protocol or spec, document, paper. Licence is as the survey found it; "n.v." means the licence file was not read.

## Verdict per vendor and group

**Anthropic.** The richest local in-process seam of the four vendors (a `PreToolUse` hook whose deny holds in every mode, deny rules evaluated after a hook allow, absolutised paths, an OS sandbox with an empty default network allowlist) attached to the weakest binding model: approvals persist as text patterns, `PermissionRequest` does not even receive the per-call id, and the only persisted pending-approval object (`defer`) is plain JSON. Managed Agents adds a server-side decision record with machine reason codes and a confirmation that must cite a specific event, which is the best receipt shape among the hosted services and still unsigned and unhashed. Nothing Anthropic ships produces a canonical action, an action hash or a signed receipt; the Model Context Protocol, which Anthropic donated, defines none of these either and says so. For BlarAI the borrowable ideas are all vocabulary: `decision_source` on the decision event, `reason_code` as a value to branch on rather than text to display, and the agent-teams rule that a relayed approval is untrusted input.

**OpenAI.** One real action-level primitive, the Agents SDK's `needs_approval` interruption, and it is instructive in both directions. Python already computes a SHA-256 fingerprint over the tool name and normalised arguments to match approvals, then never shows it to the approver or writes it anywhere; the run state that holds a pending approval is unsigned JSON; `always_approve` unbinds arguments for the rest of the run on purpose. Codex is the only OpenAI surface with a decision record, opt-in and unsigned. The 2023 governance paper names approval, action ledgers and attribution as practices and the 2026 framework does not mention agents. Two closed repository issues asked for exactly the authorisation layer this document is about.

**Google.** The Agent Development Kit has the richest in-process seam of any surveyed framework (`before_tool_callback` can allow, substitute a result, or mutate arguments; plugins run first and globally) and a confirmation that embeds the original call verbatim and re-executes it as stored, which is per-call binding by construction without a hash, marked experimental. The cloud stack is the clearest statement of where the large vendors are heading: a network gateway as the enforcement point (GA), a per-agent cryptographic identity (GA), deterministic tool-level allow and deny with dry run (GA 2026-08-31), and a model-judged intent engine (Preview) whose own documentation says verdicts may be wrong. All records are Cloud Logging rows; nothing runs locally except ADK and the A2A protocol, which has no approval message and no audit format.

**Microsoft, all four layers.** Microsoft is the only vendor whose stack contains the strong pattern: the `responsibleai` Agent Hooks contract and the Agent Control Specification hash the canonical context the approver saw and refuse execution on mismatch, and the crate is fail-closed in code. Both are cooperative in-process contracts that say so, both are experimental or alpha, their records are hashed but unsigned, the toolkit around them has hard network dependencies and a subprocess policy engine, and the settled call not to adopt any of it as software stands. Everything above that layer (Agent 365, Entra Agent ID, Purview, Foundry, Copilot Studio, Defender) governs agents as identities and servers as units, records plain rows, and runs in the cloud; the per-action user confirmations (Microsoft 365 Copilot's non-GET plugin prompt; Foundry's `require_approval: always`) are unhashed and unrecorded. Dapr, placed in the Microsoft survey by origin (an origin that survey took as given and did not re-verify), is the only mainstream runtime that signs execution records and verifies them on load, and it is a sidecar control plane with mutual TLS off by default, so it is a pattern to copy and not software to run.

**Standards bodies.** Nothing standardises an action identity or a decision receipt. OWASP's Agent Control Standard is the Microsoft specification in a new home (an inference from its AGT dependency; no page names the donor) and adds `ask` and `defer` dispositions without stating a hash binding. NIST's initiative, the CSA guidance, CoSAI's principles and ISO/IEC 42001 are documents; the NCCoE concept paper's premise, per the survey's search summary, is that per-action human authorisation is impractical at agent speed, which is the opposite of BlarAI's posture and worth knowing as the direction of the standards conversation. The two open proposals worth watching are the in-toto `agent-decision` predicate (a signed per-decision record shape with the tool and a SHA-256 argument digest) and the OpenTelemetry tool-risk attributes; both have no maintainer response.

**Open source.** The MCP-gateway field is crowded and shallow on these five questions: every gateway matches on tool name and raw arguments, only Pipelock canonicalises before hashing, only Pipelock and mcpkernel sign per call, and only three (MCP Guardian, Pipelock's `ask`, the mcpg Slack plugin) put a human on an individual call. Mastra's `beforeToolCall` approval is the cleanest framework-level statement of the strong pattern (single-use, same canonical arguments, drift blocks). BlarAI has no MCP surface, so the gateways are references only; adding an MCP surface would be a capability decision and is the LA's.

**Academic work.** The 2026 papers converge on the same object BlarAI is missing at its doors: a canonical or content-addressed action, a signed and chained per-decision record, and an explicit disclosure of what the record does and does not prove. The Agent Passport System does all three in running code with a `scope_of_claim` on every receipt; Auditable Agents adds the Auditability Card as a six-question coverage disclosure and reports signed hash-chained records at 8.3 ms median; the Agent Control Protocol adds single-use signed execution tokens; the Black Box paper anchors approvals separately from tool parameters so that "approval preceded execution" is checkable. All are single-group references with unverified licences or code, and every borrow from them carries "source read required".

## BlarAI against the field, question by question

**1. Action identity.** The field's best is a canonical, hashed action object: CAVA's nine-field schema, the Agent Control Specification's canonical input, the Agent Passport System's content-addressed reference. Most of the field, including every big-four surface, is a tool name plus arguments plus an opaque call id, and the only vendor that computes a content fingerprint (OpenAI's Python SDK) hides it. BlarAI's Canonical Action Representation is CAVA-shaped, carries source, destination, verb, resource, canonical arguments and sensitivity, and defines a hash over exactly the right fields (timestamp and request id excluded, which the ACS design argues is correct for BlarAI's turn-scoped envelope). The gap is that nothing computes it on the live path, and that the CAR lacks the four fields CAVA's open schema requires (category, systems touched, reversibility, target), which exist elsewhere in BlarAI's risk-tier and tool metadata. Position: one function call behind the field's best; proposed item 4 (extend the CAR) is the design work, and the field adds evidence for its field list (CAVA's schema, PCAA's externality context, Agent Hooks' `content_hash`).

**2. Approval binding.** The field's best is content-bound, re-derived before execution, single-use: Agent Hooks, ACS §17.1, CAVA's `verify.js`, OSuite's lease, Mastra, FIDES. BlarAI binds an escalation approval to a tool name and a rule label (register row 27), and the per-turn Hello envelope covers up to three searches per touch by an LA decision that is disclosed rather than hidden. This is the one question on which the field is clearly ahead, and the design for closing it is on disk (`acs-vocabulary-adoption-design-2026-09-16.md`, "The approval binding", #1541): put `sha256:` plus the CAR hash in the escalation context as a descriptor, echo it in the verifier's result, recompute from the CAR about to dispatch, refuse on mismatch with `host_error:approval_identity_mismatch`, consume once. Two field observations sharpen that design without changing it: Claude Code's `PermissionRequest` path receives no per-call id, which is the exact defect to avoid on BlarAI's TUI-prompt verifier (the design's step 3 covers it, and the regression lock below pins it); and Managed Agents rejects a confirmation for any event whose permission was not `ask`, which is the invariant "no approval without a pending escalation" that the design's consume-once step should also assert.

**3. Receipt.** The field's best is a signed, hash-chained per-decision record that includes denials: Dapr, Aegis, ACP, APS, Pipelock, Audita, and the in-toto predicate proposal; none of the four vendors signs anything. BlarAI's `AuditLog` is stronger than any of them on the signer (a TPM key on the chip rather than a software key) and equal on the chain, and it serves ingest while the two live doors write log lines (register row 28). Two facts from the code narrow the picture further. `AuditLog.verify()` is called only from test files; no boot path, no health check and no ceremony invokes it. `_load_existing` restores the chain head from the last record on disk without recomputing a hash or checking a signature, so a tampered active segment would be extended rather than refused. Dapr's pattern (verify on every state load, append a terminal tamper event, refuse to continue) is the single new idea in the surveys that BlarAI's own code shows a need for, and it is proposed below. Position: machinery ahead of the field, wiring behind it; #1542 is the wiring, and the verify-on-load item (#1543, register row 29) is the piece #1542's design did not contain.

**4. Enforcement seam.** The field's seams are cooperative hooks, gateways and shell sandboxes, and the in-process ones say in their own documentation that they are not a boundary against a host that skips them. BlarAI's in-process checker is the same shape as the cooperative hooks and stronger on error handling than most (any exception denies; malformed arguments in the OpenAI SDK force manual approval, which is the nearest equivalent), and it sits inside a perimeter no surveyed item has: a process-wide socket guard with a latched kill switch, an outbound payload screen, one permitted network importer enforced by a scan, an empty-by-default door slot, signed manifests verified before every model load. The field is adding model-judged verdicts at the seam (Google semantic governance, Anthropic auto mode, Managed Agents `auto`, Foundry Task Adherence); ADR-041's rule that the probabilistic plane may only tighten a deterministic allow is the opposite choice, and nothing in the field's own documentation of those engines ("Verdicts may not be accurate"; "not a human checkpoint") argues against it. The open seam item is Gap C (#977): the two egress layers agree only while the deterministic adjudicator holds the door slot, the slot's docstring says first-wins while the body implements last-write-wins, and the honest fix named in BlarAI's own test docstring is an executable boot-time posture check. Agent Hooks' single-bundle rule (agent, chat and function parts install together or not at all) is the field's version of the same fix. Position: ahead of the field; one known open item, already ticketed.

**5. Local operation.** Every big-four governance service is hosted. Of the local ones, Claude Code sends each fetched hostname to Anthropic, OpenAI's SDK ships traces to OpenAI unless told otherwise, Prompt Shields' container stops serving if it cannot report billing, Defender for Endpoint decides in the cloud, and every framework needs a model endpoint that on this hardware would be BlarAI's own. Fully local with no vendor call: ADK with Ollama, Agent Framework with Ollama (no OpenVINO provider), Agent Hooks and the ACS crate (with a compiled-in HTTP client), Dapr self-hosted, the MCP gateways, and the academic references. BlarAI runs the decision, the model, the approval (Windows Hello on-chip) and the record (TPM signer) on one machine with a verified boot, and the LA's 2026-09-16 constraint that no external hosted governance service ever touches the runtime removes every hosted item from consideration by decision, not by score. Position: ahead of the field; no surveyed item is as local as BlarAI while also carrying a model.

## [PROPOSED] additions to the list, and what is rejected

The eleven numbered items on disk are the comparison document's 1 to 7 (item 7 landed as `docs/governance/trust-spine-claim-register.md`, #1539) and the PCAA document's 8 to 11; items 1, 2, 8 and 9 are covered by #1542 and #1541, item 3 by #977. The ACS design restates items 1, 2, 6, 8 and 9 in the specification's vocabulary. Four ideas from the surveys join the list. Each is a hardening of an existing capability, a test, or a document; none opens a door or changes a posture; each rests on documentation-level survey rows for the external side and therefore carries "source read required before design", as the ticket requires without exception. Nothing is built.

**12. Verify the audit chain on load and fail loud on tamper (#1543; register row 29, Gap D).** [PROPOSED] Borrowed from Dapr 1.18 (verification on every state load; a terminal `DAPR_WORKFLOW_HISTORY_TAMPERED` event; once signed, always signed). Evidence on BlarAI's side is from source at `12e3b651`, not from the survey: `AuditLog.verify()` is called only from test files (`shared/tests/test_audit_log.py`, `shared/tests/test_tpm_record_signer.py`, `tests/integration/test_security_cascade.py`, `services/policy_agent/tests/test_entrypoint.py`) and by no production code; `__init__` calls only `_load_segment_index` and `_load_existing`, and `_load_existing` restores the chain head from the last record without recomputing a hash or checking a signature. Design shape: run the fast `verify()` (active segment plus the segment-index anchor chain) inside the Policy Agent's `_build_audit_log` and the Assistant Orchestrator's `_build_ingest_audit_log`; on `AuditChainError` the Policy Agent refuses to start in production (matching its existing refusal when the audit path is absent) and the ingest sink disables the knowledge feature loudly (matching its existing posture on a missing TPM key); a `verify(full=True)` at the manifest-signing ceremony. Before choosing fast versus full at boot, register the verification budget in `shared/timeout_registry.py` and measure the fast verify's cost over the real active segment: the active segment holds up to 100,000 records and per-record signature checks are TPM-backed in production. This is fail-loud (security-by-design principle 11) applied to a control that already exists. Regression locks: tamper one byte of a record in the active segment on disk, construct the log, assert refusal (the motivating case; a sealed segment is separately caught by the anchor pin); tamper a sealed segment, assert refusal; construct over an untampered log, assert start. Source read required before design: Dapr's `workflow-history-signing` implementation, to confirm the verify-on-load semantics the documentation describes before copying its failure handling. Pairs with #1542 because the doors' receipts are only worth writing into a chain that is checked.

**13. A `decision_source` field on the receipt (recorded on #1542).** [PROPOSED] Borrowed from Claude Code's OpenTelemetry `tool_decision.decision_source` (config, hook, user_permanent, user_temporary, user_abort, user_reject) and Codex's config-versus-user distinction. BlarAI's receipt design already carries `approval_outcome` and `approver_identity` (which verifier answered, never who); a closed enum of where the decision came from (`rule`, `layer3_lock`, `envelope_lease`, `verifier`, `no_verifier`, `operator_abort`) makes a later audit answer "was this allowed by policy or by a person, and through which surface" without joining records, and `approver_identity` keeps saying which verifier, so the two fields do not overlap. A field, not a mechanism; it belongs inside #1542's design as a refinement of the receipt table. Source read required before design: Claude Code's hooks reference for the `decision_source` values, if the enum is to mirror them.

**14. A regression lock that approval text inside untrusted context never lifts an escalation (recorded on #1541).** [PROPOSED] Borrowed from Claude Code's agent-teams rule ("a teammate can't approve a permission prompt or supply consent on your behalf"; in auto mode a relayed approval claim is "untrusted input rather than confirmation from you") and the MCP rule that possession of a state handle is not authentication. BlarAI already has this property by construction: consent comes only from a registered verifier's `ApprovalResult`, and grounded content never gains instruction authority (register rows 10, 21, 22). It has no test that says so. The lock: place the literal strings an operator would type to approve, and a string shaped like an action identity (`sha256:` prefix), inside datamarked document content and inside a tool result; drive a real ESCALATE through the tool loop with no verifier registered, assert denial; register a verifier that denies, assert denial. It pins the invariant so that #1541's identity work cannot accept an identity echoed from context, and it should also assert that a verifier result with no pending escalation is ignored (Managed Agents rejects a confirmation for any event whose permission was not `ask`). Source read required before design: Claude Code's agent-teams documentation, if the lock's threat cases are to mirror its relayed-approval cases.

**15. Shape the coverage-disclosure table as an Auditability Card (#1544).** [PROPOSED] Refines PCAA item 10 (the per-surface interception-depth table for the tool loop, the egress door, coder-fleet dispatch and the vsock services) with the six questions of Auditable Agents' Auditability Card: which actions are recorded, which lifecycle phases are covered, which policies are mechanically checkable, what the responsibility chain is, what integrity protection the records have, and what happens when logs are missing. The ACS design's coverage statement (four intervention points emitted, four not) is the first row of that card; the Agent Passport System's per-receipt `scope_of_claim` is the same idea at record level and, for a single-tenant system with a fixed schema, a schema-level statement is equivalent. Documentation only; it is the honest form of the claim and the shape a certification portfolio reads. Source read required before design: the Auditable Agents paper's card definition was read as HTML; its code was not, and none is needed for a documentation artefact.

Evidence the surveys add to items already on the list, without changing them: item 4 (extend the CAR) gains the field list from CAVA's open schema (`runtime`, `operation`, `category`, `systems_touched`, `reversible`, `target`), PCAA's externality context (destination visibility and ownership, account provenance, external write, reversibility), and Agent Hooks' optional `content_hash`; item 5 (a confidentiality axis) gains FIDES as the only shipped two-axis label algebra and CaMeL's capability labels as the academic form; item 6 (trace the deny-mid-stream persistence path) gains Agent Hooks' verdict-gated persistence rule as the standard to test against; item 2 gains the two invariants named under question 2 above.

**Rejected, with the reason.**

- Model-judged verdict engines at the seam (Google semantic governance policies, Anthropic's auto-mode classifier and Managed Agents' `auto` policy, Foundry's Task Adherence): ADR-041 places action-authorisation trust in the deterministic plane and lets the probabilistic layer only tighten a deterministic allow; the engines' own documentation ("Verdicts may not be accurate"; "not a human checkpoint"; a fail mode that is selectable) argues for that rule, not against it. Any change here is a quality and security posture decision, the LA's, and this document does not propose it.
- Every hosted control plane (OSuite Studio, Managed Agents, Agent 365, Foundry, the Gemini Enterprise Agent Platform, Cloudflare, Lakera): excluded by the LA's constraint of 2026-09-16 that no external hosted governance service ever touches the runtime.
- Microsoft Agent Framework and the Agent Governance Toolkit as software: settled in the comparison and verdict documents; the reasons (structural absence, experimental Python-only security layers, no OpenVINO provider, hard network dependencies, release cadence) are unchanged by anything in the surveys.
- MCP gateways and firewalls (agentgateway, ToolHive, MCP Guardian, Pipelock, mcpkernel, the rest): BlarAI has no Model Context Protocol surface; the gateways govern a seam BlarAI does not have. Adding an MCP surface would change what BlarAI can do and is the LA's decision, not a hardening item.
- Dapr as a runtime: a sidecar control plane with a certificate authority, mTLS off by default and signing silently disabled without it; the wrong shape for a single-process local system. Its verify-on-load pattern is taken (item 12); its software is not.
- The Prompt Shields container: a content classifier that phones home for metering every 10 to 15 minutes and stops serving if it cannot; the opposite of BlarAI's egress posture, and content safety is out of the name.
- OpenTelemetry export of receipts (the OTel GenAI conventions, Agent 365 observability, OpenAI's default exporter): an export is an egress. The conventions' attribute names are noted for a future projection if receipts are ever shown outside BlarAI; nothing leaves the host.
- Agent identity systems (Entra Agent ID, Google Agent Identity, SPIFFE-based schemes, AGNTCY badges, signed Agent Cards): BlarAI is one agent on one machine with per-boot mTLS between its own services (register row 16); a fleet identity system governs a problem BlarAI does not have.
- The in-toto `agent-decision` predicate and the CAVA in-toto projection helpers: reference shapes only, for the day a receipt is exported for the portfolio; not proposed, because BlarAI never exports proof today and an export path would be its own decision.
- Dry-run or evaluate-only modes (Google IAM dry run, Agent Hooks `evaluate_only`, Defender audit mode): the ACS design says BlarAI has no evaluate-only posture and should not add one silently; a shadow mode for the checker would be a posture choice and the LA's.
- `simulate-first` as a route outcome (PCAA item 11): unchanged; a capability change and the LA's.
