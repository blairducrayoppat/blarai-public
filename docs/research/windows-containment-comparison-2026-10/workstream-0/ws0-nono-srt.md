### AppContainer limitations stated in the NEP
The NEP does NOT list a limitations section for AppContainer. Everything it says about it (verbatim):
- "FS access is governed by capability SIDs and object ACLs rather than an arbitrary path allow-list, so it is still coarser than Landlock, but it avoids provisioning a persistent user."
- "AppContainer-only, no WFP. Simpler and unprivileged, but AppContainer's network isolation is capability-based and does not by itself force traffic through the proxy the way the WFP SID-fence does; likely leaves egress gaps."
- Option B: "accept whatever AppContainer + a per-process WFP subscription can do without persistent filters — likely no sound egress fence at all."
- "Notably, `srt-win` does **not** use this [AppContainer]."
NOT mentioned anywhere in the NEP: loopback exemption/restrictions, toolchain compatibility, per-launch admin for AppContainer, profile creation cost. (grep-verified absent as topics; these come from other sources, not this file.)

### Threat model
There is NO section titled threat model. Stated threats are in "Motivation" and "Security Considerations": confining "untrusted AI agents on the machine where they run"; surrogate-spawn escapes (schtasks, parent-process reparenting, BITS, RunAs COM); unmediated egress ("highest-value guarantee (no unmediated egress)"); path escape surface (junctions, 8.3 names, ADS, UNC/`\?\`, reparse points); persistent-state attack surface ("That state is itself a target"); credential secrecy (DPAPI, DACL-gated stored password). Privilege model: one-time elevated install, per-run unprivileged via Secondary Logon (`CreateProcessWithLogonW`), "does *not* require `SeAssignPrimaryTokenPrivilege`". Non-goals: container/VM, per-path parity, WSL2.

### Other facts in NEP relevant to #1740
- NEP says srt ships a Windows backend: "I looked at `srt` version from anthropic which already ships a Windows backend (`vendor/srt-win-src`)". Its model: "a dedicated low-privilege user + NTFS ACLs... persistent local account (`srt-sandbox`) ... `CreateProcessAsUserW` under a restricted token, a locked-down job object, a non-interactive window station/desktop, a process-mitigation-policy stack, an explicit handle whitelist, and self-protection."
- NEP's own characterisation of the dedicated-account shape: "idiomatic Windows, but it is coarse and it is *stateful*: an account, ACLs, and a broker survive between runs." and "Robust and battle-tested on Windows, but stateful (persistent account + ACLs) and not per-path/per-invocation." (i.e. criticism is statefulness/coarseness - NOT weaker isolation.)

### Mechanism (quotes)
- README: "The sandboxed process runs under a dedicated `srt-sandbox` local user account ... a Windows Filtering Platform (WFP) egress fence keyed on the sandbox account's SID, and per-session explicit ACEs that grant or deny that SID access to configured filesystem paths."
- Launch (README Security model; launch.rs:117; logon.rs): "the broker calls `CreateProcessWithLogonW` to start a runner as `srt-sandbox`, and the runner spawns the target under a restricted token inside a job object." launch.rs line 255 calls `CreateProcessAsUserW` for the child. Password: "random password stored DPAPI-encrypted in `HKLM\SOFTWARE\sandbox-runtime`".
- Token, token.rs @SHA module doc: "`SidsToDisable = [BUILTIN\Administrators, <every SE_GROUP_LOGON_ID SID in the base token>]` ... `LUA_TOKEN` flag ... All privileges deleted except `SeChangeNotifyPrivilege`. Integrity Level = Medium (same as a normal user process). No `RestrictingSids` array - that breaks Schannel/LSA RPC." Code: `CreateRestrictedToken(base, LUA_TOKEN, Some(&disable), ..., None, // RestrictingSids - intentionally empty`. So the "restricted token" is a LUA token with disabled groups and stripped privileges; it is NOT a write-restricted / restricting-SID token.
- Job object, job.rs: KILL_ON_JOB_CLOSE + JOBOBJECT_BASIC_UI_RESTRICTIONS (clipboard, global atoms, system params, display settings, desktop switching, ExitWindows, cross-job handles). launch.rs sets process-mitigation bits (extension-point disable, font disable, no remote image load, no low-label image load). winsta.rs: isolated window station/desktop. self_protect.rs: rewrites the runner's DACL so the child cannot OpenProcess it.
- Network, wfp.rs module doc: "persist **one machine-wide** filter set - two filters at each of `FWPM_LAYER_ALE_AUTH_CONNECT_V4` and `_V6` (4 total) ... **PERMIT loopback** ... `IP_REMOTE_PORT` is in `[low, high]` (default 60080-60089). No user condition. ... **BLOCK sandbox user** - `ALE_USER_ID` SD ... Matches only tokens whose user SID is `<srt-sandbox SID>`." And: "BFE enumeration is admin-gated ... `wfp status` returns `cannot-read` for a non-elevated caller; the non-elevated readiness check is `srt-win wfp verify` (a behavioral connect probe)." So WFP keying on a USER SID (ALE_USER_ID security-descriptor AccessCheck) is established in shipped code.
- Filesystem (README Security model): "enforced by NTFS discretionary ACLs. The `srt-sandbox` account has no inherent rights on the calling user's files, so at `initialize()` the sandbox writes **additive, inheriting explicit ACEs for the `srt-sandbox` SID only**"; allowWrite -> inheriting MODIFY ALLOW; allowRead -> READ|EXECUTE ALLOW; denyRead/denyWrite -> inheriting DENY ACE plus FILE_DELETE_CHILD DENY on the parent. `reset()` removes them; crash-recovery on next `initialize()`.
- README "Known limitations" (Windows): schannel revocation checks blocked by the fence; per-user tool installs not reachable; per-exec allowRead/allowWrite overrides unsupported; `proxyAuthToken` visible in runner command line; "DNS resolution via the system resolver is not fenced ... `getaddrinfo()` is serviced by the `Dnscache` service running as `NETWORK SERVICE`".

## TASK 4 - Who calls the dedicated-account shape the WEAKER option, and why
Result: nobody credible says "weaker than AppContainer" in those words. What exists:
1. NEP-0005 (lukehinds, nono maintainer; READ raw) prefers AppContainer for STATE reasons, not strength: "Robust and battle-tested on Windows, but stateful (persistent account + ACLs) and not per-path/per-invocation." and AppContainer "minimizes persistent state and stays closest to nono's per-invocation model." It also says AppContainer-only "likely leaves egress gaps", so it keeps the SID-keyed WFP block (needs a user SID). Dedicated-user model = "a documented fallback only". SID-keying = "the design's best idea".
2. srt issue #402 comment by Robinvliet, 2026-10-04 (READ via API JSON; third-party user, srt 0.0.76, Win11 24H2 build 26200). Critique of the SHAPE's filesystem boundary: "So anything on a second volume, and every folder a user creates directly under `C:\`, is open to the sandbox account with Modify. Inside the user profile this does not happen, because the profile has no ACE for these groups." and "The README's security model says the `srt-sandbox` account 'has no inherent rights on the calling user's files'. That holds inside the user profile, but not for the user's files on a second volume or in a folder under `C:\`." Cause: the account token carries Everyone, BUILTIN\Users, NT AUTHORITY\Authenticated Users, INTERACTIVE, so group ACEs apply. Proposed fix: "Making it write-restricted (`WRITE_RESTRICTED`, with the `srt-sandbox` SID and `sandbox-runtime-users` as restricting SIDs) would require every write to be granted to one of those SIDs ... Codex's Windows sandbox takes this route, with a write-restricted token plus a capability SID per writable root." (The Codex claim is the commenter's; I did not verify it.) Issue opener qingzheguo-flash (2026-07-16) asks: "Any roadmap for true default-deny write isolation on Windows (AppContainer/BFS/etc.)?" - unanswered.
3. srt #559 (arleckk, 2026-09-17): named pipes reachable and enumerable from the sandbox user (127 pipes identical inside/outside); "A local named pipe uses `\Device\NamedPipe`, not a network socket, so it never reaches that layer at all" - IPC gap of a plain-user identity.
4. srt README itself concedes DNS via Dnscache is not fenced and per-user tool installs are unreachable; #579 states "One account per machine".
5. nono #2000 (panga) calls srt's design "useful references for a native backend", not weaker. mogul (nono PR #555, 2026-06-15): "I think there's a path via LPAC etc" - a wish, not an argument.
NOT FOUND: any source stating that a restricted-token/dedicated-account sandbox is weaker than AppContainer on isolation grounds; any srt maintainer statement on AppContainer plans (zero AppContainer hits in the repo at HEAD).
