## T1a. OpenAI Codex Windows sandbox docs  [READ-P: official docs page raw markdown]
URL: https://developers.openai.com/codex/windows.md (title "Windows sandbox"; raw markdown fetched with curl, saved cx/win.md)
- Three implementations (verbatim): "`mxc`: The recommended sandbox on compatible Windows devices. Uses native process isolation without administrator-approved setup, additional Windows accounts, or local firewall rules."
- "`elevated`: The preferred legacy fallback when MXC is unavailable or disabled. Requires administrator-approved setup. Commands in the sandbox run without administrator privileges."
- "`unelevated`: A legacy fallback when elevated setup is unavailable ... Has weaker network isolation than `elevated` and doesn't support denied read paths."
- elevated mechanism (verbatim): "`elevated` ... uses dedicated lower-privilege sandbox users, filesystem permission boundaries, firewall rules, and local policy changes needed for commands that run in the sandbox."
- unelevated mechanism (verbatim): "It runs commands with a restricted Windows token derived from your current user, applies ACL-based filesystem boundaries, and uses environment-level offline controls instead of the dedicated offline-user firewall rule. It provides weaker network isolation than `elevated` and doesn't support denied read paths".
- Both legacy modes: "By default, both legacy sandbox modes also use a private desktop for stronger UI isolation."
- Setup failure causes (verbatim list): UAC declined; "the machine does not allow firewall rule changes"; "the machine blocks the logon rights needed by the sandbox users"; error 1385 = "Windows is denying the logon type the sandbox user needs".
- MXC compat (verbatim): "The host must already have the required Microsoft Execution Containers (MXC) capabilities, which Microsoft is rolling out to Windows 11 devices. Microsoft introduced MXC process isolation in **Windows 11 24H2 (build 26100.9278)** and **25H2 (build 26200.9278)**."
- Test cmd needs Codex CLI >= 0.162.0. Enterprise opt-out: requirements.toml `[windows] allow_mxc = false`.
=> KEY: "MXC" = "Microsoft Execution Containers" (Windows 11 24H2/25H2 build .9278+). Codex made it preferred and demoted the user/ACL/firewall design and the restricted-token design to "legacy". This machine is Win11 26200 (25H2) -> check UBR (>= 9278?).

## T1b. Codex source: windows-sandbox-rs  [READ-P: raw source via raw.githubusercontent.com at main HEAD cc7ba33601286a751477832b01de7b6f8de0dd9c (2026-10-10)]
Path: codex-rs/windows-sandbox-rs/src/ (also codex-rs/windows-sandbox-service/). Local copies in scratchpad/cx/*.rs.
- token.rs:42-44,500: consts DISABLE_MAX_PRIVILEGE=0x01, LUA_TOKEN=0x04, WRITE_RESTRICTED=0x08; "let flags = DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED;" then CreateRestrictedToken(base_token, flags, ...). Restricting-SID order comment: "Exact order: Capabilities..., ExtraRestricting..., Logon, Everyone". Capability SIDs are random per workspace / readonly / writable root (cap.rs CapSids{workspace, readonly, workspace_by_cwd, writable_root_by_path}, stored in CODEX_HOME/cap_sid; "included in a workspace-write token only when the root is currently allowed").
- token.rs set_default_dacl comment: "An OWNER RIGHTS ACE suppresses its implicit WRITE_DAC grant, which would otherwise let a different logon rewrite this DACL."
- lib.rs:749 (legacy/unelevated backend), verbatim: "WRITE_RESTRICTED tokens consult restricting SIDs only for writes, so this backend cannot make capability-SID deny-read ACLs authoritative." and errors "deny-read overrides require the elevated Windows sandbox backend" / "Restricted read-only access requires the elevated Windows sandbox backend". => write-restricted token cannot deny reads (known limit).
- identity.rs: SandboxRuntimeAccount::{Offline,Online}, users.offline / users.online => two dedicated local accounts. wfp.rs: Windows Filtering Platform persistent filters on FWPM_CONDITION_ALE_USER_ID with FWP_ACTION_BLOCK (per-USER network block; a firewall can key on a real user SID, not on a restricting SID). service_identity.rs: SCM service "CodexSandboxService" (admin-installed, provisions accounts over an authenticated pipe).
- desktop.rs: private desktop. app_package.rs / package_identity.rs: MSIX package identity gating a "registered core" runner (not AppContainer sandboxing). grep -i appcontainer over the 12 fetched files found nothing relevant.
- Net: elevated = dedicated user + write-restricted token (capability-SID restricting SIDs) + ACL grants to cap SIDs on writable roots + WFP per-user block + private desktop. unelevated = write-restricted token + ACLs + env-level offline only.

## T2. Microsoft MXC  [READ-P: github.com/microsoft/mxc README + docs + source via gh api; the blog = SUMMARY only]
Name = "Microsoft eXecution Container (MXC)" (README title; OpenAI docs say "Microsoft Execution Containers"). Only one project by this name found: microsoft/mxc (MIT, created 2026-02-06). Releases: v0.7.0-rc1 2026-06-13 (pre), v0.8.0 2026-08-22 (pre), v0.9.0 2026-09-29 (pre), v1.0.0 2026-10-07 (not prerelease). main HEAD 7bf21024 (the v1.0.0 tag; c6f301d5 originally cited here is main, 20 commits later)3a1430c4c921a05c57af838f7392348f (2026-10-09).
- README: "MXC is a **sandboxed code execution system** for running untrusted code (model output, plugins, and tools) on Windows, Linux, and macOS. It provides multiple containment backends, from OS-native process sandboxes to full VMs". Backends: ProcessContainer, Windows Sandbox, LXC, Bubblewrap, Seatbelt, MicroVM (Nanvix), Hyperlight, IsolationSession, WSLC. Windows default `processcontainer`; others windows_sandbox*, wslc, microvm*, hyperlight*, isolation_session; "\* These backends are **experimental**." (README stars windows_sandbox, microvm, hyperlight; not isolation_session/wslc.)
- OS support (docs/backends/process-container/os-version-support.md): Process Isolation needs 24H2 26100.9278 / 25H2 26200.9278 / 26H2 26300.9550 / 26H1 28000.2804. Session Isolation needs 26100.9550 / 26200.9550 / 26300.9550 / 28000.3086.
  *** THIS MACHINE: Win11 10.0.26200, UBR 0x24f1 = 9457 (reg query just now). Meets ProcessContainer (26200.9278); does NOT meet Session Isolation (26200.9550) at this build.
- ProcessContainer tiers (src/mxc-sdk/src/backends/process_container/common/dispatcher.rs): "Tier 1 (BaseContainer), Tier 2 (AppContainer + BFS), or Tier 3 (AppContainer + DACL)". T1 = OS-native PSEC (CreateProcessSecurityEnvironment): "Filesystem-policy enforcement under T1 is delegated entirely to BaseContainer's PSEC API". networking.md: PSEC gives per-container-SID WFP egress filters + per-container WinHTTP proxy "applied with no UAC prompt per launch"; "PSEC is the only ProcessContainer path that receives directional egress filters, proxy peer identity, or host-loopback configuration"; "When PSEC is unavailable or incompatible, selection continues to AppContainer, where unsupported policy is rejected." AppContainer fallback uses capabilities internetClient / privateNetworkClientServer only (no directional WFP). T2/T3 stamp host DACL ACEs and remove them on Drop (a crash can leave ACEs; the doc names a same-container_id concurrency limitation).
- host-prep.md: Tier 3 needs admin one-time wxc-host-prep.exe (requireAdministrator): "Add minimum-rights ACEs for AppContainer SIDs to the system-drive root" because "cmd.exe, powershell.exe, pwsh.exe, node.exe ... fail with ERROR_ACCESS_DENIED inside an AppContainer because the well-known AppContainer SIDs are not granted any rights on the system-drive root by default"; and \Device\Null SD "resets to an AppContainer-hostile default at every boot" (prepare-null-device). Direct evidence of AppContainer dev-tool friction.
- IsolationSession (docs/development/architecture/backends/isolation-session/oneshot.md): "none of them runs the workload as a freshly-provisioned, per-execution Windows user account inside a dedicated OS-managed session"; goal "per-execution OS-isolated identity so the workload's actions cannot pollute the calling user's NTFS / registry / token state"; lifecycle add_user -> start_session -> run -> stop -> deprovision via OS-side Isolation Session API, bindings from "a private WinMD; the OS-side API is gated on an internal Windows feature flag". => Microsoft is productising a dedicated-account + separate-session tier (OS-managed, not hand-rolled) alongside AppContainer.
- Blog https://blogs.windows.com/windowsdeveloper/2026/10/07/microsoft-execution-containers-policy-driven-containment-for-ai-agents/ [SUMMARY via WebFetch small-model; curl hit Cloudflare]: published 2026-10-07; "now generally available"; process container = AppContainer on Windows / Seatbelt / Bubblewrap; session container "Runs under a distinct Windows account and session, isolating the desktop, clipboard, UI, input"; WSLc; MicroVM "experimental"; Windows 365 for Agents GA; Intune management "will soon be available". Third-party (SUMMARY ONLY, WebSearch snippets): Codex, GitHub Copilot, OpenClaw, Replit support MXC; "Claude Code support is coming".

## T3a. Chromium Windows sandbox  [READ-P: chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md (?format=TEXT, 600 lines, fetched 2026-10-10; commit SHA not retrieved)]
- "At its core, the sandbox relies on the protection provided by four Windows mechanisms: A restricted token / The Windows job object / The Windows desktop object / Integrity levels". "The Windows sandbox is a user-mode only sandbox. There are no special kernel mode drivers, and the user does not need to be an administrator".
- Alternate desktop: "applications that have windows on the same desktop are also effectively in the same security context because the sending and receiving of window messages is not subject to any security checks ... The sandbox creates a third desktop that is associated to all target processes."
- Integrity: "our renderer processes run at the lowest Untrusted integrity level"; "the integrity level is a bit redundant" given token/job/desktop; "network and network utility processes run at Medium integrity, the GPU process at Low".
- App Container section (verbatim): "The sandbox therefore takes the existing restricted token and adds the Low Box attributes, without granting any Capabilities, so as to gain the additional protection of no network access from the sandboxed process." i.e. Chromium LAYERS AppContainer ON TOP of a restricted token, mainly for network denial.
- LPAC (verbatim): "Less Privileged App Container (LPAC) runs at a lower privilege level than normal App Container, with access granted by default to only those kernel, filesystem and registry objects marked with the `ALL RESTRICTED APPLICATION PACKAGES` or a specific package SID." Caveat verbatim: "all locations in the filesystem and registry that the LPAC process will access during its lifetime need to have the right ACLs on them ... This is typically done by the installer". (LPAC is a fixed-binary, installer-ACLed design.)
- Also: ACG, CIG, Win32k lockdown, child-process restriction as extra layers; "Job levels can be broken out of" (Project Zero ref).
- Design principle verbatim: "Emulation is not security: Emulation and virtual machine solutions do not by themselves provide security."

## T4. Deprecation / roadmap signals
- AppContainer: no deprecation found. Microsoft's newest agent-containment product (MXC GA 2026-10-07) uses AppContainer as its Windows "process container" fallback/tiers 2-3 and an OS-native PSEC/BaseContainer API as tier 1 [READ-P source, see T2]. MSRC Windows security servicing criteria [SUMMARY via WebFetch, not read raw; curl blocked]: lists "AppContainer sandbox boundary: An AppContainer-based sandbox process cannot access or tamper with code and data outside of the sandbox" (serviced, bounty-eligible), plus "User boundary" and "Session boundary"; does not mention restricted tokens; "By default, components are not considered boundaries unless explicitly named as such."
- Restricted tokens: no deprecation; API still current (learn.microsoft.com/windows/win32/secauthz/restricted-tokens fetched, describes CreateRestrictedToken). Not named as a servicing-criteria boundary (SUMMARY). OpenAI Codex now calls its restricted-token (unelevated) and user+restricted-token (elevated) implementations "legacy" [READ-P docs] in favour of MXC.
- MDAG: deprecated and removed in 24H2 (T3b). MXC IsolationSession (dedicated per-execution OS-provisioned user + session) needs build 26200.9550+; backend bindings from "a private WinMD ... gated on an internal Windows feature flag" [READ-P source] -> OS-internal API, not a public documented Win32 surface.
- Win32 App Isolation: still "in preview" on Learn (T3b).
- MXC: v1.0.0 released 2026-10-07, 4 pre-releases before; microvm/hyperlight/windows_sandbox experimental; Intune management "soon" (SUMMARY).

## T5. Who calls what weaker/stronger  (quotes)
- David LeBlanc (Microsoft; Office sandbox author), "Practical Windows Sandboxing - Part 1" [READ-P: learn.microsoft.com/en-us/archive/blogs/david_leblanc/practical-windows-sandboxing-part-1; undated archive, Office 2007-2010 era]: "restricted tokens were part of a somewhat failed sandboxing effort named SAFER ... one of the reasons SAFER was considered a failure is that it tried to sandbox general purpose apps on the same desktop as everything else. This isn't going to work. It can make a somewhat reasonable speedbump ... but I'm interested in a serious security boundary, not a speedbump." and on SidsToRestrict: if token user still enabled "the process has enough rights to open a non-restricted process (or edit your profile and all your stuff), which then allows it to escalate privilege back to the original token, and all we've accomplished is a speed bump." Part 3 [READ-P]: "the desktop isn't truly a security boundary - what's the boundary is the window station, and to be precise, it's the logon ID". => restricted-token sandboxes are only as strong as restricting-SID discipline + desktop/winsta separation; that is design-in-depth, not a free boundary.
- Chromium [READ-P]: "Job levels can be broken out of" (extra layers added); "the integrity level is a bit redundant"; adds AppContainer (no capabilities) over the restricted token to deny network. Chromium does BOTH layers.
- Codex own code [READ-P]: write-restricted token "consult restricting SIDs only for writes ... cannot make capability-SID deny-read ACLs authoritative" -> reads are not confined by the restricted-token backend; docs: unelevated "has weaker network isolation than elevated and doesn't support denied read paths". Dedicated user was added for the elevated mode specifically so that firewall/WFP can key on a real user (code: FWPM_CONDITION_ALE_USER_ID).
- OpenAI docs for MXC [READ-P]: MXC "Uses native process isolation without administrator-approved setup, additional Windows accounts, or local firewall rules." (positions dedicated-accounts + firewall as heavier/legacy). Issue #48721 [READ-P, one reporter]: the dedicated-account design "persistently mutates ACLs on every writable root" and leaves files owned by the sandbox account.
- Microsoft MXC source [READ-P]: IsolationSession goal "per-execution OS-isolated identity so the workload's actions cannot pollute the calling user's NTFS / registry / token state" - Microsoft treats a dedicated per-execution account+session as a distinct, STRONGER-isolation tier than ProcessContainer (README lists IsolationSession separately; blog calls it "session container ... distinct Windows account and session ... isolating the desktop, clipboard, UI, input"). No source states "stronger" in those words; this is my reading of the tier structure.
- NOT FOUND: any credible primary source explicitly ranking "dedicated local user + NTFS ACLs" vs AppContainer/restricted token for security strength. MSRC lists user boundary, session boundary and AppContainer boundary as three distinct serviced boundaries (SUMMARY). Forshaw/Project Zero: my one search returned nothing usable; not read.

## SUMMARY
T1 Codex (docs+source read; OpenAI blog NOT read - Cloudflare):
- Shipped as experimental restricted-token sandbox PR #4905 merged 2025-10-30 (sha 87cce88f); earlier AppContainer PR #4175 (2025-09-24) closed unmerged, no reason in PR text.
- elevated = dedicated Offline/Online local users + write-restricted token (DISABLE_MAX_PRIVILEGE|LUA_TOKEN|WRITE_RESTRICTED, capability-SID restricting SIDs) + persistent ACL grants + WFP per-user block + private desktop; needs admin (UAC, firewall, logon rights, service). unelevated = restricted token + ACLs + env-level offline (weaker network, no deny-read).
- Known limits: write-restricted cannot protect reads; persistent ACE/ownership pollution (#48721); setup failures (error 1385, logon rights, firewall policy).
- Now: MXC is "recommended"; elevated/unelevated are "legacy fallbacks" (docs, CLI >= 0.162.0).
T2 MXC (microsoft/mxc, README/docs/source read; blog via summary only):
- Tiers on Windows: T1 OS-native PSEC BaseContainer, T2 AppContainer+BFS, T3 AppContainer+DACL (needs admin wxc-host-prep); plus IsolationSession (per-execution dedicated user+session), WSLC, experimental WindowsSandbox/MicroVM/Hyperlight.
- v1.0.0 2026-10-07 (GA per blog summary); process isolation needs 26200.9278, session isolation 26200.9550. This box: 26200.9457 -> ProcessContainer OK, IsolationSession not yet.
- PSEC gives per-container WFP egress filters with no UAC per launch; AppContainer fallback only has internetClient / privateNetworkClientServer capabilities.
- AppContainer friction documented by MXC itself: system-drive root ACE and \Device\Null SD fixups for cmd/pwsh/node.
T3 production users: Chromium = restricted token + job + alt desktop + integrity (+ AppContainer no-caps, LPAC for some); Firefox = Chromium sandbox lib, token USER_LIMITED/RESTRICTED + JOB_LOCKDOWN + alt desktop/winsta + low/untrusted integrity; MDAG = Hyper-V, removed in 24H2; Win32 App Isolation = AppContainer, still "preview"; Windows Sandbox = hypervisor VM; Adobe/Office = summary only.

T5: LeBlanc (Microsoft) calls bare restricted tokens "a speedbump" unless SidsToRestrict + separate desktop/winsta/logon-ID are done right; MSRC names AppContainer, user and session as boundaries (summary); no direct dedicated-account-vs-AppContainer ranking found.
