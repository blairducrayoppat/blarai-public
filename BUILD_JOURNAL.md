# BlarAI — Build Journal & Lessons Learned

This is the honest, running record of building BlarAI: what I set out to do, what went wrong, how I recovered, and what I learned. It is written as the work happens, not polished afterward. It keeps the failures in — the failures, and recovering from them, are the part worth showing. It is the raw material for an end-of-project post-mortem and for a professional portfolio in AI-assisted development and the governance of local AI systems.

**The project.** BlarAI is a locally-run AI assistant: a privacy-first system that runs entirely on local hardware, the language model on the GPU. It began as an air-gapped terminal program; it is now a native Windows app with voice, vision, document ingest, a knowledge bank, local image generation, a headless coding-agent dispatch, and — since the governed air-gap removal of 2026-06 — exactly one policy-gated network door. The goal it was built toward, and now largely is: a local *agentic* assistant that can use tools, help with code, and store, analyze, and generate content from my own data. *(Blurb updated 2026-07-03; the 2026-05-21 entry below preserves the original starting point.)*

### 2026-10-05 — A deferral nobody owned: the coder-containment flip lapsed for 78 days, and the review of the new wiring is not finished

*Plain summary: the safety fence around the coding agents (a separate Windows account) had never been switched on, and the reason came out only when a read-only check was run on it. The switch-on was postponed for a week in July and nobody picked it up again. This entry covers what the check-up found, the test that showed we can block the coder's internet access even with Bitdefender running, and how the new wiring went through three rounds of independent review, which kept finding holes in the same check-then-use pattern and in the lint meant to catch them. The fence is still off and the strongest fix is not merged.*

It started during the 9B evaluation arc, when an ideation note on a third-party agent sandbox that I had just written said coder containment was off because Bitdefender owns filtering. A read-only forensics pass checked that against the git history and the framing was wrong. `"containment": "off"` in agentic-setup's `fleet-driver.json` is the dormant day-one default from commit `4c91809` on 2026-07-10. The Lead Architect (LA) had approved deferring the flip on 2026-07-11, for a good reason (the ACP driver had just gone live, and switching on containment the same night would have confounded the first overnight battery on it), with a stated bound of 2026-07-18 and "re-surface to the LA if it slips." The last word on #775 was 2026-07-15. The bound was about 78 days past. Bitdefender explains the separate, LA-accepted gap in *egress* blocking; it never explained the flag. I corrected that note and #1669 where the wrong framing had been written (comment 3859), and kept the wrong version visible.

The sentence "it will be completed, tracked here, not drift" had been on the ticket the whole time. It named a date and no owner and no event anyone would observe, and nothing in the process could notice a date passing in a comment. That is the same shape the project's deferral discipline refuses for review findings, which require a `blocked-by` someone can observe; I had not thought to apply it to a flip.

The pre-flight (read-only, 2026-10-05) found the neglect had a cost. Nothing had run `verify-coder-containment.ps1` since 2026-07-10. `C:\blarai-fleet`, where the coder's worktrees and the job queue live, was Modify for Authenticated Users, inherited from `C:\`, as the pre-flight reported (#775 comment 3879: "every local account can write the coder worktree/queue root"); #1686 records that the coder-leg job and result queue sits under it. The pre-flight did not test whether any other local account exists or writes there. The coder account itself still had Modify on all 45 child folders of `C:\Users\__USER__\projects` (#1678), which makes "cannot write outside its worktree" false. And the `verify-fleet-driver` suite had been red since the 2026-07-11 driver flip, because it asserted the driver was still `stdin`; the flip edited only the config.

**The egress test.** The accepted gap was that Windows Firewall rules, including the per-account rule, are inert on this machine because Bitdefender owns packet filtering. #1671 asked a narrower question: does a raw Windows Filtering Platform filter, which is a different mechanism from a Firewall rule, enforce anyway? With the LA at the machine I ran a script three times. Each run: the operator's own connects to two public addresses all worked, the coder account's baseline connect worked (egress open today), one provider, one sublayer and four filters were added in one transaction in a dynamic session, the coder's connect was then blocked while the operator's traffic was untouched (checked every two seconds, no failures), and after the engine closed the filters were gone and the coder's egress was open again. That last arm matters: the probe counts an exception as "blocked," so only the open-again reading makes the block attributable to our filters. Three of three. What it does not show: the filters were dynamic by design, so reboot persistence is untested, as are IPv6 destinations, UDP and DNS, ports other than 443, a Bitdefender update or restart, and a real coder dispatch under the block. And one thing the results file makes plain that the ticket comment did not: the "loopback allowed" reading was taken against a small listener the script started on 127.0.0.1:8000 itself, not the live model server. I wrote the ticket result as "loopback OK"; the file says stub. That is a smaller claim than I made, and this entry is where I correct it.

**The fused leg and its review.** The unbuilt piece was the fused leg: a whole dispatch's coder step running as `blarai-coder` through a queue and a scheduled task, with the gate and merge staying with the operator. The first review round (on `a03a9c0`) reproduced a forged result being accepted: the SID check read a field the result file writes about itself, and a third account could write that file. Round two reproduced the next class: the workdir was link-checked once before the coder ran, the coder could swap it for a junction, and the operator's `git add -A` then ran in the other repository and staged a file there. Round three (on the #1691 fixes) found three more: after my fix, a swap *after* the identity check still worked (N1, reproduced in a temp sandbox), my lint missed quoted `git -C "$wt"` and parameters named `$Repo` (N2), and two gitdir files were unlocked (N3). Round three itself calls N1 a residual of round two's class ("M1: FIXED for every check-time and pre-call swap, with one residual (N1)"), so this was not three different classes; it was forged contents, then check-then-use on paths, then the same check-then-use again plus a lint that "certifies more than it tests" (N2). N1 and N2 were still open when round three ended.

What changed my approach was the third round's shape. The structural answer I chose, and have NOT had reviewed, is: one funnel per kind of operator-side use of anything the coder can write (git, commands, file writes, removal, reads), one strict shared parser for every job and result, and a lint that fails when a new use skips its funnel, which on the unmerged branch `fix/1691-n1-n3-n5` is an AST walk over 14 scripts instead of text matching (merged main still has the text lint round three criticised). The funnel is unverified until its review; the first funnel design was merged and still had N1. The route table is `docs/fused-leg-operator-uses.md` in agentic-setup. I rejected the alternative of adding one more reproduction-specific check after each finding; that is the path that had just produced three rounds.

N1 also taught me something about my own assumptions. My first fix for it (`49bd0d9`) enumerated and killed every process the coder account owned after the run. That needs an elevated orchestrator, and its own commit message says that without elevation the run fails closed. The orchestrator is launched by `dispatch.py` as `pwsh -NoProfile -NonInteractive` with no RunAs, so I inferred it is not elevated; that is from the launch command line and was not observed (a child inherits its parent's token, and I did not check whether the orchestrator runs elevated). If the inference holds the design would have refused every real run. The replacement (`d0120f5`) has the runner, which runs as the coder, create a Windows job object with kill-on-close and start the coder inside it, then drain the job and report confirmed-empty; the operator refuses a result without that and quarantines the worktree, and clearing a quarantine takes a non-empty clearing name (`Clear-FusedQuarantine -ClearedBy`), which is recorded in an audit line; that is an accountability record, not an authentication, since any non-empty string is accepted. That design is built with tests and **not merged**: it is on `fix/1691-n1-n3-n5` in agentic-setup. What `Stop-ScheduledTask` actually guarantees in the real OS is untested ("verify live") because it needs the registered task.

The mutation harness had its own blind spot, found in round one: it copied three files, the suite read a fourth, every mutant copy crashed, and a crash was counted as killed. A reviewer added a mutant known to survive and the harness reported "22 of 22 killed." The kills the builder reported were real; the harness just could not report a survivor.

On the automated reviewers: they kept sending leads, in batches (three on the Policy Agent validator work, about ten on the rules tooling). On #1684 two of the three leads (A1, A2) matched findings the independent reviewer reproduced (J1 and J2); the third (A3) flagged the regression in `3458ce7e` and the reviewer then confirmed it as K2, so there the lead came first. The leads earned their place; running the code is what turned them into reproductions.

Not decided and not done: the flip. The remaining criteria are in ADR-045 (the job object, #1686, #1678, #1682, the coder's own setup, a real-mode verify, a watched dispatch, a rollback drill, a full 117-mutant pass that has not completed), and the flip is the LA's ceremony. The 2026-07-10 accepted egress gap stays in force until the filters are persistent and checked.

**Recurrence of lesson 290:** a go-live flip approved for deferral with a date and no owner and no event anyone would observe lapsed for 78 days.
**Lesson 383:** when review keeps landing on the same pattern, look for the one place every instance passes through and make it the only way in, with a lint that fails when something goes around it; and treat that funnel as unverified until a review has attacked it, because the lint itself was the next finding.
**Lesson candidate, not minted: the orchestrator-not-elevated premise was inferred from a launch line and never observed, and the design was replaced before the inference caused an incident:** a control that needs a privilege must be checked against how its caller is actually launched, not how it is documented (here the launch was only inferred from a command line, and the check should be to observe the token).
**Field note (recorded in FIELD_NOTES.md):** a cmdlet or script that exits non-zero on a mutant copy because a file it reads is missing is counted as a kill; every mutation harness needs an unmutated control that must pass, and "killed" must mean a named failing check.

**Next:** merge the job-object branch after a re-review; #1682 persistence test (reboot, Bitdefender restart); #1686 and #1678 provisioning stages for the LA to run (on 2026-10-05 the LA decided to narrow the `projects` grant, #1678 comment 3892; the stage carries a dry-run listing and a negative verify check); the register of wait budgets in `shared/timeout_registry.py`; then the supervised dispatch and the flip.


### 2026-10-05 — A fix that shortens what the judge sees is fail-open: three review rounds on a validator that no live request reaches

*Plain summary: while tracing why two Policy Agent test cases failed, I found that the Policy Agent's prompt
validator had real holes (a forgeable end-marker, free-text property names, unchecked fields) and that two of its
rules can never fire on the assistant's tool calls. I fixed them, and the first fix I wrote introduced a worse
problem than it removed. The model that this validator protects is, as far as the code shows, on no live path
at all.*

The trace behind #1674 found the holes (#1684, #1685) as a side effect of asking which requests ever reach the
model. The first fix (`87569134`) did the obvious thing: reject the delimiter, cap field lengths, escape
newlines, and truncate over-long fields with a marker. A reviewer who ran the code showed the truncation was
fail-open. The rule checker judges the full request and the model would judge a prefix, so a payload placed
after the cap was invisible to the classifier and present for the actor. The right shape is that a field the
judge cannot see whole is not judged: it is denied before any model runs (`61fead17`). The same review found
that chat-template tokens such as `<|im_end|>` pass the validator and are turned into real control tokens by the
production tokenizer, so one resource string could end the user turn and plant a fake assistant turn; main had
the same hole while my docstring claimed the opposite.

Two more rounds followed. I removed the echo of rejected keys to close a prompt-forgery route, which changed 10 of
the 35 shipped evaluation prompts; I refused that (a changed marker could change the 14B's verdicts and force a
GPU re-baseline) and the compromise, echoing identifier-safe keys, was itself found to re-open the hole for keys
like `DECISION_ALLOW` (`3458ce7e`). The final shape echoes only the nine keys the golden cases carry
(`50542fbb`), the 35 golden prompts recompute byte-identical to main, and the validator walks the whole schema so
the verdict no longer depends on key order. The refused-token list is the union of every local brain tokenizer,
read from the files. For #1685 the facts were that none of the assistant's ten tools has an owner or size
argument and that the write-gated rules need a verb the assistant never sends, so the honest fix was to say the
rules do not apply at those doors and lock that with tests that fail when a tool gains such an argument.

Trade-off: I could have shipped the first version, which looked complete and passed its own 29 tests. The cost of
the later rounds was most of a working session; the benefit is that the validator now has one rule for the
one thing that matters, validate, render and act on the same string. Three automated security reviews of the
commits each named a real lead (parser differential, truncation, a control regression), and each was
reproducible only by running attacks, which is why the reviewer was told to run them.

**Recurrence of lesson 329:** truncation was applied to the text the classifier sees while the rule checker judged the full request and the actor read the original; the repair denies a field the judge cannot see whole. The same hardening found the model-backed classifier on no live path at all, a recurrence of lesson 46 (#1683).

**Next:** #1683 decides whether to wire the classifier into the door or retire it; #1673 extends the rule
checker for argument-borne threats; #1688 fixes the test isolation guard.


### 2026-10-05 — A command-text guard can never be airtight, so the control for main moved inside git; and a rules corpus whose "enforced" column means only "someone says so"

*Plain summary: two rules in CLAUDE.md (never commit work directly to main; never stage everything with `git add -A`) had been broken by session memory, so I built machinery to enforce them. The first design, a guard that reads the text of each command before it runs, had 24 or more holes found by independent review. The design I moved to puts the check inside git itself, where the text-parsing gap does not exist; the native hooks do nothing until the Lead Architect installs them, and the text guard stays best-effort. Alongside it I built a generated list of every rule in CLAUDE.md and what, if anything, enforces it: 142 of 168 rules have nothing. The new tests also made the standing test run much longer, which forced a split into a fast and a slow tier. Parts of this are not finished.*

The starting point was the lesson that a rule written down is not a control. Both rules were already in CLAUDE.md and both had failed by memory: other sessions' untracked files swept into a commit, and work committed straight to main. The first version of the control was the obvious one, a Claude Code hook that reads each shell command and refuses the bad ones. It is useful and it is not a boundary, and the review rounds are what taught me the difference. An independent reviewer and a seeded fuzzer (real bash and PowerShell with a recording git shim, over 4000 variants) found 24 or more ways around it across four rounds: wrapper and expansion forms among them (the guard's own documentation lists the classes). Each was fixed and locked, and each round found new ones. A parser of command text and the shell that executes the command are two parsers, and the gap between them is where every bypass lived. I accepted that I could not close it by being more careful.

So the control for main moved to the place that executes. A `reference-transaction` hook sees every update of `refs/heads/main` by any route, including `commit-tree` plus `update-ref`, `branch -f` and `git push .`, none of which a text guard would recognise, and allows it only as a verified `git merge --no-ff` whose tree equals what `git merge-tree` computes, or a commit made only of journal, ledger, review and similar prose files. A `pre-commit` hook covers the commit path. That is ADR-043; I will not restate it. ADR-043 records, as rejected on evidence, three choices that looked like details (I did not find these in the review file, so I do not attribute them to review): a relative `core.hooksPath` did not resolve when `git push .` ran hooks from inside `.git`, so the hooks were skipped; a planted `python` earlier on the path and `PYTHON*` variables took the guard over; an edited `_lib.sh` ran unverified. Each became a fix with a test, which is why the hooks now verify their own files against committed blobs and run the interpreter recorded at install as `python -I -S`.

Git has no hook for `add`, so blanket staging can still only be seen as text. That part stays a best-effort guard and says so. I considered a bare "gatekeeper" repository that sessions push to and only a process updates main from; it is the strongest option and a change of topology, so I recorded it as the next step and did not build it. The cost I accepted: about 4 seconds per commit on main (each git process spawn costs about 0.3 seconds on Windows), and a merge-only rule, so work lands on main by `git merge --no-ff` and never by fast-forward.

The corpus. I wanted the rules to be machine-readable without spending bytes in the always-loaded CLAUDE.md, so a script generates `docs/governance/rules-corpus.yaml` from it: 168 rules, ids derived from each rule's own name so inserting one moves no other id. The part I care about is the column that says what enforces each rule. I rejected inferring it. A test that mentions a rule's words is not evidence that it enforces the rule, and a heuristic column would read as coverage. So an enforcing file says so with an `enforces-rule:` marker, and a short curated file covers what cannot carry one (the user-level hook, reviewer agents). The column therefore means exactly one thing: a marker exists, which is the enforcing file's author asserting it. The generated gap list is the finding: 29 of 168 rules have an enforcement entry (26 a test, hook, verifier or gate, 3 reviewer-only), 139 have none, and 142 have no test, hook, verifier or gate, including six critical ones (the atomic ship motion, the comprehension gate, performance recording, test-the-seams, among them). I built this and it is not a measurement of enforcement. Three rules still read "none" although partial tests exist (review finding N11; the record is on the unmerged branch).

The gate cost. The commit-protection tests, which drive real shells and mutate the guard, were estimated at about 25 minutes added to the standing gate (ADR-043). I split them: the git-tooling tests are marked slow per test and run before changing the guard, hooks, installer or the git rules, and monthly; a fast core stays in the gate. After the split the gate on merged main was 12806 passed, 0 failed, 0 skipped, 482 deselected (up from 133 deselected, so the 349 slow tests moved out), in 1547 seconds, with a builder running verifies in parallel. Three documents give three different durations for the slow tier (about 25 minutes added to the gate in ADR-043, about 35 minutes for 349 tests in the ticket, about 45 minutes in TEST_GOVERNANCE), measured at different times under different load; none is a controlled measurement and I am not reconciling them by picking one. The trade-off I accept is that nothing forces anyone to run the slow tier, so a change to the guard that skips it is a lapse the gate will not catch.

What is not finished, so this is not read as done. The review file has these headings: the pre-merge review (round 1: N1 to N19 and P1 to P3, the P items being automated leads), Round 2 (Q1 to Q7), Round 3 (final verification of the corpus branch, where the R1 to R5 findings were raised) and, in the version at the install-hardening branch tip, a Round 4 section on `feat/1690-install-hardening` verifying the R1 to R4 fixes (the commit that added the file says "rounds 1-3"). About ten batches of automated review leads went in as well; that review report and its disposition are on the unmerged install-hardening branch, not on main (`32e31564`), so the merge itself carries no review record. The R findings are not in main: the install-step hardening is on `feat/1690-install-hardening`, unmerged. It copies the hooks from main into the git common dir so a branch switch cannot disable or break them, reads the scope from an identity recorded at install, and has the text guard refuse plain merge, `--ff-only`, pull and cherry-pick on main before git touches files. Until it merges the native hooks live in the working tree, and they are inert until the LA runs the installer in any case. The advisory rules-review pilot (diff versus corpus, proven on three past diffs plus planted violations, three repeats, a false-positive rate) is not built. The skills audit has a plan (keep the three agents and the sprint and gate skills, measure the plugin skill-listing cost, then decide) and no result.

**Lesson 384:** a parser of command text and the program that executes the command are two parsers; a control built on the first can never be airtight, so enforce at the seam that executes and keep the text guard only where nothing better exists, labelled as best effort.
**Lesson 385:** a column that says "enforced" is a claim by whoever wrote the marker; generate the list of what nothing enforces next to it, because that list is the finding.
**Recurrence of lesson 70:** the lock leaves the standing gate by design, for cost: the 349 commit-protection tests moved to a slow tier that nothing forces anyone to run.

**Next:** merge the install-hardening branch after its review; LA runs the installer and `--check`; build the rules-review pilot; close the three N11 rules; run the slow tier at the monthly mark; the skills-audit measurement.

**Known formatting defect:** the first seven commits of this documentation branch (ca7ce1ee, 34bb81d8, 8b8c8820, 130a4f90, 58ff2ccf, 9a66d330, e61d48d5) have no blank line before their Co-Authored-By and Claude-Session lines, so git does not read those lines as trailers (they print as part of the subject). History is not rewritten (a rewrite is destructive); the later commits have the blank line.


### 2026-10-05 — The Governator was reopened on a narrower claim than the one it was cancelled for

*Plain summary: the Lead Architect reopened the cancelled runtime-governance venture today because new measurements showed that, for one dimension (what a dedicated Windows account can reach on the network and on disk), in these runs an outbound connect from the account failed while the filters stood, enforced by Windows rather than by the agent, with the limits stated below. The claim that evidence supports is smaller than the one the cancellation demanded, and what the product is has not been decided.*

On 2026-09-18 the Lead Architect cancelled the venture with one sentence: if we can never truthfully say agents cannot get around this, we do not have a product. That followed from my own study's finding that every seam a third party can reach on Windows is cooperative, and that the one non-cooperative seam I probed, a per-process firewall rule, failed silently at 37 of 37 requests because Bitdefender owned the firewall. Today he reopened it, in his words "between this and the BitDefender study results, The Governator is reopened". I read "this" as the containment evidence; that is my reading and he may correct it. I could not trace a separate document called the Bitdefender study; the Bitdefender results I can point to are the study's seam-6 finding and the fact that Bitdefender was running during every new measurement. I recorded his sentence verbatim and noted that which results he meant is his to say.

The new evidence is two spikes with him present. A raw Windows Filtering Platform block keyed to the `blarai-coder` account held in 3 of 3 runs while Bitdefender owned filtering (#1671), and a restricted non-interactive account ran a model on the iGPU, was denied all 8 secret reads and all 4 outside writes, and served a completion over loopback with its own outbound blocked (#1689). The enforcement there is a Windows filter keyed to which account the process runs as, not a hook the agent runs, so in these runs it did not depend on the agent's cooperation. That is the kind of seam the study found missing, and it is why I read reopening as coherent with the evidence rather than a change of mood. It is also fail-open when the operator's installer process exits, because the filters were dynamic.

What it does not give is most of the room. Each run held the filters for about three to five seconds in a dynamic session; the observations are single IPv4 connects to port 443 on one machine under one antivirus and one driver; the loopback permit was first shown against a stub listener, and the later model run was one 4B INT8 model, one prompt, 64 tokens, with speed parity unmeasured. Nothing is shown for reboot persistence, IPv6, UDP or DNS, a Bitdefender update, or a real coder dispatch. It says nothing about whether any individual action is acceptable, nothing about software that runs as the operator, and administrators and kernel adversaries are out of scope. The setup itself is account, ACL and firewall provisioning that is blocked for the harness and run by the LA. I put every one of those limits in ADR-049 in the sources' own words.

The trade-off is the point of the entry. ADR-042 asked for a claim of "agents cannot get around this". ADR-049 reopens on a claim that is at most a bounded statement about one dimension; the candidate wording in the ticket, "an agent run inside the contained account cannot reach the network or read your files; enforced by Windows, not by the agent", is not yet supported as written (B:\models writable, the coder able to read and modify all of projects, C:\blarai-fleet writable by every account, coder egress open today because containment is off), and it came from the #1693 ticket, not from me and not from an adopted decision. The rejected alternatives were keeping the cancellation (the evidence is a reason to look again), reopening only as BlarAI-internal work (ADR-042 Decision 2 already kept that, so it would reopen nothing), and reopening as specification-only (a form the LA has not chosen, so choosing it would pre-empt the gate). I decided none of the open questions: claim, form, audience, licence, publication, naming, the relation to a third-party open-source agent sandbox (#1669) and to Anthropic's sandbox runtime, funding, and the 8 to 14 hours a week the study priced for the specification path all stay with him. ADR-049 supersedes ADR-042 Decision 1 and the repository disposition in Decision 6, flags Decision 3's ground ("no second party") for re-examination rather than re-affirming it, and the old text stays visible under a banner. The LA later said "Your recommendations are approved", which I recorded on #1693 (comment 3898) as confirming that scope; it was a general approval of my recommendations, not a line-by-line reading of the ADR, and the ADR says so. Claim, form, audience, licence, publication, naming, time and funding remain undecided.

What I did: wrote ADR-049, bannered ADR-042, added the register row and a pointer on the 2026-09-20 row, and wrote this. What I did not do: touch BlarAI's runtime, the governator repository, the study, or the accepted coder-egress gap; and I did not read the evidence document itself, because it was not yet on disk, so I cited the Vikunja comments and raw data. I also found two source disagreements and kept the corrected versions: #1671 comment 3873 called its result a "re-visit trigger" on #775, which comments 3893 and 3894 correct, and its loopback result was a stub (comment 3891).

**Lesson candidate, not minted: the entry records no failure of its own, and the generalisation is unproven:** reopening a decision is a decision about a claim, so the record should state the new claim next to the old one and say which is smaller; evidence that supports one dimension must not be allowed to read as support for the whole thing it once failed to support.

**Next:** present the full comprehension gate for the reopened program, then refresh the 2026-09-17 feasibility study against the new evidence, with the LA's gate confirmation before any build (#1693).

### 2026-10-06 — A rollback proved by injecting one failure is not a rollback: the install step was rebuilt twice over, and I ran my own gate in the wrong place twice

*Plain summary: the commit-protection hooks' install step had two holes a reviewer proved (a locked file during an update left main unprotected; a fake Python could stand in for the guard). A builder rebuilt it, a fresh reviewer closed both, and the work, the doc branches and the journal fold merged to main as e8427330. The hooks are still not installed in the real repository.*

The second review round on db605011 found two blocking holes. R1: during an update, a locked installed file made the new rollback stop halfway, delete the shims and set the record aside, and a code commit on main then succeeded with exit code 0. The rollback tests had injected a failure in exactly one place, the record write, so the path that failed in practice was never exercised. R2: the hook checked only the hash of the venv launcher, which is identical in every venv, so repointing pyvenv.cfg at a fake interpreter that exits 0 let a code commit through even though the install check reported not-OK.
