# BlarAI — Build Journal & Lessons Learned

This is the honest, running record of building BlarAI: what I set out to do, what went wrong, how I recovered, and what I learned. It is written as the work happens, not polished afterward. It keeps the failures in — the failures, and recovering from them, are the part worth showing. It is the raw material for an end-of-project post-mortem and for a professional portfolio in AI-assisted development and the governance of local AI systems.

**The project.** BlarAI is a locally-run AI assistant: a privacy-first system that runs entirely on local hardware, the language model on the GPU. It began as an air-gapped terminal program; it is now a native Windows app with voice, vision, document ingest, a knowledge bank, local image generation, a headless coding-agent dispatch, and — since the governed air-gap removal of 2026-06 — exactly one policy-gated network door. The goal it was built toward, and now largely is: a local *agentic* assistant that can use tools, help with code, and store, analyze, and generate content from my own data. *(Blurb updated 2026-07-03; the 2026-05-21 entry below preserves the original starting point.)*

### 2026-08-05 — Monthly retrospective: the month we built the instruments, and the month they failed

*Plain summary: July added 5,401 tests and a whole apparatus for measuring whether BlarAI works — an eval harness, oracle machinery, a coordinator, verifiers, lints, gates — and then spent its second half discovering that almost every one of those instruments had been reporting a pass it never earned. The bill was not a twist at the end. It was the price of the build.*

I came into this retrospective believing July had *converged* on instrument honesty — that the theme emerged late, out of the 07-30 reckoning, and that everything before it was ordinary building. That is wrong, and the journal disproves it in its own second entry. The eval harness landed on 07-02 and caught, the night it was built, a golden case that had encoded the old parser's nested-paren defect as expected behaviour. Lesson 186: golden sets are commitments, not observations. Day two. By 07-09 the class had a number — lesson 222, born when the design-verify tier screenshotted apps over `file://`, where browsers block module JS, and the fleet's own web scaffold is a module app. That instrument could never have rendered *any* working app. It convicted B5's perfectly functional habit tracker, and "the coder can't build charts" came within one review of entering the capability ledger as measured fact.

So the shape is not convergence. It is two phases and a causal link: July is the month this project acquired measuring instruments at industrial scale, and then discovered that essentially every one of them had been reporting a pass it had not earned. You cannot discover your instruments are lying until you have instruments. The reckoning is not a late twist; it is the bill.

The month divides into four dense pushes, not an even grind — 32 entries in week one, then 124 in the week of 07-06 (43 on 07-11 alone), 72, 57, and 33, with 07-25 and 07-26 empty. Week one was the capability program the Lead Architect opened by asking what obvious wins the project was lacking; the honest answer was that we had four thousand software tests and not one measurement of whether the model was getting smarter or dumber. That produced the eval harness (#717), the Qwen3-native tool-call format replacing our homemade dialect (#718), NPU embedding offload (#720), and the first policy-gated egress — Kagi web search, live 07-02, behind its ceremony (#719). Week two matured the fleet and then, on 07-11, built the QUALITY program in a single 43-entry day: oracle-QA, an oracle *mutation* audit that asks whether the oracle actually catches wrong code, a flake differential, a grader-tampering fingerprint, a GREEN-quality audit. Instruments deliberately built to audit instruments. Week three built the coordinator (epic #841) — C3's heartbeat shipped as seven independently-reviewed limbs on 07-14, all merged dormant with zero flags flipped, and by 19:03 that evening BlarAI had taken its first autonomous breath in shadow, with one encrypted journal row and nothing visible to show for it. The same week restructured the docs: 157 files at the top level down to 16, the journal rotated into monthly volumes, LESSONS three-tiered, pre-mint search down 91 percent.

Then the apparatus got turned on itself, and it kept failing.

The precise class is narrower and nastier than "instruments lied," and getting it right matters because the wrong phrasing suggests the wrong fix. Every one of these failed **silently, in the safe-looking direction, and rendered identically to an honest clean result.** 07-21 states it exactly: a permanently-first night and a real first night render identically. 07-30 puts it in general form: "it has been green for weeks" is indistinguishable from "it stopped looking weeks ago" unless something deliberately breaks it and checks that it screams. That indistinguishability is the entire reason this took a month to see, and it is why vigilance was never going to be the answer.

The specimens are worth keeping. A safety gate that never once ran, because `Write-Log` is defined as `Write-Output`, which in PowerShell contributes to the enclosing function's return value — so `Test-NightAdmission` returned a two-element array, a non-empty array coerces true, and `while (-not (Test-NightAdmission))` had never entered since the day it was written; the probe gate, the 30-minute retry and the 04:00 stop were all unreachable, and every `lean preflight:` memory measurement had been swallowed into a return value, which is why no night directory in the archive contains a memory number. A history reader that searched for last night *inside tonight's folder*, giving eleven consecutive nights a population of one — and whose docstring defended the first-night `None` as "an honest baseline, not a fabricated zero," which is precisely the honesty that kept anyone from looking. A governance golden set of 50 cases whose committed baseline held 41, computing `pass_rate: 1.0` over 41 of 50 and under-reporting the suite by 18 percent. A verifier that had reported 0 passed / 7 failed since around 22 July with nobody reading it, because it bailed at check S1 and never evaluated the rest; fixing it turned `0/7` into `29/0` and ran 28 behavioural checks for the first time in over a week. A morning-report alarm — the only mechanism by which the report can say a night's evidence was lost — that had fired every healthy night for weeks.

And the sharpest one, because it is about the shape of the trap rather than any single bug: a pinned worktree is detached by design, so the check `blarai_branch -eq 'main'` is `$false` forever. **The pin succeeding would have been indistinguishable from the pin failing.** That is the same defect as the screenshot tier and the first-night reader and the admission gate, wearing different clothes each time.

The half of this that is actionable, and that I would have missed if I had written this retrospective from memory: in every single instance, what caught the instrument was never the system. It was an independent reviewer, or the Lead Architect using the thing, or a control deliberately built with a chance of failing. The 07-30 entry says it flatly — nothing here was found by the system reporting a problem. On 07-27 he spent an evening actually driving the dispatch corridor and produced eight distinct defects in a row, every one found by him using it, none by any suite, with the standing gate green the whole time. On 07-29 the same: every defect came from watching the operator, none from the gate. The 07-23 entry draws the conclusion I want to keep, and it indicts its own author while doing it — the thing that caught them was never cleverness, it was a control that had a chance of failing: a positive control with a known non-perfect answer, a corpus written by someone who did not want the change to succeed, an exit code actually checked. The alternative rejected each time — reasoning carefully about whether the thing worked — is the approach that produced a published 73 percent improvement that had to be withdrawn two hours later, when an independent reviewer's 22-row set, built without reference to the design, measured 11/18 before and 11/18 after. Net zero. All 38 counterexamples were undercounts, the one direction the builder's safety argument was silent on.

The trade-off I keep coming back to is the one on 07-23 that was made correctly: a control was ready and was *deliberately held for two days*, because it changed the instrument that was measuring an A/B in flight. The obligation was banked as its own ticket with an observable predicate rather than carried in someone's head. The rejected path — ship the control now because it is right — would have been defensible and would have destroyed the comparison it was meant to protect. Holding a correct fix is sometimes the correct move, and the only thing that makes it honest rather than negligent is that the predicate is written down somewhere a later session must read.

Numbers, because a retrospective without them is a mood. The standing gate opened July at 4,744 passed and closed at 10,145 — 2.14 times the opening figure, plus 5,401 tests. Lessons ran 183 to 343: 161 minted in one month. Fifty-eight distinct lesson numbers took recurrence tallies, and lesson 222 is the month's spine, referenced thirteen times between 07-09 and 07-29. Nine third-instances shipped their required structural control, and the pattern in them is worth naming: the control is almost never more vigilance. It is an external-probe registry that refuses to let a module reach the egress door without enrolling a probe; an AST enumeration of every post-seed consumer, deny-by-default, proven red against the real defect; a handoff-brief verifier with a required anchors block, escalated as #929 by an overnight integrator who correctly refused to invent doctrine at 3am and waited for approval.

Seven gate runs went red, and only one was a regression. Two were the runner rather than the tree — the PowerShell tool shell poisons environment-sensitive tests, and a "fix" for one of them turned out to be no fix at all when the bash re-run came back byte-identical green. One went red the moment a doc-rot control was given teeth, which is the rule rather than the exception: when you give a check teeth, the first thing it bites is never a regression. One was an invisible U+000B vertical tab inside a Windows path in the lessons archive, hiding a real recurrence from the tally checker. And one deserves its own line: main's standing gate had been red since the 07-29 go-live ceremony dropped a gating declaration, and nobody knew, because the freshness check compares two documents to each other rather than either of them to reality. That is the month's thesis reproduced inside the month's own safety net.

The performance record ran to 19 dated July entries. The one I would keep is 07-16, when a headline died of a download: our 07-10 finding that llama.cpp beats OpenVINO on MoE models was destroyed by a six-minute re-run, because the OpenVINO number had been measured on a broken community conversion. Intel's official IR runs the same model 131 times faster on prefill and 22 times faster on decode. The line that stings is that the falsifying evidence was already ours — this box had served a same-class MoE at 38.6 tokens per second since 06-29, and the 1.59 we recorded should have collided with that the night it was written down.

If July has one sentence, it is that the project's verification apparatus finally grew large enough to be turned on itself, and every time it was, it failed. If it has a second, it is the one from 07-30 that is about people rather than tools: author-is-not-verifier is not a formality about second opinions, it is the recognition that the person closest to a change is systematically blind to the risk it adds, in exact proportion to how well they understand the risk it removes. That entry earned the right to say it — its author described the failure mode precisely, in writing, in a commit message, while introducing it in the code under that message.

August opens with the bill still partly unpaid. The standing baseline carried a *derived* figure into August — 10,145 by arithmetic, because the primary checkout was held when it landed — and it sat in the slot reserved for a measurement for six days. It was re-measured on 08-05 at exactly 10,145. The derivation was right, which is the point worth keeping rather than quietly overwriting: an instrument that happens to be correct is still an instrument nobody checked.

### 2026-08-05 — He asked for a page, and the system could not hear the word

*Plain summary: the dispatch corridor told the operator it was building a command-line tool when he had asked for a web page, because the one word he used was the one word the platform scan did not carry. Nothing raised an error. The fix is a vocabulary table that generates its own tests, because this was the third time in one day the same shape appeared.*

The failure is small enough to state in a sentence and it took me a while to accept that the sentence is the whole of it. On 2026-07-29 he asked for "one page that displays my two recipes from `assets/recipes.txt` as vertical steps with my photos", and the plan card came back "Building this as: a command-line tool", "a Python project". For a recipe web page. On a project whose banked interview answer literally said "both — computers and phones in a browser".

I went looking for the bug and there isn't one. `operator_platform_signal` carried `web`, `website`, `web page`, `webpage`, `web site`, `web app`, `browser`, `html`, and the weak bare-`site` tier added mid-review a few days earlier. It did not carry bare **page**. So the scan returned the empty string, his words never reached the precedence rule at all, and everything downstream then behaved exactly as designed: the refiner saw an unanswered platform question, forced the gradeable command-line default because that is the safe thing to do with an empty project, and the card honestly disclosed the assumption it had made. Every component was correct. No exception, no log line, no failed test. The system could not hear the word he used, and there is no error path for that.

That is the same shape as most of what July surfaced, which is why I did not treat it as a one-word fix. It failed silently, in the safe-looking direction, and rendered identically to a correct result — a plan card that says "command-line tool" for someone who wanted a command-line tool is indistinguishable from one that says it because it went deaf.

So the fix is not another arm on the regex. Bare "page" is the third instance of this class in a single day — the webpage variants, then bare "ecommerce site", now this — and the rule is that the third instance ships a structural control. `OPERATOR_WEB_VOCABULARY` is one table: each weak-tier term with the compounds that disqualify it, and the tests are generated from the table rather than written beside it. Seventeen new locks, every one of them enumerated over the table's own contents, so a term contributed without its exclusions fails a test instead of shipping silently. The exclusions are the boring half and the half that matters: `title page` and `front page` are documents, `page 3` is a document, `page margins` is layout, `page me` is a verb, and `ask Page about the invoices` is a person — that last one checked against the noun's original casing, so sentence-initial "Page that shows my recipes" is still ordinary prose and still reads web. I rejected the alternative of leaving "page" out of the weak tier entirely and relying on the card's disclosure to catch it: the disclosure did catch it, once, because he was reading carefully at a ceremony. That is not a control, that is his attention, and spending his attention is the thing this arc exists to stop.

The part I did not expect is that widening the vocabulary broke the system's own prose. `shared/fleet/clarify.py` carries a planner-facing steer whose documented contract is that it names no platform, precisely so it cannot override the operator's choice — and the web variant read "the page is only the face". The moment "page" became a web word, that system-authored sentence started reading as *the operator* naming a platform. `test_the_gradeability_steer_is_for_the_planner_and_names_no_platform` went red in the same run that made my new tests green. The test was right and the prose was wrong; the steer now says "the view is only the face", and I changed its comment to point at `OPERATOR_WEB_VOCABULARY` as the authority rather than asserting "names no platform" on its own word. That property was never this module's to assert — it is a claim about a word list another module owns, and it was true only until that list changed. Gate-locked, not asserted, is the only version of that claim worth writing down.

Gate on the tip that merged: 10162 passed, 0 failed, 0 skipped, 129 deselected in 343.34 s, primary checkout with models present and the nightly battery stood down. The +17 is exactly these locks, and both doctrine surfaces moved in the same commit. The merge tree hash is byte-identical to the gated tip, so the result carries by proof rather than by the assumption that a merge of one branch changes nothing.

A lesson number is owed here and I am not minting it. `LESSONS.md` sits about 1.7 KB under its 125,000-byte gate ceiling, and #1255 records that the next ordinary fold breaches it and turns the standing gate red for whoever is mid-merge at the time. Minting tonight to look complete would hand that failure to the next session. The lesson — that a control which cannot hear a word cannot be fixed by more care, only by making the vocabulary the data its tests enumerate — is recorded here and owed on #1255.

**Next:** F-B, the serious half of #1161, where a project that already holds his answer still treats the question as unanswered — a remembered answer is an answered question, and it belongs at the same precedence tier as a typed one. Then #1251's computed `Coverage`, which needs its own battery night.

### 2026-08-06 — The harness tells me the date in UTC, and his evening is a different day

*Plain summary: I built an entire comprehension gate on the wrong date because the date the tooling hands me is UTC and he was seven hours behind it, then drifted eight hours later the same session. The clock is now the first step of grounding, because reading it costs a second and not reading it corrupted everything downstream.*

He asked whether there is a structural foundation for me to know his actual wall-clock time, given that he changes timezone every few weeks. There was not, and the gap had already cost twice in the session he was asking during.

The first instance is the worse one because it poisoned a checkpoint rather than a passing remark. My opening comprehension gate stated the date as 2026-08-06 and computed every staleness figure from it: the landing card was "seven days stale", `main` had been frozen "seven days", July's retrospective was "six days overdue". The machine's local time was 2026-08-05 22:04 Pacific. Every one of those numbers was a day out, and I presented them to him as grounded facts in the artifact whose entire purpose is proving I ground myself. The harness injects `Today's date is …` in UTC; his evening is the next UTC day; I never questioned it because a date arriving as ambient context does not feel like a claim.

The second instance is more ordinary and more embarrassing. Hours later I had drifted to believing it was just after midnight — I had taken a clock reading at 22:33, then kept adding my own sense of elapsed time to it rather than re-reading. He corrected me: "it is only 7:48am! you should be completing like a dozen or two loops before 23:00!" I was eight hours off, and the consequence was real: I had been treating the nightly battery as an imminent constraint to work around when there were fifteen hours of runway, and I had told him a battery could not be re-run in time when it could.

Both are the same defect. `MEMORY.md` already carried two lines about exactly this — "verify current time, no fixed timezone" and "measure time, never narrate it" — and I had read them at session start, and they changed nothing. An advisory line in a context file is not a control. It sits in the same bucket as every other piece of ambient knowledge and loses to whatever number is closest to hand, which is precisely the injected UTC date.

So the fix is a grounding step, not another note. `<grounding>` in CLAUDE.md now opens at item 0 with the clock: read local wall-clock and timezone from the machine, treat the harness's date as UTC and therefore as a different day, take a timezone he states over the machine's and over anything remembered, and re-read before any staleness, overdue, stall or kill judgment. It is the cheapest item on that list — one command — and it is first because four of the other five produce numbers that are meaningless if the date is wrong.

The trade-off I considered and rejected was making this a rule in `LESSONS.md` instead. That would have been the natural home for the judgment, and it would have been the third advisory line about time in a file whose advisory lines about time had already failed twice that morning. The grounding list is executed; the lesson index is read. When the same class fails twice in a session, the answer is to move it from something you know to something you do.

One honest limit stays in the doctrine text: the machine's timezone is authoritative for the machine, not for him. If he lands somewhere and the box has not caught up, the machine will confidently report the old zone. That is why a timezone he states outranks it — the only reliable source for where he actually is remains him.

**Next:** the same question applied to the other ambient facts the harness supplies, which I have never audited for whether they are true in his frame or merely true in the tooling's.

### 2026-08-06 — Two standing authorizations that only existed in my head

*Plain summary: he asked whether future sessions know they may spin up subagents and may run the battery on demand. One was authorized but contested by the tooling's own instructions, the other was not written down anywhere. Both are now in the rule block that survives compression.*

He asked the right question twice in a row: does every future session know it can fan out teammates, and does it know the loop directive without him pasting it into chat. I checked rather than answered, and the two cases turned out to be different failures.

Subagents were authorized — `critical_rules` rule 9 has said "fan out subagents, worktree builders, local scripts" for weeks. But every session also receives, in its harness prompt, the line "Do not call the AgentTool unless the user requested it." That is a Claude Code binary constant, not his instruction, and nothing in CLAUDE.md said so. The conflict was resolved only in a memory file, which is exactly the wrong altitude: a memory line is ambient, and the harness line is explicit and imperative. I hesitated on it myself this morning before going to check. So rule 9 now names the constant and states that it overrides it. A standing authorization that loses an argument with the tooling is not standing.

The battery was the plainer gap. CLAUDE.md described the rhythm — "overnight GPU window opens 23:00 unconditionally" — and said nothing about triggering a run any other way. So the battery reads as an end-of-day event, and I treated it as one until he corrected me: "triggering the battery is part of the development loop! it is only 7:48am! you should be completing like a dozen or two loops before 23:00!" He was right, and `battery-bootstrap.ps1 -Now` had existed the whole time, with a `-CampaignConfig` side-file path for a probe that banks nothing. Rule 9 now says the battery is a loop input and names both flags.

The trade-off was where to put them. `autonomy` is the natural home and already carries the fan-out reasoning, but rule 9 is the block marked "the 10 rules that must survive any context compression", and both of these fail specifically under pressure — when a session is deep, cautious, and looking for a reason not to spend the machine. Depth is exactly when a compressed rule block is all that is left. CLAUDE.md is now 47,505 of its 48,000-byte budget, so that placement cost most of the remaining headroom, and the file is one ordinary addition from the ceiling — the same shape as LESSONS.md's #1255, and worth a trim pass before the next thing needs to go in.

**Next:** audit the rest of what the harness supplies for the same shape — ambient instructions that contradict doctrine and are only reconciled somewhere too quiet to win.

### 2026-08-09 — The monitor I built to detect a quiet tree was watching two corpses

*Plain summary: A tool built to answer "is anyone still working here?" checked whether certain processes existed, not whether they were doing anything. Both processes it kept finding were watching files that had stopped changing hours and days earlier — one log ended six hours before I even looked at it, the other two days. The real answer had been sitting in a timestamp the whole time, and a standing-gate test I found afterward turned out to be the same mistake wearing different clothes.*

I was asked to work the public-mirror sync — the weekly job that copies this repository to a public GitHub mirror. It had been silently failing since 08-03, and the instinct was to fix it and move on. Reading before acting stopped that: a July retrospective entry said the mirror was "correctly frozen" because the current journal named a private codename, and a ticket (#1104) already had an independent investigation from two nights earlier reaching the same conclusion in more detail — the leak-gate had found a real hit, not a false positive, and explicitly escalated the content question rather than deciding it. Nothing about that had changed since; the codename references had merely moved, verbatim, into a July archive file when the month rotated, which is not the same as being resolved.

An independent gate review, before any of this reached the Lead Architect, caught two real defects in my draft: I'd named the wrong branch as "someone's live work" when the actual state was three different branches in thirty minutes, none of them anyone's parked edits, and the message had visibly garbled text in three sections. Both were fixed before he ever saw them. Then he asked to see the flagged text directly rather than take my summary — and he was right to: when I quoted it verbatim, I miscounted it as three codename mentions in my own summary sentence, when I had correctly worked out four just a few lines earlier in the same reasoning. He decided (correctly, on the complete text either way): not privacy-sensitive, fine to be public. A second independent review of the resulting decision record caught that I had also mischaracterized the leak-gate itself as having "false-blocked" — wrong, and the opposite of what the ticket's own record said: *"the control worked, and the only reason this is not an incident is that it worked."* Two reviews, two rounds of me being wrong about a claim I could have re-derived instead of restated, both caught before landing.

The mechanical half was small: a bookkeeping ref had drifted two commits behind the real remote tip, so I realigned it and built `scripts/check_public_mirror_sync.py` — an on-demand check, tested against real throwaway git repos rather than mocked git calls, that reports the drift instead of failing silently for nine days like the thing it replaces almost did twice. Gate-green, independently reviewed, ready to merge in under an hour. Then it sat for three more, because the primary checkout was taking a new merge every fifteen to twenty minutes and the nightly battery window opened on top of that — correctly not merging into a tree something else is using is not a failure, but it meant the actual work was done long before it could land.

He asked me to set up monitoring so I would not miss the signal. I built one: poll every ninety seconds, look for processes matching battery- and dispatch-shaped command lines, require the match to be empty for five consecutive checks plus twenty quiet minutes on `main` before declaring it safe. It reported "still busy" identically four times across ninety minutes — same six processes, every check. That consistency is what made me stop trusting it rather than keep waiting on it. I read the two log files the matched processes were tailing. One had last written at 18:21:06 that evening — a fleet run that had ended, its retry left unused, six hours before I even looked. The other had last written 2026-08-06 20:14:36 — two days stale. Neither `tail -f` had received a byte since, and neither ever would; they were watching corpses, and a process attached to a dead file looks, to a liveness check, identical to one attached to a live one. A broader sweep found nothing else running that mattered, and the nightly battery's own Task Scheduler record showed it had fired at 23:00:01 and exited within the hour — a stand-down, not an overnight run. `main` had genuinely been idle since 22:15:35. I merged on that direct evidence rather than the monitor's, at 00:51:43 — `a208b705`.

The post-merge gate re-run, required regardless of how small the change looks, turned up a third instance of the identical shape, in a file my merge never touched. Three tests in `shared/tests/test_image_placement.py` assert against a live external site directory outside git, pinned to whatever it looked like when the tests were written that same evening — two unused images, one report shape. Re-run three and a half hours later, the site has since been regenerated with a different asset-naming scheme entirely; the tests don't have a stale answer, they have no answer the current shape can even parse. I confirmed by structural proof, not inference, that my merge could not have caused it — `git show --stat` touches zero files the test imports — diagnosed it, and left it flagged on the ticket that owns the context (#1349) rather than guess at a fix on someone else's active arc at one in the morning.

Three instances in one session, all the same defect: a value captured at one moment gets treated as still describing the present, and nothing re-checks it against what actually changed underneath. My own summary sentence, a monitor's process list, a test's hard-coded expectation — the mechanism differs each time and the shape does not. This reads like the same family as the instrument-honesty arc already running in this project (#1241 and its kin): the failure is never that the check runs and lies, it's that the check answers a question adjacent to the one being asked, and the adjacency is invisible until someone reads the timestamp instead of trusting the presence.

Gate on merged main: 10840 passed, 3 failed (diagnosed, unrelated, flagged on #1349), 0 skipped, 133 deselected. The pre-merge branch measurement was 10787 passed, 0 failed, 23 skipped (documented gitignored-model/docset delta) — the difference is everything else that landed on `main` in the hours the merge waited.

**Proposed lesson:** *A liveness check that matches on process presence, not on evidence the process is still producing anything, cannot distinguish an active worker from an orphaned watcher of a file that stopped changing. Check the timestamp inside, not the process outside.* Possibly a recurrence of the #1241 instrument-honesty class rather than a fresh number — worth checking against that index before minting, not asserting here.

Neither is mine to pick up tonight. *(Corrected below — the LA asked directly, that tree was free, and I did pick the allowlist half up an hour later.
